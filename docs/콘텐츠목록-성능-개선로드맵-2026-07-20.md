## 2. 슬라이스

### 391 — 브리핑 오디오 자동 다운로드 차단 🔴 최우선 · 한 줄
**왜 1순위**: 전송량의 100%이고, 고치는 비용이 가장 싸다.

`FloatingBriefingMini.tsx:91` · `MorningBriefingPlayer.tsx:78` 의 `new Audio(briefing.audio_url)` 는 **기본 `preload="auto"`** 라 생성 즉시 파일 전체를 받는다. `FloatingBriefingMini` 는 `DashboardShell` 에 상시 렌더되므로 **모든 대시보드 화면에서** 8~9MB 를 받는다. 재생 버튼을 누르지 않아도.

- `preload = 'none'` 지정, 또는 **재생 클릭 시점에 Audio 객체 생성**으로 변경.
- **같은 파일을 두 번 받는 원인 규명**(8.63MB + 9.42MB). 오디오 객체 중복 생성 또는 재시도로 보인다.
- ⚠️ 재생·일시정지·진행률·`audio_duration_seconds` 표시가 깨지지 않아야 한다. 지연 생성 시 첫 재생 지연이 생기므로 버튼 상태 처리 필요.
- 검증: 전송량 **1MB 이하**, wav 요청 **0건**(재생 전).

### 392 — 키워드 칩 API 재설계 🔴 SQL 핸드오프
**왜 2순위**: 응답 **372바이트에 1.59초**. 순수 서버 처리 시간이라 리전·캐시로 못 덮는다.

`src/app/api/contents/keywords/route.ts` 는 칩 12개를 위해 **30일치 published 뉴스 전 행의 `matched_keywords` 를 1,000건씩 페이지네이션해 전부 앱으로 가져와 메모리에서 집계**한다(`while(true)` + `QUERY_PAGE_SIZE = 1000`).

- **DB 집계로 내린다** — `unnest(matched_keywords)` + `group by` + `order by count desc limit 12` → RPC 또는 뷰. 앱은 12행만 받는다.
- **응답 캐시** — 30일 집계라 분 단위 신선도로 충분. `revalidate` 또는 `Cache-Control: s-maxage`.
- ⚠️ **SQL 핸드오프 필요**(수희).
- 함께 확인할 것: `summary_ko` 결측 비율 (count 쿼리 한 줄 — 393 판단 근거).
- 검증: 칩 응답 **200ms 이하**.
- 📌 **커밋 시 같이 넣을 것**(디렉터 결정 2026-07-20): `docs/sonnet-지시서/390-콘텐츠목록-체감속도-실측.md` · `docs/콘텐츠목록-성능-개선로드맵-2026-07-20.md` — 측정 근거·판정 기록이라 미커밋으로 두지 않는다.

### 393 — 폰트 · 표지 이미지
**왜 3순위**: 391 이후 남는 전송량의 대부분.

- **폰트**: `PretendardVariable…woff2` **2.06MB**, 3회 요청. 한글 가변폰트 전체를 서브셋 없이 싣는다.
  → 서브셋(사용 글리프 한정) 또는 `font-display` 전략 조정. 3회 요청 원인도 규명.
- **표지 404**: `AIDC.jpg`·`통신 b2b.jpg`·`뉴스.jpg` 등 **7건이 0B/404**. `public/topic-covers/*.jpg` 40여 개가 미커밋이라 프로덕션에 없다. **카드 표지가 깨져 있다.**
  → **이 레인 산출물 확인됨**(디렉터, 2026-07-20). 커밋하면 해결.
- **이미지 최적화**: `ContentCard.tsx:82` 주석(`next/image remotePatterns 미설정 → unoptimized`) 확인. 다만 측정에서 `/_next/image` webp 응답(1.49KB·1.68KB)도 관측됐으므로 **실제 적용 범위를 먼저 확인**하고 필요한 곳만 전환.
- 검증: 표지 404 **0건**, 폰트 전송량 감소.

### 394 — 체감 개선 (연출·스켈레톤)
**왜 마지막**: 391~393 으로 실제 시간이 줄면 **필요한 연출의 양이 달라진다.** 먼저 넣으면 숫자를 가려 회귀를 못 본다(390 §4).

390 §6.1 채택분 + 2026-07-20 외부 검토 2차 반영.

**원칙: 최초 로딩 = 정확한 스켈레톤 / 재조회 = 기존 목록 유지 + 진행선.**
스켈레톤은 **정확할 때만** 스피너보다 낫다. 부정확한 스켈레톤은 스피너보다 나쁘다 — 지금이 그 경우다(아래 ①).

- **① 스켈레톤 한 종류로 통일 + 실제 카드와 일치**
  `contents/loading.tsx`(16:9 이미지 블록 **있음**) ↔ `ContentsBoard.SkeletonCard`(**없음**) 로 모양이 3번 바뀐다. 특히 **실제 카드에는 큰 썸네일이 있는데 `SkeletonCard` 에는 이미지 영역이 없어**, 데이터 도착 시 없던 사진이 튀어나오며 레이아웃이 크게 뛴다. 이것이 디렉터가 지적한 깜빡임의 정체다.
  구조: 썸네일(16:9) · 카테고리·날짜 · 제목 2줄 · 요약 2~3줄 · 소스·키워드.
- **② 카드별 막대 길이 변주** — 현재 6개가 완전 복제본이라 인공적이다. 제목 길이·요약 줄 수·메타 폭만 조금씩 달리해도 자연스러워진다.
- **③ 명암 규칙** — `배경 < 스켈레톤 면 < 카드 경계`. 현재 흰 배경 대비가 너무 낮아 "로딩 중"이 아니라 "덜 그려진 페이지"로 읽힌다. 다만 **진하게 만들기보다 미세한 펄스**로 상태를 전달한다. **좌우로 강하게 흐르는 shimmer 는 쓰지 않는다**(뉴스 화면에서 산만).
- **④ 키워드 칩 영역 높이 예약** — 칩은 `/api/contents/keywords` 응답 후 렌더되므로 늦게 나타나며 **아래 스켈레톤을 밀어낸다.** 스켈레톤 모양을 맞춰도 칩 줄이 늘어나는 순간 레이아웃이 뛴다. 최소 높이를 잡아둘 것. (392 로 완화되지만 없어지지 않는다.)
- **⑤ 전환 시 이전 목록 유지** — `setItems` 를 비우지 않고 `opacity 0.85` + **콘텐츠 영역 상단 2px 진행선**(브랜드 마젠타) + 120~180ms 페이드.
  적용: 탭 재방문 · 키워드 선택 · 검색 · 페이지네이션 · 상세→목록 복귀.
  (카드↔목록 전환은 이미 재호출되지 않음 — `newsView` 가 fetch effect 의존성에 없음.)
  **원형 스피너는 쓰지 않는다.** 목록 *전체*가 갈리는 상황이라 우상단 소형 스피너는 "국소 갱신" 신호가 되어 범위가 맞지 않는다. 진행선이 "이 영역 전체가 갱신 중"을 정확히 말한다. 텍스트를 곁들이려면 진행선 + `결과 업데이트 중` 조합.
- **⑥ 로딩 사다리** — ~200ms 무표시 / 200ms~ 스켈레톤(뜨면 **300~400ms 최소 유지**) / 1.5s~ 문구 / 5s~ 재시도·오류 안내.
  ⚠️ **200ms~1.5s 구간에 문구를 함께 띄우지 않는다.** 스켈레톤이 이미 "로딩 중"을 말하므로 신호가 중복된다. **문구는 1.5s 이후에만.**
- **⑦ 보이는 상태와 실제 동작의 일치** — 로딩 중 검색창이 눌리는데 아무 일도 안 일어나면 안 된다.
  **확인 결과: 현재 검색은 URL 파라미터를 바꾸는 방식이라 로딩 중에도 정상 동작한다.** 따라서 **비활성화하지 말고 활성 유지**한다.
- **⑧ 초기 카테고리 확정** — `/dashboard/contents` 무파라미터 진입 시 `category=''` 1차 쿼리 + `router.replace` 2차 쿼리(390 §1-e). 서버 확정하거나 첫 쿼리를 미룬다. `050b4a6`(#90) 패턴 참고.

> **비교 근거**(디렉터 제시, 2026-07-20): Firebase 콘솔은 중앙 스피너 하나를 쓴다. 그쪽이 옳은 이유는 **본문 모양을 예측할 수 없기** 때문이다(프로젝트 상태에 따라 다름). 우리는 항상 카드 그리드라 모양이 확정적이므로 스켈레톤이 맞다. **단, 약속한 모양이 실제와 같아야 한다** — ① 이 그래서 이 슬라이스의 핵심이다.

## 3. 보류 — 측정으로 우선순위가 내려간 것

| 항목 | 사유 |
|---|---|
| **`body_original` select 제거** | `contents` 응답이 **49.19KB**. 20건에 49KB면 원문이 거의 안 실려 있다. 빼도 체감 변화 없음. 코드 정리 차원에서 언젠가. |
| **`count: 'exact'` 분리** | **기각.** 대상 4,126행 + 237 인덱스 → 수 ms. 390 §8.1. |
| **첫 페이지 SSR 주입(R1)** | 전체 로드가 이미 1.18초. 391~393 후 재측정하고 판단. `ContentsBoard`(654줄) 구조 변경은 2량 이상. |
| **`users` 조회 서버화** | 185~307ms, 858B. `DashboardHeader` 클라이언트 조회. 전 화면 공통 셸이라 이 레인 범위 아님. |
| **RSC prefetch 정리** | **손대지 않는다.** `issues`·`search`·`dashboard`·`mypage` 는 API 가 아니라 prefetch 이고, `prefetch-ok` / `prefetch={false}` 규율이 이미 서 있다. 390 §393-A. |

## 5. 규율

- **슬라이스마다 재측정.** §1 과 같은 방법. 숫자 없이 "빨라진 것 같다"로 넘어가지 않는다.
- **연출을 먼저 넣지 않는다.** 390 §4.
- **추정 금지 — 이번에 세 번 틀렸다.**

  3. `body_original` 페이로드 → 49KB 라 영향 미미
  세 번 다 **구조만 보고 크기를 확인하지 않은 것**이 원인이다. 다음엔 코드를 읽기 전에 숫자부터 잰다.
