## 0. 목표·범위

## 1. 아키텍처 개요

```
Vercel Cron (05:00 KST)
   └─> POST /api/cron/crawl          (서버 라우트, CRON_SECRET 검증)
         └─> Orchestrator
               ├─ sources 조회 (is_active=true, 주기 도래분)
               ├─ 소스별 Adapter 실행 (RSS | API)  ── 병렬, 소스 단위 격리
               │     └─ raw item[] 추출
               ├─ Normalizer (메타 표준화 + 해시 계산)
               ├─ Dedup 3단계 (URL → title_hash → body_hash)
               ├─ (후속) Quality/Keyword 필터 #13
               ├─ Upsert → contents (service_role, 멱등)
               └─ crawl_logs 기록 (소스별 성공/실패/건수)
```

핵심 원칙

1. **소스 단위 격리** — 한 소스 실패가 전체를 멈추지 않음(`Promise.allSettled`).
2. **멱등성** — 같은 글 재수집해도 중복 안 생김(`original_url` 유니크 + upsert).
3. **service_role 적재** — 크롤러는 RLS 우회(AGENTS §7). 절대 클라이언트에 노출 금지, 라우트 내부 전용.
4. **무상태 + 짧은 실행** — Vercel 함수 타임아웃 대비, 소스별로 잘게.

## 2. 소스 모델 (sources 테이블 활용)

`#1` 에서 만든 `sources` 를 그대로 사용:

| 컬럼 | 크롤러 사용처 |
|---|---|
| `type` | 어댑터 선택 (`news_site`→RSS/HTML, 후속 `youtube_channel`→API …) |
| `rss_url` / `url` | 수집 엔드포인트 |
| `is_active` | 수집 대상 on/off |
| `crawl_interval_minutes` | 주기. null=수동(크론 제외) |
| `last_crawled_at` | 주기 도래 판정 + 증분 수집 기준 시각 |

**어댑터 인터페이스(공통)**

```ts
interface SourceAdapter {
  type: SourceType
  fetch(source: Source, since?: string): Promise<RawItem[]>
}
interface RawItem {
  original_url: string
  title: string
  body?: string
  author?: string
  published_at?: string
  thumbnail_url?: string
  language?: string   // 미상이면 추론
}
```

`news_site` 1차 구현: **RSS 우선**(가볍고 안정), 본문 부족 시 원문 fetch + 본문 추출(`@extractus/article-extractor` 등) 폴백.

## 3. 스케줄링

- **Vercel Cron**: `vercel.json` 에 `{ "crons": [{ "path": "/api/cron/crawl", "schedule": "0 20 * * *" }] }` — UTC 20:00 = **KST 05:00**.
- 라우트는 `CRON_SECRET` 헤더 검증(외부 호출 차단).
- Orchestrator 가 `crawl_interval_minutes` + `last_crawled_at` 로 **이번 틱에 돌릴 소스만** 선별 → 소스별 주기 차등 가능(뉴스 매일 / 리포트 주1회 등).
- ⚠️ **Vercel 로그 접근 불가**(용주 계획서 위험메모) → 실패 진단은 `crawl_logs`(아래)로 자체 관측.

## 4. 중복 필터 3단계 (스키마 연계)

`#1` 에서 심은 컬럼을 그대로 사용. 단계가 올라갈수록 비용↑ 이므로 **싸고 확실한 것부터**:

| 단계 | 기준 | 구현 | 스키마 |
|:---:|---|---|---|
| 1 | **원문 URL 동일** | upsert `on conflict (original_url)` → 무시/갱신 | `contents_original_url_key` 부분 유니크 |
| 2 | **제목 유사(정규화)** | 제목 소문자·공백·문장부호 제거 후 `sha256` → `title_hash` 매칭 | `contents_title_hash_idx` |
| 3 | **본문 동일** | 본문 정규화 후 `sha256` → `body_hash` 매칭 | `contents_body_hash_idx` |

- 2·3단계는 적재 전 `select 1 from contents where title_hash=$1` 로 선조회(인덱스 사용).
- **유사도(편집거리)까지 필요하면** Sonnet #12 에서 임계값 기반 비교 추가(해시는 완전일치만 잡음 → near-dup 은 #12 범위). 본 설계는 해시 완전일치까지 책임지고, fuzzy 는 #12 로 위임.

## 5. 멱등 적재

```sql
insert into contents (category, source_id, title, original_url, body_original,
                      title_hash, body_hash, published_at, collected_at, ...)
values (...)
on conflict (original_url) where original_url is not null
do update set
  title = excluded.title,
  body_original = excluded.body_original,
  updated_at = now();   -- view_count/bookmark_count 등 사용자지표는 보존
```

- `on conflict` 갱신 시 **사용자 파생 컬럼(view_count·bookmark_count·is_editor_pick) 은 덮지 않음**.
- 카테고리·서비스 매핑은 적재 후 `content_services`/`content_keywords` 별도 upsert.

## 6. 실패 처리·재시도·로그 — 신규 테이블 제안 `crawl_logs`

> ⚠️ 스키마 추가 필요(현재 없음). Sonnet #23 "크롤링 현황 페이지"가 읽을 데이터 = 이 테이블.

```sql
create type crawl_status as enum ('success', 'partial', 'failed');

create table public.crawl_logs (
  id            uuid primary key default gen_random_uuid(),
  source_id     uuid references public.sources (id) on delete set null,
  status        crawl_status not null,
  fetched_count integer not null default 0,   -- 가져온 raw 건수
  inserted_count integer not null default 0,  -- 신규 적재
  duplicate_count integer not null default 0, -- 중복 스킵
  error_message text,
  started_at    timestamptz not null default now(),
  finished_at   timestamptz,
  created_at    timestamptz not null default now()
);
create index crawl_logs_source_idx on public.crawl_logs (source_id, created_at desc);
-- RLS: admin 조회만 (인증 사용자 노출 불필요)
```

재시도 정책

- 소스 fetch 실패 → 해당 소스 즉시 `failed` 로그 + **다음 틱 재시도**(별도 즉시 재시도 안 함, 단순화).
- 일시 네트워크 오류 한정 **소스 내 3회 지수백오프**(0.5s·1s·2s) 후 포기.
- 부분 성공(일부 item 파싱 실패) → `partial` + 성공분만 적재.

## 10. PRD 4장 반영 (2026-05-30 Notion 확인)

PRD v2.1 4장 확인 결과 설계에 반영/보완할 점:

- **소스 = admin 관리 데이터** (하드코딩 X). 크롤러는 `sources` 에서 `is_active` 읽어 실행. → Q1 해결. 초기 seed 소스만 별도 준비(국내 IT매체·벤더 블로그·Substack/Medium RSS).
- **당일 발행분만 수집** (기본). 최초 구축/신규 소스 시 admin이 소급기간(최대 30일) 지정. → `since` 기본값 = 오늘 0시.
- **2차 중복 = 제목 90% 유사** (edit distance 또는 TF-IDF 코사인). 해시 완전일치(#3)로 못 잡는 near-dup → Sonnet #12.
- **유사 중복 처리 = 대표 1건 + "관련 기사 N건" 링크.** ⚠️ **스키마 갭**: 현재 `contents` 에 관련기사 그룹 개념 없음 → `cluster_id`(자기참조) 또는 `duplicate_of` 컬럼 필요. **백로그 BL-3**.
- **품질 보류 상태 필요**: 관련도 0.3 미만은 "보류(관리자 검토)", 어드민 "콘텐츠 승인 대기 목록" 존재. ⚠️ **스키마 갭**: 현재 `is_published` boolean 2상태 → `pending/published/rejected` 3상태(enum) 권장. **백로그 BL-4**.
- **품질 필터**(본문 300자 미만·광고패턴·관련도) = Sonnet #13.
