# 어드민 개선 — 검토와 권고 (GPT 계획서 비평 + 현실 기반 방향)

> 작성: Opus(Cowork) · 2026-07-01 · 입력: GPT 「어드민 최종 개선 계획서」 + 현재 코드 현황(as-is 문서) + 실재 인프라 확인
> 목적: "정답 없음" 전제 하에 계획서를 냉정하게 걸러 **실현 가능한 개선 방향**을 잡는다.

---

## 1. 총평

**방향(reframe)은 옳다.** "어드민 = 관리 기능 모음 → 서비스 운영 관제 시스템", 4개 축(사용자·콘텐츠·인사이트·사용성)으로 재정의한 것, 그리고 진단(기능 분산·콘텐츠 관리 과부하·수동 트리거 편중·품질관리 부재·분석 부재)은 우리가 앞서 정리한 관찰(§9)과 정확히 겹친다. 북극성으로 채택할 만하다.

**그러나 계획서 그대로는 못 간다.** 이유:
- **범위 과대.** 신규 페이지 ~15개(작업 큐·품질 진단·중복관리·제외규칙·검수함·5개 분석·TTS·감사로그…) + 대규모 인프라 2종. 슬라이스 1개씩 도는 팀 속도로는 수개월. "한 번에" 하려다 아무것도 못 끝낸다.
- **가정한 인프라가 실재하지 않는다**(아래 §2). 특히 분석(Phase 5)과 작업 큐(Phase 3)는 UI가 아니라 **바닥부터 짓는 기반 공사**다.
- **LLM 키 블로커와 충돌.** 인사이트 검수(Phase 4) 강화는 정작 생성이 LLM에 막혀 있어 가치가 상한에 걸린다.

결론: **reframe은 채택, 실행은 "가치 × 실현가능성 × 블로커"로 재정렬**한다.

## 2. 현실 점검 — 계획이 가정한 것 vs 실재

| 계획서 전제 | 실재 여부 | 함의 |
|---|---|---|
| 사용자 이벤트/애널리틱스(DAU·MAU·퍼널·성과) | **없음** (events 테이블·클라 로깅·PostHog류 0) | Phase 5는 UI가 아니라 **계측 인프라부터**. 최대 net-new. |
| 작업 큐/자동화 로그(재시도·상태·비용) | **없음** (jobs는 `after()`+cron, 큐 테이블 없음) | Phase 3은 **큐 인프라 구축**. 읽기전용 로그부터가 현실적. |
| 콘텐츠 품질 점수(복합) | **없음** (구성요소가 흩어짐) | 점수 구성요소부터 실재 확인 필요(아래). |
| 중복 탐지 | **부분 존재** (`crawler/dedup.ts`·`feed-dedup.ts`·`cluster_id`) | 중복 후보 UI는 기존 로직 위에 가능. |
| 본문/링크 건강 | **존재** (152 콘텐츠 건강 대시보드·155 link_ok) | 품질 진단의 씨앗 이미 있음. |
| 출처 신뢰도 등급·분류 신뢰도 확률·엔티티 추출 성공률 | **불확실/부분** (trust_tier·importance_score 타입은 있으나 등급 체계·분류 확률은 미확인) | 품질 점수를 지금 만들면 **껍데기** 위험 → "있는 신호로 시작, 없는 건 후속". |
| 인사이트 근거·인용 데이터 | **존재** (citations·source_content_ids) | 인사이트 검수 UI(근거·체크리스트)는 지금도 가능. 단 생성은 LLM 블로커. |

> 핵심: **분석과 작업 큐는 "짓는 것", 품질·검수·대시보드는 "기존 위에 세우는 것".** 난이도·선행조건이 완전히 다르다.

## 3. 냉정한 우선순위 재배치

가치(서비스/운영 임팩트) × 실현가능성(선행조건·블로커) 로 4구간:

**A. 지금·저비용·고가치 (선행조건 없음, 기존 자산 활용)**
- **운영 대시보드 "오늘 할 일 + 파이프라인 상태"** — 기존 대시보드·152 건강 지표 재구성. 매일 가치.
- **콘텐츠 검수함 + 반려 사유 코드** — 콘텐츠 관리에서 "검수 흐름"만 분리. "쓰레기 거르기" 핵심의 첫 발.
- **콘텐츠 관리 화면 분리**(검수 vs 보강 배치) — 위험한 대량작업을 검수와 떼어냄.

**B. 기반 공사지만 가치 큼 (제대로 지어야, 단계적으로)**
- **최소 이벤트 로깅 + MAU/DAU 1개 페이지** — 4번째 목적(사용성)의 토대. **5개 분석 페이지가 아니라 씨앗 1개부터.** 퍼널·콘텐츠 성과는 트래픽·이벤트가 쌓인 뒤.
- **작업 로그(읽기 전용)** — 먼저 cron/after 실행 결과를 "보이게". 재시도·큐는 그 다음.

**C. 선행 신호 확정 후 (지금 만들면 껍데기 위험)**
- **콘텐츠 품질 점수 + 중복·저품질 관리 + 제외 규칙** — 구성 신호(출처등급·분류확률 등)를 먼저 실재화하거나, **있는 신호(본문길이·link_ok·dedup·중복률)만으로 v1**을 짜고 나머지는 후속(인사이트 카드에서 쓴 규칙-폴백 접근 그대로).

**D. 블로커·저리스크라 후순위**
- **인사이트 검수 강화**(근거·체크리스트·부분 재생성) — UI는 가능하나 **생성이 LLM 블로커**라 효용 상한. 키 연결 즈음 착수.
- **작업 큐(재시도·비용)·권한 세분화·감사 로그·TTS 별도 메뉴** — 사용자 수 적을 땐 리스크 낮음. 운영 성숙기.

## 4. 권고 시퀀스 (GPT의 6-Phase 대체)

> 원칙: 큰 리네임·빅뱅 재편은 피하고, **페이지 작업과 함께 점진적으로** 메뉴를 옮긴다(북마크·습관 보호).

**1차 — 운영 관제의 최소 실체 (블로커 0)**
1. 운영 대시보드 재구성: 상단 상태(정상/주의/장애) + "오늘 할 일"(검수대기·본문미보강·분류실패·인사이트초안·발행대기) + 파이프라인 한 줄.
2. 콘텐츠 검수함 신설 + 반려 사유 코드(중복·광고·본문부족·원문불가·관련성낮음·출처낮음·번역·요약오류). 콘텐츠 관리에서 검수 분리.

**2차 — 사용성 계측의 씨앗 (기반, 단계적)**
3. 이벤트 로깅 최소셋(login·content_open·insight_card_click·bookmark_add·briefing_play·search 등 6~8개) + events 스키마.
4. 사용자 지표 1페이지(DAU/WAU/MAU·신규·부서별 활성). **퍼널·성과는 이후.**

**3차 — 품질 관리 v1 (있는 신호로)**
5. 콘텐츠 품질 진단 v1: 본문길이·link_ok(155)·중복(dedup)·미태깅으로 "저품질 의심" 목록·소스별 지표. (출처등급 등은 후속 가중치.)
6. 제외 규칙(본문 최소길이·중복률·도메인 반려율 자동 보류) + 중복 후보 병합 UI.

**4차 — 성숙기 (여력/키 연결 시)**
7. 작업 로그→작업 큐(재시도·비용), 인사이트 검수(근거·체크리스트), 콘텐츠 성과·퍼널, 권한 세분화·감사 로그, TTS 메뉴.

## 5. 특히 조심할 점 (계획서에 대한 반론)

1. **퍼널 5종을 초기에 만들지 말 것.** 내부 도구는 사용자 수가 작아 다단계 퍼널의 통계적 의미가 약하다. **MAU·부서별 활성·콘텐츠 CTR/북마크** 같은 단순 지표가 먼저다. 퍼널은 트래픽이 붙은 뒤.
2. **품질 "점수"의 함정.** 구성요소가 실데이터로 없으면 점수는 신뢰 못 할 껍데기가 된다. "점수 먼저"가 아니라 **"신호 먼저, 점수는 있는 것부터".**
3. **인사이트 검수 강화의 순서.** 생성이 막힌 상태에서 검수 UI만 키우면 빈 그릇. **LLM 키 → 생성 품질(170) → 검수 UI** 순.
4. **작업 큐는 "로그부터".** 곧장 재시도·큐 엔진 짓지 말고, 실행 결과 가시화(읽기)로 시작해 필요를 확인.
5. **빅뱅 메뉴 리네임 지양.** "분류엔진→지식화규칙", "AI인사이트→인사이트검수" 등 명칭 변경은 좋으나 **해당 페이지를 실제로 손댈 때 함께** 바꾼다(설명 문구 추가와 세트).
6. **감사 로그·권한 5단계는 후순위.** 사용자 소수·신뢰 팀 환경에서 리스크 낮음. 발행 사고 방지(발행 전 체크)만 먼저.

## 6. 그래서, 지금 결정할 것

방향(§1 reframe·§3 우선순위·§4 시퀀스)에 동의하는지, 그리고 **1차 착수 지점**을 어디로 할지:

- (a) 운영 대시보드 "오늘 할 일 + 상태" 재구성 — 매일 쓰는 첫 화면, 즉효.
- (b) 콘텐츠 검수함 + 반려 사유 — "쓰레기 거르기" 핵심 흐름의 시작.
- (c) 이벤트 로깅 + MAU 1페이지 — 사용성 목적의 토대(단, 기반 공사).

개인 권고: **(a)+(b)를 1차 묶음**으로(둘 다 블로커 0, 서로 붙어 있음), (c)는 2차. 확정되면 사용자 화면 때처럼 **슬라이스 지시서**로 쪼개 진행한다.
