# 성능 테스트 로그 → 리전 이동 결정 (2026-07-12)

> 목적: **"리전을 옮긴다"** 는 결론에 **어떻게 도달했는지** 를 남긴다.
> 다음 세션이 *"왜 콘텐츠 목록을 SSR 안 했나"*, *"정말 리전을 옮겨야 하나"* 를 다시 묻지 않도록.
> 관련 지시서: 316(`4724955`) · 317 · 318(`8af73a7`).

---

## 0. 결론 (먼저)

**서울↔시드니 왕복 ~170ms 는 코드로 줄일 수 없다.**
prefetch 폭주 · 페이지 셸 블로킹 · 캐시 부재를 **전부 잡은 뒤에도**, 모든 요청이 여전히 태평양을 건넜다.
코드로 짜낼 수 있는 건 다 짰다. **남은 병목은 물리적 거리 하나다.**

**→ Supabase + Vercel 리전을 시드니 → 서울로 옮긴다.**
**→ 지금이 유일한 기회다** — 콘텐츠 4,538건 · 리포트 13건 · 사용자 소수 · **오픈 전.**

---

## 1. 테스트 로그 — 가설을 하나씩 지운 과정

각 단계: **가설 → 측정 방법 → 결과 → 다음.**

### T1. "브라우저가 시드니 Supabase 를 직접 부른다" — ⚠️ 성급히 철회했다가 나중에 재확인
- **측정**: DevTools Network, `supabase.co` 필터
- **결과**: `supabase.co` 요청이 **0개로 보였다** → 가설 철회
- **함정**: **DevTools 도메인 열이 프로젝트 ref(`nkfvgeltrgrojsc…`)로 잘려서** `supabase.co` 글자가 안 보였을 뿐이다. **요청은 있었다.** (T6에서 재확인)
- **교훈**: 화면에 안 보인다고 없는 게 아니다. **도메인 열을 넓혀서 실제 호스트를 확인했어야 했다.**

### T2. "prefetch 폭주가 원인이다" — ✅ 맞음
- **측정**: DevTools Network, `?_rsc=` 필터, L1 탭 클릭
- **결과**: **UUID 이름의 RSC 요청 수십 개**, 각 550~700ms, 일부 1.4초. `issues` 1.37초.
- **원인**: 목록 카드가 뷰포트에 들어오면 Next.js 가 `/dashboard/contents/[id]` 를 prefetch. 그 페이지가 `force-dynamic` 이라 **prefetch = 실제 서버 렌더 + DB 쿼리 7~8개.** 카드 20개 = 서버 쿼리 ~150개.
- **다음**: 316 착수

### T3. "`staleTimes` 캐시로 덮으면 되나" — 🟡 부분적, 그리고 역효과
- **측정**: 316 배포 후, 같은 탭을 30초 안에 재방문 / 30초 후 재방문
- **결과**: 2회차는 즉시(캐시 히트), **30초 후 다시 느려짐**(캐시 만료). 그리고 **`staleTimes.dynamic > 0` 이 dynamic full prefetch 를 켜서 L1 탭이 오히려 더 느려졌다.**
- **교훈**: **캐시는 cold 렌더가 느린 걸 숨길 뿐 고치지 못한다.** David 관찰과 정확히 일치 — *"하위탭은 빨라졌는데 L1 탭은 아직 느리다."*

### T4. "316 으로 prefetch 를 잡았나" — 🔴 한 갈래만
- **측정**: 318 직전, `/dashboard/issues` 에서 `?_rsc=` 필터
- **결과**: **UUID 요청이 다시 수십 개.** `issues` 1.03~1.76초.
- **원인**: 316 은 `/dashboard/contents/[id]` **한 라우트만** 막았다. 이슈·기업·토픽·리포트·데일리인사이트 카드 **25곳이 여전히 prefetch.**
- **다음**: 318 (전 라우트 확대 + 빌드 가드)

### T5. "페이지 셸이 데이터를 기다리느라 막히나" — ✅ 맞음
- **측정**: 316 배포 후 Network — `entities` **816ms · 791ms**, `contents` 958ms
- **원인**: 페이지 함수 본문의 `await` 는 **화면 전체를 막는다**(`<Suspense>` 는 자식만 구한다). `trending` 7개 · `entities` 6개 · `briefings` 3개가 페이지-레벨 `await`. `entities` 는 `getUser()` → 데이터 조회가 **직렬 5회 왕복.**
- **다음**: 317 (셸 스트리밍)

### T6. ⭐ "그 UUID·`services`·`contents` 요청의 도메인이 정말 Supabase 인가" — 결정적
- **측정**: `.env.local` 확인 → `NEXT_PUBLIC_SUPABASE_URL=https://nkfvgeltrgrojscrhhlg.supabase.co`
- **결과**: **`nkfvgeltrgrojsc…` = Supabase 다.** T1 에서 안 보이던 게 바로 이거였다.
- **의미**: 콘텐츠 목록(`dashboard/contents/page.tsx`, 834줄 **클라이언트 컴포넌트**)이 **브라우저에서 시드니 Supabase 를 직접** 부르고 있었다.
  ```
  services 292ms · sources 237ms · contents 506~958ms   ← 전부 브라우저 → 시드니
  ```
  (David 확인: 이 기록은 **여러 탭을 오간 누적** — 탭마다 다시 부르는 건 정상이나, 매번 태평양을 건너는 게 문제)

### T7. "318 후 prefetch 폭주가 죽었나" — ✅
- **측정**: 318 배포 후 `?_rsc=` 필터
- **결과**: **UUID RSC 요청 0개.** prefetch 폭주 종료.
- **드러난 것**: 폭주가 걷히자 **가려져 있던 네트워크 비용이 그대로 노출됐다**(T6).

## 2. 남은 병목 — **코드로 못 고치는 것**

316·317·318 로 아래를 전부 제거했다:
- prefetch 폭주(316·318) · 페이지 셸 블로킹(317) · 페이지네이션 재-count(316) · 캐시 부재(316 staleTimes)

**그런데도 모든 요청에 붙는 고정 비용이 남는다:**

| 경로 | RTT | 성격 |
|---|---|---|
| 사용자(서울) → **Vercel(시드니)** RSC | ~170ms | **모든** 페이지 이동 |
| 브라우저(서울) → **Supabase(시드니)** 직접 | ~170ms | 콘텐츠 목록 등 클라이언트 조회 |
| Vercel(시드니) → Supabase(시드니) | ~5ms | (같은 리전이라 저렴) |

**이 170ms 는 코드 최적화로 0 이 되지 않는다.** 왕복 횟수를 줄일 수는 있어도(그래서 316·317·318 을 했다), **왕복 자체의 비용은 거리에서 온다.**

---

## 3. 왜 "리전 이동"이 답인가

- **왕복당 170ms → ~15ms.** 코드를 한 줄도 안 고치고 **모든 경로가** 빨라진다.
- **남은 병목이 이것 하나**임을 T1~T7 이 증명했다. 다른 후보(prefetch·셸·캐시·count)는 전부 소거됐다.
- **오픈 전이 유일한 창**: 데이터가 작아(4,538건) 마이그레이션이 가볍고, 사용자가 소수라 다운타임 영향이 작다. 오픈 후엔 둘 다 커진다.

### ⚠️ 함정 3개 (별도 절차서에서 다룬다)
1. **`auth.users`(로그인 계정) 마이그레이션** — 콘텐츠 테이블만 옮기고 계정을 놓치면 전원 로그인 불가.
2. **Storage 파일 복사** — 리포트 PDF·썸네일·표지 이미지.
3. **환경변수 갱신** — `NEXT_PUBLIC_SUPABASE_URL`·`ANON_KEY`·`SERVICE_ROLE` 전부 새 프로젝트 값으로.

> 사내 데이터를 호주에 두는 것 자체가 감사(compliance) 리스크일 수 있다 — 이동의 부수 효과로 함께 해소된다.

---

## 4. 리전 이동 후에도 남는 것 (별개 이슈)

리전을 옮겨도 **거리와 무관한** 비용은 그대로다. 순서상 리전 다음이다:
- **콘텐츠 목록의 브라우저 직접 호출 구조** — Vercel↔Supabase 가 같은 서울이 되면 **서버로 옮기는 편이 여전히 낫다**(왕복 자체가 사라진다). 단 309·313·297 이 전부 여기 붙어 회귀 위험이 크다.
- **검색 `title.ilike '%…%'`** — 인덱스를 못 탄다. 데이터가 커지면 느려진다. `pg_trgm`/FTS.
- **`entities` 직렬 5회 왕복**(317 §3-2) — 서울에서도 5×15ms 는 5×5ms 보다 느리다.

## 5. 측정 재현 (다음에 또 볼 때)

- **prefetch 폭주 여부**: DevTools → Network → `rsc` 필터 → 목록 진입 → **UUID 이름 요청 개수**(0이어야 함)
- **네트워크 vs 서버 분리**: Vercel → Observability → Functions → 라우트별 **실행 시간**
  - **~50ms** → 병목은 네트워크 = **리전이 답**
  - **300ms+** → 병목은 서버 = 코드(직렬 사슬 등)
- **⚠️ 스트리밍 함정**: `<Suspense>` 를 쓰는 페이지는 DevTools "시간" 열이 **스트림이 닫힌 시각**이지 사용자 대기시간이 아니다(`dashboard` 홈이 2.07초로 찍히는 이유). **숫자가 아니라 눈으로** — 껍데기가 즉시 뜨는지 본다.
