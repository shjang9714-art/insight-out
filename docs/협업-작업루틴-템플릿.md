# 협업 작업루틴 (슬라이스 루프) — 범용 템플릿

> 어느 프로젝트에나 붙여 쓸 수 있는 표준 협업 절차. 프로젝트별로 대괄호 `[...]` 항목만 채우면 됨.
> 핵심 사상: **작게 나눠(슬라이스), 지시서로 명세하고, 구현과 검증을 분리하고, 검증 통과 후에만 커밋한다.**

---

## 0. 핵심 원칙

1. **슬라이스 단위로 일한다.** 한 번에 하나의 관심사(one concern)만. 크면 쪼갠다.
2. **명세(지시서)와 구현을 분리한다.** 계획하는 사람과 코드 치는 사람이 다르면 품질이 올라간다.
3. **구현과 검증을 분리한다.** 구현자 자신의 "됐다"를 믿지 않고, 검증자가 **코드 사실을 재현**해 확인한다.
4. **검증 통과 전엔 커밋하지 않는다.** 커밋은 "합격 도장" 이후에만.
5. **불확실하면 만들기 전에 묻는다.** 잘못된 추론보다 확인이 싸다.
6. **정직성 우선.** 되지 않은 걸 됐다고 하지 않는다. 막히면 막혔다고 보고한다.

---

## 1. 역할 (4개, 프로젝트에 맞게 매핑)

| 역할 | 하는 일 | 안 하는 일 |
|---|---|---|
| **디렉터** (사람) | 방향·우선순위 결정, 위임 전달, "커밋해" 트리거 | 세부 구현, git 실행 |
| **플래너** (지시서 작성·검증) | 지시서 작성, 재현 검증(✅/🔧), 다음 스텝 제안 | **git 실행 안 함**(§1.1) |
| **구현자** (코딩) | 구현 + 타입/린트/빌드 + 완료 보고 · **커밋·병합·푸시 전담**(§1.1) | 검증 통과 전 커밋 안 함 |
| **[외부 작업자]** (선택) | DB 마이그레이션·인프라 등 코드 밖 작업 | — |

> 1인 다역도 가능(사람이 디렉터, AI 하나가 플래너+구현자). 단 **구현과 검증은 논리적으로 분리**해서, 검증 단계에선 "짠 코드를 다시 사실 확인"하는 태도로 전환한다.

### 1.1 git은 구현자만 만진다 — **디렉터도, 플래너도 하지 않는다**

**규칙**: 커밋 · 병합 · 푸시는 **전부 구현자**가 한다. 플래너는 검증 결과(✅/🔧)만 내고, 디렉터는 "커밋해" 트리거만 준다.

**왜 플래너가 하면 안 되나**
- 플래너의 실행 환경이 구현자와 다를 수 있다(다른 머신·컨테이너·마운트). 파일명 정규화, 줄바꿈, 권한, lock 파일 처리가 미묘하게 달라 **레포를 오염시키기 쉽다.**
  - 실제 사례: 플래너가 리눅스 샌드박스에서 커밋하면, macOS가 NFD로 저장한 한글 파일명이 **기존 NFC 파일의 중복본으로 추가**된다.
- 플래너는 "코드 사실을 재현 확인"하는 역할이다. **자기가 커밋한 것을 자기가 검증하면 분리가 무너진다.**

**왜 디렉터가 하면 안 되나**
- 팀이 여러 레인으로 병행하면 origin이 계속 앞서간다. 푸시 전에 **fetch → 상태 판단 → merge → 충돌 해결 → 빌드 → 푸시**를 상황에 맞게 섞어야 한다.
- 이건 판단이 필요한 작업이고, **틀리면 남의 작업을 날린다.** 디렉터가 매번 git 상태를 읽고 결정하는 건 비효율이고 위험하다.
- 미완료 병합이 남아 있거나, 다른 레인이 방금 푸시했거나, 락 파일이 꼬여 있을 수 있다. **구현자가 그때그때 판단해 처리한다.**

**구현자가 푸시할 때 할 일** (⑥)
1. `git log --oneline origin/main..HEAD` — 나갈 커밋이 맞는지 확인
2. **미완료 병합·더티 트리부터 정리** (다른 레인이 남긴 것일 수 있다 — 실제로 반복 발생했다)
3. `git fetch origin [기본브랜치]` → `git merge origin/[기본브랜치]` (**[rebase 금지 여부는 §10 규약]**)
4. 충돌 나면 **해결하고 보고**. 판단이 애매하면 **푸시하지 말고 디렉터에게 묻는다.**
5. `npm run build` (또는 프로젝트 빌드) — **통과 전엔 절대 푸시 안 함**
6. `git push` → **푸시 후 origin SHA 보고**

> 플래너가 이미 커밋해둔 상태라면, 구현자는 **새로 커밋하지 말고** 병합·빌드·푸시만 한다.

## 2. 표준 사이클 (1 슬라이스 = 1 루프)

```
⓪ 최신화(착수 전): git fetch origin [기본브랜치] && git merge origin/[기본브랜치]
   - 작업트리가 깨끗한지, 미완료 병합이 남아있지 않은지 먼저 확인
① 디렉터: 무엇을 할지 지시(방향·제약)
② 플래너: 지시서 작성 → docs/[지시서 폴더]/NN-제목.md  (아직 커밋 X)
   - 지시서 §1(현행 진단)은 ⓪로 최신화된 코드 기준으로 쓴다
   - 필요 시 구현 전 결정용 질문(포크/모호점)을 먼저 해소
③ 구현자: 지시서대로 구현 + 타입체크/린트/빌드 + 완료 보고
   - 이 시점엔 커밋·푸시 안 함
④ 플래너: 재현 검증(코드 사실 대조) → ✅ 통과 / 🔧 수정요청
⑤ 디렉터: ✅ 확인 후 "커밋해" 트리거
⑥ 구현자: 지시서 + 코드를 한 번에 커밋 → **푸시 직전 ⓪를 다시** → 푸시
⑦ 배포/반영 확인: [배포 확인 방법]으로 최신 커밋이 실제 반영됐는지 검증
```

### ⓪ 최신화가 사이클의 일부인 이유

여러 레인이 병행하면 origin은 계속 앞서간다. 최신화 없이 시작하면 두 가지가 깨진다:

1. **지시서 §1(현행 진단)이 낡은 코드를 근거로 삼는다.** 플래너가 "확인된 코드 사실"이라고 써놓은 게 이미 사실이 아니게 되고, **재현검증의 기준 자체가 무너진다.** 이 루틴은 §1의 정확성 위에 서 있으므로 이건 치명적이다.
2. **푸시 시점에 대량 병합 충돌.** 작업하는 동안 origin이 더 벌어져, 검증까지 끝낸 커밋을 병합하다 사고가 난다.

그래서 **착수 전(⓪)과 푸시 직전(⑥) 두 번** 최신화한다.

- **미완료 병합·더티 트리 먼저 확인.** 다른 레인이 남긴 해결 안 된 병합이 있을 수 있다. 있으면 **그것부터 정리하고** 내 작업을 시작한다 — 내 변경과 섞이면 원인 추적이 불가능해진다.
- **rebase vs merge는 프로젝트 규약을 따른다**(§10). 레포에 따라 rebase가 위험할 수 있다(예: 비ASCII 파일명 정규화, 서브모듈).

- **②의 지시서는 위임 전 커밋하지 않는다** — 구현자가 로컬 파일을 직접 읽고, ⑥에서 코드와 함께 커밋.
- 상호의존 슬라이스는 **한 쌍으로 배포**(따로 나가면 잠깐 깨짐). 지시서 헤더에 "동반 배포" 명시.

## 3. 지시서 표준 형식

파일: `docs/[지시서 폴더]/NN-핵심키워드.md` (NN = 연속 번호)

```
# 지시서 NN — 제목

> 작성: [플래너] · 날짜 · 레인/맥락
> 근거: [요구사항 출처 — 사용자 피드백/설계안 §x]
> 협업 루프: 로컬(커밋X). 디렉터 위임 → 구현 → 검증 → "커밋". SQL 유무 명시.
> 선행/동반: [의존 슬라이스]

## 0. 한 줄        — 이 슬라이스가 하는 일 1문장
## 1. 현행 진단    — 검증된 코드 사실(파일:라인). 추측 아닌 확인된 것만
## 2. DB / SQL     — 있으면 마이그레이션, 없으면 "없음"
## 3. 구현         — 파일별 변경. 정밀함이 필요한 곳은 코드블록
## 4. 회귀 가드    — 건드리면 안 되는 것, 빈/경계 상태, 비기능 요건
## 5. 검증         — 구현자 자체 체크(타입/린트/빌드 + 기능 확인 명령)
## 6. 후속(범위 밖)— 이번에 안 하는 것(다음 슬라이스 후보)
## 7. 라이브 체크리스트 — 배포 후 사람이 눈으로 볼 항목
```

원칙: **§1은 반드시 실제 코드를 열어 확인한 사실**로 채운다(그래야 구현자가 헤맬 여지가 줄고, 검증 기준이 명확).

## 4. 위임·보고 규약

- **위임은 복사용 코드블록으로.** 디렉터가 그대로 구현자에게 붙여넣는다.
- **완료 보고 타이틀 = `지시서 NN — <지시내용>`.** 어느 슬라이스 보고인지 즉시 식별. 여러 개면 각 번호 명시. 아래에 변경 파일·검증 결과.
- **커밋 메시지 규약**: `<type>: 지시서 NN <한국어 요약>` (예: `feat: 지시서 40 …`).

### 4.1 위임 블록은 짧게 — 지시서를 베끼지 않는다

**지시서에 이미 있는 내용을 위임 블록에 다시 쓰지 않는다.** 중복은 토큰 낭비이고, 둘이 어긋나면 어느 쪽이 진실인지 모호해진다. **지시서가 단일 진실**이다.

위임 블록에 담을 것은 **네 가지뿐**:
1. 지시서 **경로**
2. 시작 전 **최신화**(⓪)
3. **특히 헷갈리기 쉬운 항목 2~3개**만 짚기(예: "§1을 먼저 읽을 것 — 원인이 처음 가설과 다르다")
4. **워크플로우 한 줄**

```
지시서 NNN 구현해줘.

지시서: docs/[지시서 폴더]/NNN-....md
시작 전: git fetch && git merge origin/[기본브랜치]  (rebase 금지 여부는 §10)

§1(현행 진단)을 먼저 읽을 것 — [주의점 한 줄].
§4 회귀 가드 중 특히: [가장 깨지기 쉬운 것 1~2개].

검증은 §5. 구현 후 완료 보고 → 재현검증 통과 후 "커밋해" 트리거를 주면
그때 커밋 + 병합 + 푸시.
```

### 4.2 커밋·푸시도 구현자에게 위임한다

**검증 통과(④✅) → 디렉터의 "커밋해"(⑤) → 구현자가 커밋·병합·푸시(⑥)** 순서를 지킨다.
- 플래너가 이미 커밋해둔 경우: 구현자는 **새로 커밋하지 말고** 병합·빌드·푸시만 한다.
- 배포 위임 블록:

```
[슬라이스] 배포 부탁해. 커밋은 되어 있고(SHA), 병합·빌드·푸시만.

1. git log --oneline origin/[브랜치]..HEAD  ← 나갈 커밋 확인
2. 미완료 병합·더티 트리 있으면 먼저 정리
3. git fetch && git merge origin/[브랜치]   ← rebase 금지 여부는 §10
4. 빌드 → 통과해야만 push
5. 실패·충돌이면 푸시하지 말고 보고
6. 푸시 후 origin SHA 보고
```

## 5. 검증 원칙 (플래너)

구현자의 보고를 **그대로 믿지 않고 재현**한다:
- `grep`/파일 읽기로 **변경이 실제로 반영됐는지** 확인(추가/삭제/미사용 잔재).
- 타입체크·린트를 **독립 재실행**(보고 수치 대조).
- 요구사항 대비 **누락·초과·부작용** 점검(회귀 가드 §4 대조).
- 통과면 ✅ + 커밋 트리거 블록. 불충분하면 🔧 + 구체적 수정 지시.
- 고위험 변경은 별도 검증(스크린샷·유닛테스트·서브에이전트).

> 검증자의 확신은 검증을 건너뛸 이유가 아니다. "됐을 것"이 아니라 "됐음을 봤다".

## 6. 예외: 외부 작업 핸드오프

코드 밖 작업(DB 마이그레이션 등)이 필요하면:
- 해당 산출물(예: SQL 파일)은 **예외적으로 먼저 커밋·푸시**해 외부 작업자가 받게 한다.
- 코드는 **그 컬럼/자원이 없어도 안 깨지게(graceful)** 짠다(예: 없는 컬럼 조회 시 폴백). → 적용 순서에 자유도 확보.
- 지시서 §2에 핸드오프 대상과 적용 후 점등될 기능을 명시.

---

## 7. 기록 (git 단독 권장)

- **단일 source of truth = git의 작업 상태 문서**(예: `docs/작업계획서.md`) — 슬라이스별 상태(신호등)·설명·커밋 SHA.
- 별도 외부 툴(Notion 등) 동기화는 **선택**. 이중 관리가 부담되면 git 단독으로.
- 트리거 한 줄로 일괄 반영: 마지막 기록 이후 커밋을 모아 **묶음(슬라이스) 단위**로 상태 갱신 + 커밋·푸시. 커밋 전수 나열은 지양(노이즈).

---

## 8. 슬라이스 사이징 규칙

- **하나의 관심사**만. UI·데이터·로직이 섞이면 쪼갠다.
- 결정이 필요 없는 것(순수 정리·리팩터)을 **먼저**, 결정·의존 있는 것을 나중에.
- 외부 의존(LLM 키·신규 소싱 등)이 있으면 **규칙 기반 폴백을 먼저** 만들고, 외부가 붙으면 고도화되게 설계("없어도 동작, 붙으면 똑똑해짐").
- 큰 것은 "골격 → 내용 → 다듬기" 순으로 여러 슬라이스로.

---

## 9. 결정·질문 규약 (디렉터↔플래너)

- 구현 방향이 갈리는 **포크**는 만들기 전에 옵션을 제시해 결정받는다(추천안 + 근거).
- 시각/UX처럼 말로 애매한 것은 **목업을 만들어 비교**한 뒤 고른다.
- 이미 정해진 관습·명백한 기본값은 묻지 말고 진행하되, 택한 것을 밝힌다.

- **최신화(⓪): `git fetch origin main && git merge origin/main`**
  - ⚠️ **rebase 금지.** 한글(비ASCII) 파일명이 macOS에서 NFD로 저장돼 있어, rebase의 재체크아웃 단계에서 파일이 **스퓨리어스하게 "삭제됨"으로 뜨며 반복 실패**한다. merge는 정상 동작한다.
  - macOS 로컬은 `git config core.precomposeunicode true` 를 켜둘 것(유령 untracked 방지).
- 배포 확인: Vercel 자동 배포 → `git log --oneline origin/main -1` 로 SHA 대조
- 여러 레인(예: daily_insights)이 병행 중이라 origin이 빠르게 앞서간다 → **⓪를 건너뛰지 말 것.**
