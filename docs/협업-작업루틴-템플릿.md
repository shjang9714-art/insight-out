# 협업 작업루틴 (슬라이스 루프) — 범용 템플릿

> 어느 프로젝트에나 붙여 쓸 수 있는 표준 협업 절차. 프로젝트별로 대괄호 `[...]` 항목만 채우면 됨.
> 핵심 사상: **작게 나눠(슬라이스), 지시서로 명세하고, 구현과 검증을 분리하고, 검증 통과 후에만 커밋한다.**

---

## 0. 핵심 원칙

1. **슬라이스 단위로 일한다.** 한 번에 하나의 관심사(one concern)만. 크면 쪼갠다.
2. **명세(지시서)와 구현을 분리한다.** 계획하는 사람과 코드 치는 사람이 다르면 품질이 올라간다.
3. **구현과 검증을 분리한다.** 구현자 자신의 "됐다"를 믿지 않고, 검증자가 **코드 사실을 재현**해 확인한다.
4. **검증 통과 전엔 커밋하지 않는다.** 커밋은 "합격 도장" 이후에만.
5. **불확실하면 만들기 전에 묻는다.** 잘못된 추론보다 확인이 싸다.
6. **정직성 우선.** 되지 않은 걸 됐다고 하지 않는다. 막히면 막혔다고 보고한다.

---

## 1. 역할 (4개, 프로젝트에 맞게 매핑)

| 역할 | 하는 일 | 안 하는 일 |
|---|---|---|
| **디렉터** (사람) | 방향·우선순위 결정, 위임 전달, "커밋해" 트리거 | 세부 구현 |
| **플래너** (지시서 작성·검증) | 지시서 작성, 재현 검증(✅/🔧), 다음 스텝 제안 | git 실행 안 함 |
| **구현자** (코딩) | 구현 + 타입/린트/빌드 + 완료 보고, **커밋·푸시 전담** | 검증 통과 전 커밋 안 함 |
| **[외부 작업자]** (선택) | DB 마이그레이션·인프라 등 코드 밖 작업 | — |

> 1인 다역도 가능(사람이 디렉터, AI 하나가 플래너+구현자). 단 **구현과 검증은 논리적으로 분리**해서, 검증 단계에선 "짠 코드를 다시 사실 확인"하는 태도로 전환한다.

---

## 2. 표준 사이클 (1 슬라이스 = 1 루프)

```
① 디렉터: 무엇을 할지 지시(방향·제약)
② 플래너: 지시서 작성 → docs/[지시서 폴더]/NN-제목.md  (아직 커밋 X)
   - 필요 시 구현 전 결정용 질문(포크/모호점)을 먼저 해소
③ 구현자: 지시서대로 구현 + 타입체크/린트/빌드 + 완료 보고
   - 이 시점엔 커밋·푸시 안 함
④ 플래너: 재현 검증(코드 사실 대조) → ✅ 통과 / 🔧 수정요청
⑤ 디렉터: ✅ 확인 후 "커밋해" 트리거
⑥ 구현자: 지시서 + 코드를 한 번에 커밋·푸시
⑦ 배포/반영 확인: [배포 확인 방법]으로 최신 커밋이 실제 반영됐는지 검증
```

- **②의 지시서는 위임 전 커밋하지 않는다** — 구현자가 로컬 파일을 직접 읽고, ⑥에서 코드와 함께 커밋.
- 상호의존 슬라이스는 **한 쌍으로 배포**(따로 나가면 잠깐 깨짐). 지시서 헤더에 "동반 배포" 명시.

---

## 3. 지시서 표준 형식

파일: `docs/[지시서 폴더]/NN-핵심키워드.md` (NN = 연속 번호)

```
# 지시서 NN — 제목

> 작성: [플래너] · 날짜 · 레인/맥락
> 근거: [요구사항 출처 — 사용자 피드백/설계안 §x]
> 협업 루프: 로컬(커밋X). 디렉터 위임 → 구현 → 검증 → "커밋". SQL 유무 명시.
> 선행/동반: [의존 슬라이스]

## 0. 한 줄        — 이 슬라이스가 하는 일 1문장
## 1. 현행 진단    — 검증된 코드 사실(파일:라인). 추측 아닌 확인된 것만
## 2. DB / SQL     — 있으면 마이그레이션, 없으면 "없음"
## 3. 구현         — 파일별 변경. 정밀함이 필요한 곳은 코드블록
## 4. 회귀 가드    — 건드리면 안 되는 것, 빈/경계 상태, 비기능 요건
## 5. 검증         — 구현자 자체 체크(타입/린트/빌드 + 기능 확인 명령)
## 6. 후속(범위 밖)— 이번에 안 하는 것(다음 슬라이스 후보)
## 7. 라이브 체크리스트 — 배포 후 사람이 눈으로 볼 항목
```

원칙: **§1은 반드시 실제 코드를 열어 확인한 사실**로 채운다(그래야 구현자가 헤맬 여지가 줄고, 검증 기준이 명확).

---

## 4. 위임·보고 규약

- **위임은 복사용 코드블록으로.** 디렉터가 그대로 구현자에게 붙여넣을 수 있게, 지시서 경로 + 핵심 변경 + 제약 + 검증 + 워크플로우 한 줄을 담는다.
- **완료 보고 타이틀 = `지시서 NN — <지시내용>`.** 어느 슬라이스 보고인지 즉시 식별. 여러 개면 각 번호 명시. 아래에 변경 파일·검증 결과.
- **커밋 메시지 규약**: `<type>: 지시서 NN <한국어 요약>` (예: `feat: 지시서 40 …`).

---

## 5. 검증 원칙 (플래너)

구현자의 보고를 **그대로 믿지 않고 재현**한다:
- `grep`/파일 읽기로 **변경이 실제로 반영됐는지** 확인(추가/삭제/미사용 잔재).
- 타입체크·린트를 **독립 재실행**(보고 수치 대조).
- 요구사항 대비 **누락·초과·부작용** 점검(회귀 가드 §4 대조).
- 통과면 ✅ + 커밋 트리거 블록. 불충분하면 🔧 + 구체적 수정 지시.
- 고위험 변경은 별도 검증(스크린샷·유닛테스트·서브에이전트).

> 검증자의 확신은 검증을 건너뛸 이유가 아니다. "됐을 것"이 아니라 "됐음을 봤다".

---

## 6. 예외: 외부 작업 핸드오프

코드 밖 작업(DB 마이그레이션 등)이 필요하면:
- 해당 산출물(예: SQL 파일)은 **예외적으로 먼저 커밋·푸시**해 외부 작업자가 받게 한다.
- 코드는 **그 컬럼/자원이 없어도 안 깨지게(graceful)** 짠다(예: 없는 컬럼 조회 시 폴백). → 적용 순서에 자유도 확보.
- 지시서 §2에 핸드오프 대상과 적용 후 점등될 기능을 명시.

---

## 7. 기록 (git 단독 권장)

- **단일 source of truth = git의 작업 상태 문서**(예: `docs/작업계획서.md`) — 슬라이스별 상태(신호등)·설명·커밋 SHA.
- 별도 외부 툴(Notion 등) 동기화는 **선택**. 이중 관리가 부담되면 git 단독으로.
- 트리거 한 줄로 일괄 반영: 마지막 기록 이후 커밋을 모아 **묶음(슬라이스) 단위**로 상태 갱신 + 커밋·푸시. 커밋 전수 나열은 지양(노이즈).

---

## 8. 슬라이스 사이징 규칙

- **하나의 관심사**만. UI·데이터·로직이 섞이면 쪼갠다.
- 결정이 필요 없는 것(순수 정리·리팩터)을 **먼저**, 결정·의존 있는 것을 나중에.
- 외부 의존(LLM 키·신규 소싱 등)이 있으면 **규칙 기반 폴백을 먼저** 만들고, 외부가 붙으면 고도화되게 설계("없어도 동작, 붙으면 똑똑해짐").
- 큰 것은 "골격 → 내용 → 다듬기" 순으로 여러 슬라이스로.

---

## 9. 결정·질문 규약 (디렉터↔플래너)

- 구현 방향이 갈리는 **포크**는 만들기 전에 옵션을 제시해 결정받는다(추천안 + 근거).
- 시각/UX처럼 말로 애매한 것은 **목업을 만들어 비교**한 뒤 고른다.
- 이미 정해진 관습·명백한 기본값은 묻지 말고 진행하되, 택한 것을 밝힌다.

---
