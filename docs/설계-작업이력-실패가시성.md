## 0. 문제 (한 줄)

이 시스템의 지배적 실패 양상은 **조용한 실패**다. 잡이 실패해도 아무 기록이 남지 않고, 특히 **크론 10개는 아무도 보고 있지 않다.**

## 1. 현행 진단 (검증된 사실)

### 1.1 실행 기록이 있는 것
- `crawl_logs` — **크롤 전용**. `crawl-now`·`source-status`만 사용.
- `llm_usage` / `translation_usage` / `tts_usage` — **사용량(비용) 집계**이지 실행 이력이 아니다. 실패·건수·소요시간을 못 본다.

### 1.2 실행 기록이 **없는** 것 — 전부
**크론 10개** (`vercel.json`):
| 잡 | 스케줄(UTC) |
|---|---|
| `/api/cron/crawl` | `0 20 * * *` |
| `/api/cron/briefing` | `0 21 * * *` |
| `/api/cron/newsletter` | `0 23 * * *` |
| `/api/cron/body-backfill` | `0 19 * * *` |
| `/api/cron/signals-backfill` | `0 18 * * *` |
| `/api/cron/ai-refresh` | `0 21 * * *` |

| `/api/cron/competitor-weekly` | `0 * * * *` (매시, 284 게이트) |

**어드민 수동 잡 13개**: `body-backfill` `canonical-backfill` `cluster-backfill` `lgu-impact` `pdf-cover-backfill` `sentiment` `signals-backfill` `thumbnail-backfill` `translate-backfill` `youtube-summary` `youtube-tagging` `youtube-transcript` `youtube(purge)`

### 1.3 왜 지금 이게 문제인가 (이번 세션에서 실제로 겪은 것)
- 261 SQL 실패 → 수희가 에러를 볼 때까지 아무도 몰랐다.
- 246 SQL이 42703으로 실패 → 뒤늦게 발견.
- `ai_report_sources` 이슈 행이 **CHECK 위반으로 계속 조용히 실패**하고 있었다.
- `content_views` 기록 API를 **아무도 호출하지 않아 데이터가 0건**인데, 감사 문서는 "already records data"라고 적혀 있었다.

코드베이스 전반이 **graceful degradation**(실패해도 안 깨짐) 원칙으로 짜여 있다. 이건 옳은 설계지만, 대가는 **"graceful = 실패가 안 보임"**이다. 그 대가를 상쇄할 장치가 지금 없다.

## 2. 핵심 판단

### 2.1 우선순위 — 크론이 먼저다
- **수동 잡**은 관리자가 버튼을 누르고 결과를 **즉시 화면에서 본다**(processed/filled/skipped). 이미 절반은 보인다.
- **크론 10개는 아무도 안 본다.** 새벽에 실패하면 Vercel 로그를 뒤져야만 안다.
→ **크론 계측을 먼저 한다.** 수동 잡은 후속.

### 2.2 테이블명은 `ai_jobs`가 아니라 **`job_runs`**
감사 문서는 `ai_jobs`를 제안했지만, 지시서 287이 정리하듯 **이 잡들의 절반은 AI가 아니다**(본문 수집·URL 정규화·썸네일·클러스터링·링크 헬스). `ai_jobs`로 만들면 같은 오분류를 데이터 모델에 박아 넣는 셈이다.

### 2.3 "성공"만 기록하면 의미가 없다
가장 중요한 신호 셋:
1. **실패** (`status='failed'` + error)
2. **안 돌았음** (마지막 실행이 스케줄보다 오래됨 → 크론 자체가 죽음)
3. **돌았는데 아무것도 못 함** (`filled=0`이 계속됨 → 조용한 무성과. 261·276이 딱 이 케이스였다)

3번을 놓치면 이 작업의 절반은 헛것이다.

## 3. 데이터 모델 (SQL 초안)

```sql
create table public.job_runs (
  id          uuid primary key default gen_random_uuid(),
  job_key     text not null,              -- 'cron:competitor-weekly', 'admin:thumbnail-backfill'
  mode        text,                       -- 'fresh'|'retry' 등(없으면 null)
  trigger     text not null               -- 'cron' | 'admin'
                check (trigger in ('cron','admin')),
  started_by  uuid references public.users (id) on delete set null,  -- admin이면 실행자, cron이면 null
  status      text not null default 'running'
                check (status in ('running','succeeded','failed','skipped')),
  started_at  timestamptz not null default now(),
  finished_at timestamptz,
  duration_ms integer,
  processed   integer,                    -- 공통 카운트(백필류)
  filled      integer,
  skipped     integer,
  remaining   integer,
  error       text,
  meta        jsonb not null default '{}' -- 잡별 추가 정보(주차, 대상기간 등)
);

create index job_runs_key_started_idx on public.job_runs (job_key, started_at desc);
create index job_runs_failed_idx on public.job_runs (started_at desc) where status = 'failed';
```

- **`skipped` 상태**: 284 크론이 `not_scheduled`로 빠지는 것처럼, "안 돌 이유가 있어 안 돎"은 실패가 아니다. 구분해야 노이즈가 안 생긴다.
- **보존**: 무한 증가 방지 — 90일 초과 행 정리(크론 또는 유지보수 버튼). 설계 단계에서 명시할 것.

## 4. 계측 방식 — 래퍼 하나로

23개 잡을 하나씩 고치지 말고, **공통 래퍼**로 감싼다.

```ts
// src/lib/jobs/run-job.ts
export async function runJob<T extends JobCounts>(
  admin: SupabaseClient,
  ctx: { key: string; trigger: 'cron'|'admin'; mode?: string; startedBy?: string },
  fn: () => Promise<T>,
): Promise<T>
```
- 시작 시 `status='running'` 행 insert → `fn()` 실행 → 결과의 카운트로 update(`succeeded`), 예외면 `failed` + error.
- ⚠️ **계측 실패가 잡을 깨뜨리면 안 된다.** insert/update 실패는 로깅만 하고 `fn()`의 결과·예외를 그대로 전파한다. (이 원칙을 어기면 가시성 도구가 새로운 장애 원인이 된다.)
- `job_runs` 테이블 미적용(42P01)에서도 잡은 정상 동작해야 한다(graceful).

## 5. 화면

### 5.1 작업 이력 (`/admin/job-runs` 또는 "일괄 작업 관리" 내 탭)
- 목록: 잡·트리거·상태·시작시각·소요·처리/설정/스킵·오류.
- 필터: 상태(실패만), 잡, 기간, 트리거.
- **잡별 최근 실행 요약**(마지막 성공/실패, 연속 실패 횟수).

### 5.2 실패 가시성 (**이게 본체다**)
- **운영 대시보드(`/admin`)에 "최근 실패한 작업" 카드** — 24시간 내 `failed`가 있으면 눈에 띄게. 없으면 조용히.
- **"안 돈 크론" 감지**: 각 크론의 기대 주기 대비 마지막 성공이 오래됐으면 경고. (스케줄은 `vercel.json`에 있으니 잡별 기대주기를 상수로 둔다.)
- **"돌았는데 성과 0" 감지**: 최근 N회 연속 `filled=0`이면 주의 표시.

## 6. 슬라이스 분해

| | 내용 | 크기 | SQL |
|---|---|---|---|
| **C-1** | `job_runs` 테이블 + `runJob` 래퍼 + **크론 10개 계측** + 이력 화면 + 대시보드 실패 카드 | 중 | **필요** |
| **C-2** | 어드민 수동 잡 13개 계측 | 소 | 없음(C-1 재사용) |
| **C-3** | "안 돈 크론"·"성과 0" 감지 + 보존 정리(90일) | 소 | 없음 |

**C-1을 먼저.** 크론이 안 보이는 게 문제의 핵심이고, C-2는 래퍼가 생기면 기계적으로 붙는다.
