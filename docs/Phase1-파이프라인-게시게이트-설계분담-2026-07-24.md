# Phase 1 — 파이프라인 게시-게이트 전환 : 설계·분담 (2026-07-24)

> 목표: 소스 편향·본문 누락 해소. 짧은 RSS 기사를 **적재 전 reject하지 말고 stub으로 저장 → 보강·품질 통과분만 공개**.
> 멀티 오너: **[수희]** 스키마·Supabase 워커 · **[Sonnet]** ingest flip · **[Opus]** 이 설계 + 지시서/핸드오프 분리.

---

## 0. 핵심 발견 (설계의 근거)
- `content_status` enum = **`pending` / `published` / `rejected`** (이미 존재, 추가 불필요).
- **게시 게이트 메커니즘이 이미 있다**: `enrichRecentContents`(orchestrator.ts)가 보강으로 풀본문 확보 후 **`status: pending → published` 승격**(L77). 검색 소스(isSearchSourced) 기사는 이 흐름(stub→보강→게시)으로 이미 돈다.
- **문제 지점 하나**: `processCrawlItem` **L437** — `!isSearchSourced && bodyLength < minBodyLength(250)` → **적재 전 reject**. 정규 소스의 짧은 RSS 기사가 pending→publish 흐름에 **아예 못 들어간다.** → RSS에 전문 싣는 매체(동아일보 등)만 생존.
- 부차: `schedule.ts` `selectCrawlSources` — `crawl_interval_minutes` NULL 소스 **영구 제외**.

→ 즉 **큰 재작성이 아니라, 적재 전 reject를 걷어 정규 소스도 stub→보강→게시 흐름에 태우는 게 핵심.**

---

## 1. 설계 원칙
**본문 보강 = 저장 게이트가 아니라 게시 게이트.**
신규 기사는 **stub(pending)으로 저장** → 보강 큐 → 보강+품질 통과 → **published 승격**. "짧다"는 이유로 URL을 버리지 않는다. (진짜 쓰레기 — 광고·제외그룹·완전중복 — 는 계속 reject.)

---

## 2. 분담

### A. 스키마·데이터 [수희]
- `content_status`에 pending 있음 → **enum 변경 없음.**
- **`discovered_at`** 신규 컬럼: 시스템 최초 발견 시각(NOT NULL, default now). `published_at`은 이미 nullable(원문 발행일 없어도 버리지 않음).
- **`crawl_interval_minutes` NULL 보정**: 활성 소스 중 NULL/0인 것에 기본 주기(예: 720분) 채우기. `disabled`(또는 `is_active=false`)만 명시 제외로.
- **보강 큐 식별은 신규 컬럼 최소화** — 기존 `status='pending' AND body_fetched_at IS NULL`로 큐를 잡을 수 있으므로 `enrichment_required` 별도 플래그는 지양(기존 메커니즘 재사용).

### B. Ingest flip [Sonnet] (지시서 예정)
- `orchestrator.ts` **L437 reject 변경**: `!isSearchSourced && short body` → **reject 대신 `status='pending'`으로 insert**(URL·제목·스니펫 stub 보존). **광고·제외그룹·완전중복 reject는 유지.**
- 신규 insert status 규칙 확정: 본문 충분 → 기존대로, **짧음 → pending**(보강 대기). ⚠️ 착수 시 현재 insert status 지정 코드 정독 후 명시.
- `schedule.ts`: `crawl_interval_minutes` NULL → 영구 제외 대신 **기본 주기 적용**, `disabled/is_active=false`만 제외.
- `discovered_at` 세팅.
- **`enrichRecentContents`의 pending→published 승격(L77) 유지·활용** — flip이 만든 pending을 이게 게시한다.

### C. Supabase 보강 워커 [수희] (B-2 실행 모델)
- 현재 보강: 크롤 tail(100/run) + body-backfill 크론(Vercel Hobby, **하루 1회**). flip 후 pending 적체 → 하루1회론 게시 지연.
- **Supabase pg_cron + Edge Function**: `status='pending' AND body_fetched_at IS NULL` 큐를 **자주(예: 5~15분)** 드레인 → 풀본문 추출 → 품질 통과 시 **published 승격**, 실패 재시도.
- 기존 enrich 로직(fetch-body·품질 검사)을 Edge Function으로 이식하거나, Vercel enrich 엔드포인트를 워커가 호출(둘 중 수희 판단).

---

## 3. 🔴 착지 순서 (중요)
1. **A 스키마(`discovered_at`·interval 보정)** 먼저.
2. **C 보강 워커** 먼저 또는 B와 동시 — pending을 자주 게시로 승격할 준비가 서 있어야.
3. **B ingest flip** — 워커(C)가 돌고 있으니 pending이 빠르게 published로 따라와 **노출 감소 최소화.**

> ⚠️ **B만 먼저 하면 안 됨.** flip으로 pending이 쌓이는데 보강이 하루1회면 잠깐 노출이 준다. C(워커)가 선행/동시여야 한다.

---

## 4. 리스크·가드
- **적체**: flip 직후 pending 급증 → C 처리량이 관건(위 순서).
- **품질 게이트**: 보강 후에도 본문 부실·유료벽·404는 published 승격 **보류**(pending 유지 또는 rejected). 품질 기준을 B/C에서 명시.
- **스팸 유입**: 짧은 stub 허용으로 광고·비기사 URL이 들어올 위험 → 최소 **URL 유효성 + trust_tier** 가드 유지(광고 reject는 그대로).
- **회귀 금지**: 검색 소스·기존 published 흐름·서빙(status='published' 필터) 무변경.
