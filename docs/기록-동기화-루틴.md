- 진행 현황 메모에 핵심 변경 1~2줄 추가, 필요 시 백로그 갱신.
- 끝의 `*마지막 sync:*` 를 오늘 날짜로.

**B. Notion 작업계획서 페이지 신호등 ← git 일치**

**F. git 변경 커밋·푸시 (필수 — 빠뜨리면 git↔Notion 어긋남)**

- `.git/index.lock` 있으면 `rm -f .git/index.lock` 후 재시도.

## 6. (지시서 189) 작업 현황 단일 소스 = DB — 신규 흐름

> 189부터 **작업(work) 항목의 상태는 어드민 "운영 게시판"(`ops_requests`, post_type=`work`) 이 단일 소스**다. `docs/작업계획서.md` 는 그 DB 를 **export 한 스냅샷**이며, 더 이상 신호등을 손으로 편집하지 않는다.

**새 흐름**:
1. 작업 상태는 **DB 에서 갱신** — 어드민 `/admin/requests`(작업 세그먼트) 화면에서 직접, 또는 188 MCP 툴(`ops_request_update` 등)로 Claude 코딩 중 바로 반영.
2. 기록 동기화 시(이 루틴 실행 시):
   - `GET /api/admin/worklog/export`(배포 앱, admin 인증) 를 호출해 최신 마크다운 스냅샷을 받는다.
   - 받은 마크다운으로 **`docs/작업계획서.md` 를 덮어쓰고 commit + push**(Sonnet, §2-F 와 동일 원칙 — git 은 Sonnet 전담).
   - 즉 위 §1~§4(Notion 동기화)는 그대로 유지하되, **§2-A(git 작업계획서.md 최신화)는 "손 편집"이 아니라 "export 결과로 덮어쓰기"** 로 대체된다.
3. `docs/작업계획서.md` 의 상단 "PRD v2.1 기반" 서문·진행 현황 메모(자유 서술)는 export 형식에 없으므로, 필요하면 export 마크다운 앞뒤에 기존 서문/메모 블록을 유지한 채 phase 섹션만 교체하는 방식으로 병합(Sonnet 판단).
4. 배포 앱은 파일을 쓰지 않는다 — export 는 **생성·반환만**. 실제 파일 갱신·커밋·푸시는 항상 로컬(Sonnet)에서 수행.
5. 기존 작업계획서의 `#P` 항목(git 수기 관리분)을 DB `work` 항목으로 옮기는 백필은 후속(선택) — 당장은 신규 작업부터 DB 에 기록.

### 7.2 무엇을 적나

예: *"500·사용량 0"이라는 같은 증상 뒤에 원인이 3개(프리뷰 모델 오버라이드 / 무료티어 429 / integer 컬럼에 소수 write)였고, 라우트가 사유를 500으로 덮어써 로그를 보기 전엔 분리되지 않았다.*
