# 지시서 351-B — 키워드 통합 상세 페이지 + 온디맨드 시계열

> 대상: 구현 에이전트 · 상위설계: `docs/키워드분석-재설계-사전분석.md` · 선행: 351-A
> ⚠️ 읽을 것: `src/app/dashboard/entities/[id]/page.tsx`(상세 골격 참고) · `src/app/dashboard/topics/[topic]/page.tsx`(matched_keywords 조회 패턴) · `src/components/entities/EntityEventTimeline.tsx` · `src/components/issues/IssueSentimentTrend.tsx`(recharts 재사용) · `supabase/schema.sql`(contents_matched_keywords_idx GIN·collected_at 인덱스) · `AGENTS.md`
> **신규 SQL 없음.** 온디맨드 집계(David 결정). 상세는 통합 `keywords/[name]`(David 결정).

## 배경
351-A로 메인(랭킹·색상·필터)은 됐으나, 키워드를 클릭해 들어갈 **상세가 없다**. `topics/[topic]`은 기사 리스트뿐이고, `entities/[id]`는 엔티티만 커버. 모든 키워드가 같은 상세를 갖도록 통합 페이지를 만든다.

## 설계 결정
1. **온디맨드 시계열** — 캐시 테이블·크론 없이, 상세 조회 시 `contents.matched_keywords` GIN 인덱스로 최근 30일 일별 카운트를 그 자리에서 집계. 느려지면 나중에 캐시로 승격(인터페이스 유지).
2. **통합 `keywords/[name]`** — 엔티티든 비엔티티든 동일 상세. 해당 이름이 엔티티면 기업 정보(연관 기업·관계지도 링크)를 **추가로** 붙인다.
3. **정보 순서 = 결론 먼저**: 스냅 → 핵심지표 → 추이차트 → (351-C가 채울)상승요인 → 관련키워드·기업 → 사건 타임라인 → 원문.

## 작업

### A. 온디맨드 집계 — `src/lib/keywords/detail.ts`(신규, server-only)
- `getKeywordDailyCounts(name, days=30)` → `{ date, count }[]`. `contents` 를 `.contains('matched_keywords', [name])` + `collected_at >= since` 로 조회 후 KST 일자 버킷팅. limit 넉넉히(예: 2000) + 초과 시 절단 표시.
- `getKeywordSnapshot(name)` → 핵심지표: `관련 문서(고유 content 수)` · `총 언급(문서×matched 빈도 합, 없으면 문서 수)` · `7일 증감%`(351-A와 동일 공식) · `연관 기업 수` · `신규 사건 수`.
- `getKeywordRelated(name)` → co-occurrence: 같은 콘텐츠에 함께 등장한 `matched_keywords`·엔티티 빈도 상위. 유형(tag-buckets)별로 그룹핑.
- 엔티티 매칭: `entities` 에서 canonical_name/alias 일치 시 `entityId` 반환(있으면 관계지도·기업 링크용).

### B. 페이지 — `src/app/dashboard/keywords/[name]/page.tsx`(신규, 서버)
- URL: `/dashboard/keywords/{encodeURIComponent(name)}`. 351-A 랭킹·버블 클릭이 이 경로로 링크(엔티티 여부 무관).
- 레이아웃(349 지면 톤 재사용 가능):
  1. **스냅** — 브레드크럼 `키워드 분석 / {name}` + 유형칩 + "최근 7일 {±%} · 갱신 N시간 전" 한 줄.
  2. **핵심지표 카드 5개** — 관련 문서 / 총 언급 / 7일 증감 / 연관 기업 / 신규 사건. `ⓘ` 로 집계 방식.
  3. **관심도 추이 차트** — recharts LineChart, 최근 30일. `IssueSentimentTrend` 패턴 재사용. (사건 마커는 351-C에서 추가 — 이번엔 라인만.)
  4. **상승 요인** — 자리(placeholder 섹션)만 두고 "분석 준비 중"; 351-C가 채운다.
  5. **2열 하단** — 좌: 사건 타임라인(엔티티면 `EntityEventTimeline`, 아니면 `topics/[topic]` 기사 타임라인 재사용) / 우: 관련 키워드(유형별 그룹, 4개+전체보기) · 연관 기업 · `관계지도에서 보기`(엔티티일 때만). 우측 패널 `sticky`.
- 데이터 0건이면 graceful 안내.

### C. 링크 정리
- 351-A 랭킹·기존 keyword 카드의 링크 대상을 **전부 `keywords/[name]`** 로 통일(엔티티는 상세 안에서 기업 링크 제공). 기존 `entities/{id}?view=keyword`·`topics/{name}` 직링크는 남겨두되 신규 진입은 통합 경로로.

## 회귀 / 주의
- **온디맨드 성능**: `.contains(matched_keywords)` 는 GIN 인덱스 사용. days·limit 상한 필수. 상세 1회 조회가 무거운 풀스캔이 되지 않게.
- 한글 키워드 URL 인코딩(`encodeURIComponent`) 양방향 확인.
- recharts는 클라이언트 컴포넌트로 분리(차트만).
- prefetch={false}, 서버 컴포넌트 기본, 색상 토큰(하드룰 9).
- 검증: `tsc` · ESLint · `check-prefetch` · `npm run build` · 육안(엔티티 키워드·비엔티티 키워드 각각 상세).

## 후속 (351-C)
상승 요인 3~5개 묶음 — 경쟁사 브리핑 3패스(사실추출→요인→검증) + 프롬프트 콘솔 재사용. 급상승 키워드만 온디맨드. B의 4번 섹션·추이 사건 마커를 채운다.
