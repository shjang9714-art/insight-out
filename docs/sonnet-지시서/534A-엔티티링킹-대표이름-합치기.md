# 지시서 534-A — 엔티티 링킹에 대표 이름 합치기

> 플래너(Opus) · 2026-08-21 · 기준 `origin/main = f20694f` · 브랜치 `agent/534a-entity-canonical-link`
> 근거: 프로젝트 문서 `진단-엔티티매칭-2026-08-21`. **DDL·SQL 없음.**
> 소급 재매칭 백필은 **534-B** 로 분리한다.

## 0. 실측 사실 (재조사 금지)

- `content_entities` 에 대량으로 쓰는 곳은 **크롤러뿐**이다(멀티라인 grep 전수 확인).
  나머지 writer 4곳은 company-docs 전용(`source='dart'`, 전체 9행).
- 링킹의 유일한 키는 `entity_aliases` 다. `aliasMap` 은
  `orchestrator.ts:1503` · `contents/[id]/extract` · `youtube-tagging-backfill.ts`
  **세 곳 모두 `entity_aliases` 만 읽고 `canonical_name` 은 안 읽는다.**
  이 코드는 지시서 99 이후 바뀐 적이 없다.
- 데이터: `entities` **114개** / `entity_aliases` **6행 → 커버 3개** /
  **111개 엔티티는 어떤 경로로도 새 링크를 못 받는다.**
- 링크 생성이 2026-08-17 에 붕괴했다: 08-16 39 entities/1,079 links →
  08-17 이후 **2~4 entities/일**. 별칭 가진 3개만 남은 것과 정확히 일치한다.
- **처방이 싼 이유**: `keyword_groups.include_patterns` distinct 229개 중에
  **entities 의 canonical_name 114개가 전부(100%) 정확히 존재한다.**
  `aliasMap` 에 canonical_name 을 넣기만 하면 114개가 즉시 링크 가능해진다.
- `EntityManager.tsx` 는 대표 이름 별칭을 **:452 자동 삽입 / :519 재등록 차단 / :541 삭제는 경고만** 이다.
  한 번 지우면 화면으로 복구할 수 없는 **편도 문**이다.

## 작업

### 1) `aliasMap` 을 대표 이름까지 포함해 만든다 — 공용 헬퍼로

세 곳이 같은 맵을 각자 만들고 있다. **한 곳에서만 만들게 한다** —
이 코드베이스에서 판정 기준이 두 벌이면 반드시 갈라진다(530 사례).

`src/lib/entities/alias-map.ts` (신규, `server-only`):

```ts
/** lower(name) → entity_id. canonical_name 과 entity_aliases 를 합친다. */
export async function loadEntityAliasMap(admin: SupabaseClient): Promise<Map<string, string>>
```

- `entities(id, canonical_name)` 와 `entity_aliases(alias, entity_id)` 를 둘 다 읽어 합친다.
- **양쪽 모두 `.limit()` 을 명시**한다(PostgREST 기본 1000행).
  현재 114 / 6 행이지만 상한 없는 select 는 이 코드베이스에서 11회 사고 났다.
- 충돌 시 우선순위: **`entity_aliases` 가 이긴다.** 사람이 명시적으로 등록한 매핑이
  자동 생성된 대표 이름보다 의도가 강하다. (같은 문자열이 다른 엔티티의 별칭으로
  등록돼 있으면 그쪽을 따른다.)
- 조회 실패는 지금처럼 **빈 맵으로 격리**한다(크롤 무중단). 다만 `console.warn` 문구에
  "링킹 skip" 을 남겨 조용히 0건이 되지 않게 한다.

호출부 세 곳을 이 헬퍼로 교체한다. **로직을 각자 복붙하지 말 것.**

### 2) 대표 이름 별칭이라는 개념을 없앤다

1)로 canonical_name 이 코드에서 합쳐지면 `entity_aliases` 에 대표 이름 행을 둘 이유가 사라진다.
편도 문도 같이 없앤다.

- `EntityManager.tsx:452` — 엔티티 신규 생성 시 **canonical alias 자동 삽입을 제거**한다.
- `EntityManager.tsx:519` — "대표 이름과 동일한 값은 동의어로 등록할 수 없습니다" 차단은 **유지**한다
  (이제 의미 없는 중복이므로 막는 게 맞다). 다만 문구를 **"대표 이름은 자동으로 매칭되므로
  따로 등록할 필요가 없습니다"** 로 바꿔, 사용자가 "그럼 대표 이름은 매칭 안 되나?"라고
  오해하지 않게 한다.
- `EntityManager.tsx:541` — 대표 이름과 같은 별칭 삭제 시의 경고 문구
  ("삭제하면 검색 매핑이 끊어질 수 있습니다")는 **이제 사실이 아니다.** 제거하거나
  일반 삭제 확인으로 바꾼다.
- ⚠️ **기존 6행은 그대로 둔다.** 삭제하지 말 것 — 1)의 우선순위 규칙상 무해하고,
  데이터를 지우는 건 되돌릴 수 없다.

### 3) 링킹 결과를 보이게 한다

지금은 링킹이 0건이 돼도 아무 데도 안 뜬다. 그래서 8월 17일 붕괴를 나흘간 아무도 몰랐다.

- `runCrawl` 이 반환하는 `CrawlSummary` 에 **`entityLinks: { attempted, linked, aliasMapSize }`** 를 추가한다.
  `attempted` 는 링킹을 시도한 콘텐츠 수, `linked` 는 실제로 1건 이상 연결된 콘텐츠 수.
- ⚠️ **`aliasMapSize` 가 이 지시서에서 가장 중요한 필드다.** 이게 갑자기 줄면 사전이 비었다는 뜻이고,
  그게 이번 사고의 정체다. `job_runs.meta` 에 남으면 다음에는 하루 만에 잡을 수 있다.
- 어드민 수집 현황(`SearchProvidersPanel`)에 한 줄로 노출한다:
  `엔티티 링킹 N/M건 · 사전 K개`. 구버전 meta(필드 없음)에서는 이 줄을 숨긴다.
