## 1. 실측 사실 — 재조사 금지

### 1-1. 버그

```ts

  .eq('entity_id', selectedNodeId)
  .limit(8)                                    // ← .order() 가 없다
  .then(({ data }) => {
    const items = (...)
      .sort((a, b) => b.collected_at.localeCompare(a.collected_at))  // ← 받은 8건만 정렬
```

**DB 가 임의의 8건(사실상 삽입 순서 = 오래된 것)을 주고, 그 8건 안에서만 최신순 정렬한다.**

### 1-2. 실측 확증 (2026-08-22, 엔티티 `AI` · `content_entities` 링크 17,432건)

| | 결과 |
|---|---|
| **현재 코드가 받는 8건** | **2026-06-15 ~ 07-11** |
| **최신순 8건** | **2026-08-20** |

**두 달 차이다.** David 가 보고한 "원 클릭시 기사가 최신화가 안된듯"의 직접 원인이다.

### 1-3. 같은 쿼리의 곁다리 결함 2건

- **`contents.deleted_at IS NULL` 필터가 없다** → 삭제된 기사가 노출될 수 있다.
- **`contents.status = 'published'` 필터가 없다** → `pending`(검토 대기) 기사가 노출될 수 있다.
  그래프 엣지를 만드는 `entity_neighbors` RPC 는 `status='published'` 만 세므로,
  **선은 없는데 기사는 뜨는 불일치**가 생긴다. (참고: `contents.status='pending'` 은 3,569건)

### 1-4. 이 수정만으로는 최근 기사가 다 나오지 않는다

엔티티 링킹이 **2026-08-17 부터 끊겨 있다**(링크율 84.9% → 11~18%).
08-17 이후 기사에는 링크 자체가 없어서 정렬을 고쳐도 안 나온다.
**534-B 백필이 끝나야 완전해진다.** 이 지시서 범위는 아니다.

### 1-5. 🔴 PostgREST 임베드 정렬은 실패했다 — RPC 로 간다

1차 시도에서 `.order('collected_at', { referencedTable: 'contents' })` 를 썼으나
**정렬이 조용히 무시됐다.** 필터(`contents.status`·`deleted_at`)는 먹었는데
정렬만 안 먹어 **여전히 2026-06-15~07-11 기사 8건**이 나왔다(2026-08-22 21:29 재시도 확인).

⇒ **이 관용구는 쓰지 않는다. 전용 RPC 로 내린다.**

### 1-6. 성능도 실측했다 — RPC 는 `SECURITY DEFINER` 여야 한다

같은 조회를 조건별로 쟀다.

| 방식 | `AI`(링크 18,183) | `지능형 관제`(링크 1) |
|---|---|---|
| `authenticated` + RLS, 엔티티 주도 조인 | **2,982 ms** | — |
| `authenticated` + RLS, `EXISTS` 재작성 | 364 ms | — |
| **RLS 없음(= `SECURITY DEFINER`)** | **1.3 ms** | **125 ms** |

RLS 정책이 행마다 `is_admin()` 을 호출해 18,183번 돈다. `SECURITY DEFINER` 로 RLS 를
걷어내면 플래너가 `contents_alive_collected_idx` 를 최신순으로 훑다가 8건에서 멈추는
판을 고른다 — **46행만 읽는다.**

**노출 위험 없음**: 함수가 `status='published' AND deleted_at IS NULL` 로 스스로 거르고,
`EXECUTE` 를 `authenticated` 에만 준다(`anon` 제외). 즉 지금 RLS 가 허용하는 범위와 같다.

## 2. 선행 SQL — David 실행 (`관계지도-관련기사-RPC-2026-08-22.sql`)

```sql
CREATE OR REPLACE FUNCTION public.entity_recent_contents(
  p_entity_id uuid,
  p_limit     integer DEFAULT 8
)
RETURNS TABLE(id uuid, title text, collected_at timestamptz)
LANGUAGE sql
STABLE
SECURITY DEFINER
SET search_path TO 'public', 'pg_temp'
AS $$
  SELECT c.id, c.title, c.collected_at
  FROM public.content_entities ce
  JOIN public.contents c ON c.id = ce.content_id
  WHERE ce.entity_id = p_entity_id
    AND c.status = 'published'
    AND c.deleted_at IS NULL
  ORDER BY c.collected_at DESC
  LIMIT least(greatest(p_limit, 1), 50)
$$;

REVOKE EXECUTE ON FUNCTION public.entity_recent_contents(uuid, integer) FROM PUBLIC, anon;
GRANT  EXECUTE ON FUNCTION public.entity_recent_contents(uuid, integer) TO authenticated;
```

## 3. 작업

`src/components/entities/KnowledgeGraph.tsx:845-853` 의 조회를 **RPC 호출로 바꾼다.**

```ts
supabase.rpc('entity_recent_contents', { p_entity_id: selectedNodeId, p_limit: 8 })
```

- 반환 형태가 `{ id, title, collected_at }[]` 로 **평평해진다.**
  기존의 `content_entities` → `contents` 중첩 매핑(`r.contents`)은 없앤다.
- **클라이언트 `.sort()` 는 남겨 둔다** — DB 정렬이 정본이고 이건 방어용이다.
- 🔴 **`error` 를 반드시 받아서 `console.error` 로 남긴다.**
  현재 코드는 `.then(({ data }) => ...)` 로 `error` 를 아예 안 본다.
  실패를 조용히 빈 목록으로 만들지 말 것 — 지금 버그가 그렇게 숨어 있었다.
- `nodeContentCacheRef` 캐시 구조는 그대로 둔다.

- ❌ **그래프/목록 탭을 건드리지 않는다.** 544-B + David 결정 대기 중이다.
- ❌ **범례·안내글을 건드리지 않는다.** 544-B 다.
- ❌ `p_limit` 을 8에서 바꾸지 않는다. 개수 조정은 544-B 에서 한다.
- ❌ **RPC 를 수정하지 않는다.** David 가 실행한다 — 호출만 한다.
- ❌ **PostgREST 임베드 정렬(`referencedTable`)을 다시 시도하지 않는다**(§1-5).
- ❌ `nodeContentCacheRef` 캐시 구조를 바꾸지 않는다.
- ❌ **에러를 조용히 삼키지 않는다.** 쿼리 실패 시 `console.error` 를 남긴다.
  현재 코드는 `.then(({ data }) => ...)` 로 `error` 를 아예 안 본다 — **`error` 도 받아서 로깅한다.**
