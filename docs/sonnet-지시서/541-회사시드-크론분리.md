## 0. 실측 — GDELT 는 원인이 아니었다

539 는 설계대로 작동했다. 그런데 목표는 달성되지 않았다.

```
providerErrors.gdelt = "시도 2개 / 실패 2개 / 서킷으로 건너뜀 9개 — 첫 오류: timeout"
duration_ms 243,600   (08-19: 265,388)
truncatedPhases ["keyword_search","company_seed"]
companySeedsProcessed 0 / 33     ← 6일 연속 0
```

|---|---|---|---|
| 네이버 | 755 | 882 | |
| Google 키워드 | 146 | 216 | |
| **아이템 합계** | 901 | **1,098** | **+21.9%** |

**GDELT 에서 회수한 128초가 전부 아이템 처리로 흡수됐다.** GDELT 카운터가 시드 11개
(시도 2 + 건너뜀 9)에서 멈춘 것으로 보아 키워드 단계는 시드 14개 중 11개쯤에서
`CRAWL_SOFT_DEADLINE_MS = 240_000` 에 걸린다.

회사 블록은 `COMPANY_SEARCH_BUDGET_MS = 20_000` 을 받지만 **진입 시점에 이미 데드라인이 지나 있다.**
같은 크론 안에 두는 한 회사 시드는 영원히 0이다. 예산을 나누는 걸로는 안 되고, **크론을 나눠야 한다.**

## 작업

### 1) `phase` 에 `'companies'` 추가

- `CrawlPhase` 에 `'companies'` 를 넣는다.
- `runCrawl` 분기 정리 — 지금 조건이 `phase !== 'sources'` 로 되어 있어 새 phase 가
  키워드 블록까지 타게 된다. **각 블록이 어느 phase 에서 도는지를 명시적으로 바꾼다.**

| 블록 | 도는 phase |
|---|---|
| 소스 폴링 | `sources` (기존 그대로) |
| 키워드 검색 | `seeds` |
| 회사 시드 | **`companies`** |

  즉 `phase='seeds'` 는 이제 **키워드만** 담당하고 회사 블록을 건너뛴다.

- ⚠️ **`attemptedSources` · `attemptedSeedSearch` 판정을 반드시 같이 고친다.**
  501 에서 이걸 놓쳐 "아무 일도 안 일어난 날"이 `ok=false`(크론 실패)로 잘못 찍힌 전례가 있다.
  새 phase 에서 건너뛴 블록은 "시도"로 치면 안 된다.
- ⚠️ `similarityWindowStarts` 의 `phase !== 'sources'` 조건도 새 phase 에 맞게 본다.

### 2) `phase='companies'` 에서는 예산 전부를 회사 시드에 준다

`COMPANY_SEARCH_BUDGET_MS = 20_000` 은 "키워드 뒤에 남는 자투리"를 전제로 한 값이다.
전용 크론에서는 의미가 없다. `phase === 'companies'` 일 때는 **소프트 데드라인 전체**를 쓰게 한다.

⚠️ 33개 시드가 240초에 몇 개나 도는지는 **아무도 모른다.** 상수를 임의로 정하지 말고
`companySeedsProcessed` / `companySeedsTotal` 계측(이미 있다)에 맡긴다. 첫 런에서 실측한다.

### 3) 라우트 신설 — `src/app/api/cron/crawl-companies/route.ts`

`crawl-seeds/route.ts` 골격을 그대로 따른다: `CRON_SECRET` Bearer 인증 → `createAdminClient()`
→ `runJob(admin, { key: 'cron:crawl-companies', trigger: 'cron' }, () => runCrawl({ phase: 'companies' }))`.
`runtime='nodejs'` · `dynamic='force-dynamic'` · `maxDuration=300`.

급상승 캐시 무효화(`revalidateTag`)는 **넣지 않는다** — 키워드 수집이 그 역할을 한다.

### 4) `expected-crons.ts`

```ts
'cron:crawl-companies': { label: '크롤(회사 seed)', maxAgeHours: 30, pgCronOnly: true },
```

**`vercel.json` 은 건드리지 않는다.** 526 과 같은 이유로 새 크론은 pg_cron 으로 간다
(`cron:trending-snapshot` 이 vercel.json 에 있는데도 호출이 사흘간 도착하지 않아 이관한 전례).
실제 스케줄 등록 SQL 은 플래너가 낸다.

### 5) 화면 오탐 방지 — 이게 빠지면 529 를 반복한다

분리 후 `cron:crawl-seeds` 의 `providers.company_google` 은 **항상 0**이 된다(블록을 안 도니까).
어드민 수집 현황이 이걸 "Google 회사 0건" 경고로 표시하면 매일 오탐이다.
529 에서 `cron:crawl` 을 읽어 매일 "네이버 0건 / GDELT 0건"이 뜨던 것과 같은 유형이다.

→ `CrawlProviderCounts` 에 **`company_phase_skipped: boolean`** 을 추가하고
(`keyword_phase_skipped` 와 같은 방식) `SearchProvidersPanel` · `CrawlLogsPanel` 이
skipped 면 경고 대신 **"별도 크론(cron:crawl-companies)"** 으로 표시하게 한다.

## 하지 않을 것

- `vercel.json` 수정, pg_cron SQL 작성
- `CRAWL_SOFT_DEADLINE_MS`(240초)·`MAX_SEARCH_SEEDS`(30) 변경 — 이번 변경의 효과를 먼저 잰다
- 키워드 단계 성능 최적화 — 별건이다
- GDELT 관련 코드 변경 — 539 로 충분하다
- 회사 시드 선별 로직(`COMPANY_SEED_COVERAGE_DAYS` 등) 변경

## 검증

1. `npx tsc --noEmit` / `npx eslint`(경고 0건) / `npm run build`
2. `runCrawl({ phase: 'seeds' })` 가 **회사 블록을 안 도는지**, `phase: 'companies'` 가
   **소스·키워드 블록을 안 도는지** — 각 블록에 임시 로그를 넣어 확인 후 제거
3. 세 phase 각각에서 `ok` 가 `false` 로 잘못 떨어지지 않는지
   (특히 due 대상이 0인 경우 — 501 회귀 가드)
4. 어드민 수집 현황에서 "Google 회사" 항목이 **경고가 아니라 "별도 크론"으로** 뜨는지
