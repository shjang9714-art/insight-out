## 1. 현행 진단 (검증된 코드 사실)

### 1.1 요약은 **LLM**이다 (룰베이스 아님)
`src/lib/crawler/summarize.ts`
```
summarizeKo(제목, 본문)      → llmComplete('summarize', …)   한국어 2~3문장
summarizeYoutubeKo(제목, 채널) → llmComplete('summarize', …)   제목·채널만으로 추정(본문 불필요)
SUMMARY_MIN_BODY_LEN = 200
```

### 1.2 무엇이 깨졌나 — 연쇄
1. **`cc59a1d`(오늘)** 가 크롤 504 타임아웃을 고치려 **인라인 요약을 크롤에서 분리**했다.
2. 요약은 `cron:summary-backfill`(`drainSummaries`)이 채우기로 했다.
3. 그 백필은 **`contents.summary_attempted_at`** 컬럼을 요구한다.
4. **SQL 295가 아직 안 돌았다** → `42703` → `return { processed: 0, filled: 0, remaining: -1 }`
5. → **요약 0건.** 그런데 `job_runs`엔 **'성공'** 으로 기록된다(또 조용한 실패).
   - `/admin/job-runs`에 `0 / 0 / — / **-1**` 로 찍혀 있다. **`-1`이 이 사고의 지문이다.**

### 1.3 ⭐ 진짜 지뢰 — SQL만 돌리면 더 나빠진다
`src/lib/contents/summarize-backfill.ts` `summarizeOne()`:
```ts
if (bodyKo && bodyKo.length >= SUMMARY_MIN_BODY_LEN) {
  summary = await summarizeKo(row.title, bodyKo)     // ← 본문 200자 이상일 때만 LLM 호출
}
...
// summary 가 null 이면:
await admin.from('contents').update({ summary_attempted_at: attemptedAt }).eq('id', row.id)
return 'skipped'
```
그리고 후보 쿼리는:
```ts
.is('summary_ko', null).is('summary_attempted_at', null)
```

→ **본문이 없거나 짧아서 LLM을 부르지도 못한 콘텐츠에까지 `summary_attempted_at`을 찍는다.**
→ 그 콘텐츠는 **나중에 본문이 채워져도 다시는 후보에 들어오지 않는다. 영구히 요약 없음.**

**그리고 `body-backfill`(본문 수집) 크론이 지금 안 도는 상태다**(`/admin/job-runs`). 즉 **본문이 없는 콘텐츠가 대량으로 쌓여 있다.**
지금 SQL을 돌리면 그것들이 **한 번에 전부 박제된다.**

> **"LLM을 호출했으나 실패"** 와 **"본문이 없어 호출조차 못 함"** 은 완전히 다른 사건이다.
> 전자는 마킹해야 하고(재시도 지옥 방지), **후자는 마킹하면 안 된다.**

### 1.4 재료 — `body_len`이 이미 있다
`supabase/schema.sql`:
```sql
alter table public.contents
  add column if not exists body_len integer
  generated always as (char_length(body_original)) stored;
create index if not exists idx_contents_body_len on public.contents (body_len);
```
**generated column + 인덱스.** 항상 정확하고, 후보 쿼리에서 바로 걸 수 있다. **새로 만들 것 없다.**

## 3. 구현 — `src/lib/contents/summarize-backfill.ts`

### 3-1. ⭐ 마킹 조건: **LLM을 실제로 호출했을 때만**

`summarizeOne()`이 세 가지를 구분해 반환하게 한다:

| 결과 | 뜻 | `summary_attempted_at` |
|---|---|---|
| `'filled'` | LLM 호출 → 요약 생성 성공 | **찍는다** (+ `summary_ko`) |
| `'failed'` | **LLM 호출함** → null/실패 | **찍는다** (재시도 지옥 방지) |
| `'not_ready'` | **호출 못 함** (본문 없음·짧음·번역 없음) | ⛔ **찍지 않는다** |

`'not_ready'`는 본문이 채워지면 **다음 배치에서 자연히 요약된다.**

### 3-2. ⭐ 후보 쿼리에 본문 조건 — `'not_ready'`를 애초에 안 뽑는다

3-1만 하면 `'not_ready'` 건이 **매 배치마다 다시 조회되어 드레인이 안 된다**(같은 20건을 무한 반복). 후보 단계에서 걸러야 한다.

요약 가능 조건:
```
category = '유튜브'                                    (본문 불필요 — 제목·채널로 추정)
또는  original_language = 'ko'  AND body_len >= 200
또는  original_language <> 'ko' AND body_translated_ko IS NOT NULL
```
PostgREST `.or()` + 중첩 `and(...)`로 표현할 것. `pendingSummaryCount()`에도 **같은 조건**을 적용해야 `remaining`이 거짓말하지 않는다.

- ⚠️ **`body_len` 미적용(42703) graceful**: 컬럼이 없으면 조건을 빼고 조회하되, `summarizeOne`의 `'not_ready'` 가드가 여전히 박제를 막는다. **앱이 죽으면 안 된다.**

### 3-3. 관측 가능하게 — 결과에 `notReady`를 실어라

```ts
return { processed, filled, failed, notReady, remaining }
```
`/admin/job-runs`의 `처리/설정/스킵/남음` 칸에 **`notReady`가 보여야 한다.**
> **"요약 안 된 게 몇 건이고, 그중 몇 건이 본문이 없어서인지"** 를 화면에서 알 수 있어야 한다.
> 이걸 안 보여주면 **또 조용히 실패한다.** 이 코드베이스의 반복된 실패 원인이 정확히 그것이다.

### 3-4. ⭐ 폴백 3종 — 요약을 "없으면 안 되는 것"에서 "있으면 좋은 것"으로 강등

**David 지시**: *"무료로 감당되는 수준이어야 한다. 콘텐츠 뉴스로 LLM이 터지면 안 된다."*
→ **요약이 없어도(한도 소진·실패·SQL 지연) 화면과 하류 산출물이 비지 않아야 한다.** 지금은 셋 다 비어버린다.

**① 카드 — `toExcerpt`의 본문 폴백이 죽어 있다** (LLM 0으로 즉시 해결)
```ts
// src/app/dashboard/contents/page.tsx:652, :715
excerpt={toExcerpt(item.summary_ko, null)}
//                                   ↑ 본문 폴백 인자에 null을 넘겨 기능을 죽였다
```
`toExcerpt(summaryKo, bodyOriginal, max)`는 **요약이 없으면 본문에서 발췌하도록 이미 설계된 유틸**이다. `ContentListCard.tsx:104`의 `'요약 정보가 없습니다.'` 폴백이 뜨는 이유가 이것이다.
- `.select`에 `body_original`을 추가하고 `toExcerpt(item.summary_ko, item.body_original)`로 고칠 것.
- ⚠️ **`body_original`은 크다(수천 자).** 목록 쿼리 페이로드가 커진다 → **발췌에 필요한 만큼만** 쓰고, 페이로드가 문제되면 **`ContentRow.tsx:72`처럼 이미 본문을 받는 경로를 참고**해 최소 범위로 처리할 것.

**② `insight/generate.ts` — 요약이 없으면 제목만으로 인사이트를 만든다**
```ts
// :61, :344
.map((a) => `[${a.id}] ${a.title}\n${a.summary_ko ?? ''}`)
//                                                  ↑ 빈 문자열 → 제목만 남는다
```
→ **`summary_ko ?? body_original 앞 N자`** 로 폴백. (briefing은 `:261`에서 이미 `body || summary` 폴백을 한다 — **그 패턴을 따를 것.**)

**③ `competitor-weekly/generate.ts`** — 동일하게 본문 폴백 추가(`:142` select에 `body_original` 포함).

> 이 셋을 고치면 **LLM 한도가 터져도 시스템이 죽지 않는다.** 요약은 품질 상승분이 되고, 없어도 돌아간다. **그게 "무료로 감당"의 실질이다.**

### 3-5. `remaining: -1`(SQL 미적용)은 실패로 기록할 것

지금은 컬럼이 없어도 `job_runs`에 **'성공'** 으로 남는다. 그래서 몇 시간을 모르고 지나갔다.
→ `remaining === -1`이면 **`failed`로 기록**되게 할 것(`run-job.ts`의 `isFailedStatus`는 `result.failed === true` 또는 `result.ok === false`를 본다. 둘 중 하나를 세팅하면 된다).

## 4. 회귀 가드

- ⛔ **본문이 없어 LLM을 호출하지 못한 건에 `summary_attempted_at`을 찍지 말 것.** 이 지시서의 전부다.
- ⛔ **LLM을 호출했는데 실패한 건은 반드시 찍을 것.** 안 찍으면 재시도 지옥 → LLM 한도 소진(283·265에서 겪었다).
- **후보 쿼리와 `pendingSummaryCount`의 조건을 일치시킬 것.** 다르면 `remaining`이 영원히 0이 안 되고 드레인이 안 끝난다.
- **유튜브는 본문 없이도 요약 가능하다**(`summarizeYoutubeKo`). 본문 조건으로 유튜브를 걸러내지 말 것.
- **`body_len` 미적용(42703)에도 앱이 죽지 않을 것.**
- 크롤(`orchestrator.ts`)은 **건드리지 말 것.** `cc59a1d`의 요약 분리는 옳은 결정이다(504 해결). 되돌리지 않는다.
- `SUMMARY_MIN_BODY_LEN = 200`을 바꾸지 말 것.
