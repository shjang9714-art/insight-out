# 지시서 441 — 본문 추출 실패 재시도 정책 (백오프)

## 0. 한 줄 · 원인
현재 본문 보강(`enrichOneBody`·`enrichRecentContents`)은 **추출 실패/미개선 시 `body_fetched_at = now`로 영구 마킹**해 `is('body_fetched_at', null)` 선정에서 제외 → **한 번 실패하면 다시는 재시도 안 됨.** Google News URL 디코딩 실패·매체 일시 지연·6초 타임아웃 등 **일시적 실패도 영구 검토대기(body_truncated/short)** 로 굳는다(조선비즈 기사 = 스니펫 "…" 만 남아 body_truncated). → **재시도 정책 도입**: 실패는 카운트+백오프로 재시도, 상한 도달 시에만 포기.

## 1. 착수 전 확인 (현행 코드 — origin/main)
- **공용 함수** `src/lib/contents/enrich-body.ts` `enrichOneBody()`: 성공(improved)→body_original+body_fetched_at, 실패(marked)→**body_fetched_at=now(재시도 방지)**. 드레인(`drainBackfill`)·수동(`enrichByIds`)이 공용.
- **선정** `drainBackfill`/`pendingCount`: `is('body_fetched_at', null) AND original_url NOT NULL` (+선택적 from/to). `cron:body-backfill`이 주기 드레인(수희 pg_cron 5분).
- **in-crawl 중복 로직** `src/lib/crawler/orchestrator.ts` `enrichRecentContents`(~1220~1270): 같은 성공/실패 처리를 **자체 복제**. 선정은 `collected_at >= runStartedAt`(이번 런만).
- **수동 재수집은 이미 있음**: `enrichByIds`(`/api/admin/body-backfill/by-ids`)는 body_fetched_at 무시 강제 재시도. (441은 **자동** 재시도를 추가.)
- 상수: `ENRICH_MIN_BODY_LEN=400`, `assessBodyQuality`(…/더보기로 끝나면 body_truncated).

## 2. 수희 SQL (`docs/sql-handoff/441-body-retry-2026-07-26.sql`)
```sql
-- 441 본문 추출 재시도 정책: 실패 카운트 + 다음 재시도 시각
alter table contents add column if not exists body_retry_count integer not null default 0;
alter table contents add column if not exists body_next_retry_at timestamptz;
-- 드레인 선정 가속(선택): 재시도 대상 부분 인덱스
create index if not exists idx_contents_body_retry
  on contents (body_next_retry_at)
  where body_fetched_at is null and original_url is not null;
```
- 적용 전에도 코드는 graceful(42703 폴백)으로 **현행 동작 유지**. 적용 후 재시도 활성.

## 3. 구현 (코드)

### 3.1 재시도 상수·백오프 (`enrich-body.ts` 상단)
```ts
const MAX_BODY_RETRIES = 4
// 시도 n회차(0-base) 실패 후 다음 재시도까지 지연(분): 30m, 3h, 12h, 24h
const RETRY_BACKOFF_MIN = [30, 180, 720, 1440]
```

### 3.2 `enrichOneBody` 실패 분기 교체 (핵심)
현재 실패 시 `update({ body_fetched_at: now })`를 **재시도 정책**으로:
- 성공(improved): 기존대로 body_original+body_fetched_at, **추가로 `body_retry_count=0, body_next_retry_at=null`**(성공 시 리셋).
- 실패(marked): 행의 `body_retry_count`(select에 추가)를 읽어
  - `count + 1 < MAX_BODY_RETRIES` → **body_fetched_at은 건드리지 않고**(=NULL 유지, 재선정 가능) `body_retry_count = count+1`, `body_next_retry_at = now + RETRY_BACKOFF_MIN[count]분`.
  - `count + 1 >= MAX_BODY_RETRIES` → **포기**: `body_fetched_at = now`(영구 종료), retry 컬럼 그대로. review_reason은 유지(body_truncated 등).
- **graceful**: 위 update가 `42703`(컬럼 없음)이면 **기존 동작으로 폴백**(`body_fetched_at=now`만). 즉 SQL 전에도 안전.
- select 컬럼에 `body_retry_count` 추가(`EnrichBodyRow`에 `body_retry_count?: number|null`).

### 3.3 선정 조건에 백오프 게이트 (`drainBackfill`·`pendingCount`)
`is('body_fetched_at', null).not('original_url','is',null)` 에 추가:
```ts
.or('body_next_retry_at.is.null,body_next_retry_at.lte.' + new Date().toISOString())
```
→ 아직 백오프 대기 중(next_retry_at 미래)인 행은 제외, 도래한 것만 재시도. (컬럼 없으면 `.or`가 에러날 수 있으니 **컬럼 존재 여부를 한 번 감지해 조건부 적용**하거나, 42703 시 `.or` 없이 폴백 쿼리로 재실행.)

### 3.4 in-crawl 경로 일원화 (`orchestrator.ts enrichRecentContents`)
- 중복된 성공/실패 처리(~1220~1270)를 **`enrichOneBody` 호출로 대체**(권장) — 그래야 재시도 정책이 in-crawl 신규 수집분에도 동일 적용. 리팩터가 부담되면 최소한 **실패 분기를 3.2와 동일 로직으로** 맞출 것(body_fetched_at 영구 마킹 금지).
- 단, `enrichRecentContents` 선정(`collected_at >= runStartedAt`)은 이번 런 신규분만 보므로, **과거 실패분 재시도는 `drainBackfill`(cron:body-backfill)이 담당** — 3.3 게이트가 그 경로에서 동작하면 됨.

## 4. 회귀 가드 / 검증
- **무한 재시도 없음**: MAX_BODY_RETRIES 상한 후 body_fetched_at 마킹으로 종료. 죽은 URL(디코딩 영구 실패·페이월)은 4회 후 포기.
- **성공 리셋**: improved 시 retry_count=0.
- **graceful**: 컬럼 미적용(42703) 시 현행 동작 유지 — SQL 전 재현검증·배포 안전.
- **관련도 판정 불변**: BODY_REVIEW_REASONS 밖(low_relevance 등)은 그대로. 재시도는 본문 계열에만 의미(단, 마킹 로직은 전 실패에 적용해도 무방).
- `tsc`/`lint`/`build` 통과.

## 5. 재현검증 (플래너)
```
git diff --stat origin/main...origin/agent/441-body-retry
git grep -n "body_retry_count\|body_next_retry_at\|MAX_BODY_RETRIES" origin/agent/441-body-retry -- src
```
확인:
1. `enrich-body.ts` 실패 분기가 백오프(retry_count+1·next_retry_at)로 바뀜, MAX 상한 후에만 body_fetched_at. 42703 폴백 존재.
2. `drainBackfill`/`pendingCount` 선정에 next_retry_at 게이트(+컬럼 없을 때 폴백).
3. `orchestrator.ts` in-crawl 실패 분기도 영구 마킹 안 함(enrichOneBody 호출 or 동일 로직).
4. SQL 파일 `docs/sql-handoff/441-*.sql` 포함, 마이그레이션 코드에 직접 실행은 없음(수희 적용).

**배포+SQL 후 검증**: 조선비즈처럼 갇힌 body_truncated 행이 다음 드레인부터 재시도되는지(next_retry_at 도래 시). 수동 즉시 재시도는 기존 `/api/admin/body-backfill/by-ids`로도 가능.
