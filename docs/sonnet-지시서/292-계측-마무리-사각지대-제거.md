# 지시서 292 — 계측 마무리: 사각지대 구조적 제거

> 작성: Opus(플래너) · 2026-07-12 · 설계: `docs/설계-작업이력-실패가시성.md` (C-2·C-3)
> 근거: 289 배포 직후 **다른 레인이 새 크론(`trending-snapshot`)을 추가했는데 계측이 안 됐다.**
> 앞으로도 크론이 추가될 때마다 사람이 기억해야만 계측이 지켜진다 → **구조적으로 막아야 한다.**
> 협업 루프: 로컬(커밋X). 위임 → 구현 → 재현검증 → "커밋해" → 커밋·병합·푸시.
> 전제: **289 배포 + SQL 적용 완료**(`job_runs` 존재). **SQL 없음.**

## 0. 한 줄

계측 사각지대를 **메우고**(trending-snapshot, 어드민 잡 13개), 앞으로 생기지 않게 **감지 장치**를 붙인다.

## 1. 현행 진단 (검증된 코드 사실)

### 1.1 사각지대 1 — 새로 들어온 크론
- `vercel.json`에 크론 **11개**, 그중 **`trending-snapshot`만 `runJob` 미적용**(나머지 10개는 289에서 계측 완료).
- 289 작업 중 다른 레인이 추가한 것. **실패해도 `job_runs`에 안 남는다** — 289가 없애려던 바로 그 상태다.

### 1.2 사각지대 2 — 어드민 수동 잡 13개
전부 미계측(`src/app/api/admin/`):
`body-backfill` `canonical-backfill` `cluster-backfill` `competitor-weekly` `lgu-impact`
`pdf-cover-backfill` `sentiment` `signals-backfill` `thumbnail-backfill` `translate-backfill`
`youtube-summary` `youtube-tagging` `youtube-transcript`

> 수동 잡은 관리자가 눌러서 결과를 **즉시 화면에서 본다**(크론보다 덜 급하다). 하지만 **"누가 언제 무엇을 돌렸는지" 기록이 없어**, 사후 추적이 안 된다. `runJob`이 이미 있으니 붙이는 건 기계적이다.

### 1.3 구조적 문제 — 감지 장치가 없다
- 새 크론이 계측 없이 들어와도 **아무도 모른다.**
- 크론이 **아예 안 도는 것**(Vercel 크론 설정 누락·비활성)도 모른다.
- **두 경우가 화면상 똑같이 보인다** — 둘 다 `job_runs`에 기록이 없다.
→ **하나의 장치로 둘 다 잡을 수 있다.**

### 1.4 `runJob` 시그니처(289, 그대로 재사용)
```ts
runJob(admin, { key, trigger: 'cron'|'admin', mode?, startedBy? }, fn)
```
- `job_key` 규약: `cron:{name}` / `admin:{name}`
- 계측 실패는 잡을 깨뜨리지 않는다(로깅만, 예외는 그대로 전파). **이 원칙을 유지할 것.**

## 3. 구현

### 3-1. `trending-snapshot` 크론 계측
`src/app/api/cron/trending-snapshot/route.ts` — CRON_SECRET 검증 **이후** 로직을 `runJob(admin, { key: 'cron:trending-snapshot', trigger: 'cron' }, ...)`로 감싼다. 289가 다른 10개에 한 것과 동일.

### 3-2. 어드민 잡 13개 계측
각 라우트에서 관리자 확인 **이후** 작업을 `runJob`으로 감싼다.
- `key`: `admin:{라우트명}` (예: `admin:thumbnail-backfill`)
- `trigger`: `'admin'`
- **`startedBy`: 관리자 user id** ← 크론과 달리 실행자가 있다. 각 라우트의 `verifyAdmin`이 이미 user를 조회하므로 **그 id를 넘긴다.**
  - `verifyAdmin`이 user id를 반환하지 않으면 반환하도록 최소 수정(기존 인증 로직은 건드리지 말 것).
- `mode`: 쿼리의 `mode`(fresh/retry)가 있으면 그대로 전달.
- **기존 반환 JSON·인증·동작은 일절 변경 금지.** 감싸기만 한다.

### 3-3. ⭐ 계측 누락 + "안 돈 크론" 감지 (`/admin/job-runs`)

**이게 이 지시서의 핵심이다.** 사각지대가 다시 생기지 않게 만든다.

- **기대 크론 목록을 코드에 상수로 둔다**:
  ```ts
  // src/lib/jobs/expected-crons.ts (신규)
  // vercel.json 의 크론과 1:1로 유지할 것. 크론을 추가하면 여기에도 추가한다.
  export const EXPECTED_CRONS: { key: string; label: string; maxAgeHours: number }[] = [
    { key: 'cron:crawl',              label: '크롤',            maxAgeHours: 30 },
    { key: 'cron:briefing',           label: '모닝브리핑',      maxAgeHours: 30 },
    { key: 'cron:newsletter',         label: '뉴스레터',        maxAgeHours: 30 },
    { key: 'cron:body-backfill',      label: '본문 수집',       maxAgeHours: 30 },
    { key: 'cron:signals-backfill',   label: '신호 분류',       maxAgeHours: 30 },
    { key: 'cron:ai-refresh',         label: 'AI 갱신',         maxAgeHours: 30 },
    { key: 'cron:link-health',        label: '링크 헬스',       maxAgeHours: 30 },
    { key: 'cron:key-insights',       label: '핵심 인사이트',   maxAgeHours: 30 },
    { key: 'cron:daily-insights',     label: '일일 인사이트',   maxAgeHours: 30 },
    { key: 'cron:trending-snapshot',  label: '트렌딩 스냅샷',   maxAgeHours: 30 },
    { key: 'cron:competitor-weekly',  label: '경쟁사 주간',     maxAgeHours: 2  },  // 매시 실행
  ]
  ```
  - `maxAgeHours`: 이 시간 안에 **어떤 기록이든**(succeeded/skipped/failed) 있어야 정상. 일간 크론은 30시간(여유), 매시 크론은 2시간.
  - ⚠️ `competitor-weekly`는 매시 돌지만 대부분 `skipped:'not_scheduled'`다. **`skipped`도 "돌았다"로 친다** — 안 그러면 항상 경고가 뜬다.

- **`/admin/job-runs` 상단에 "크론 상태" 요약 블록**:
  - `EXPECTED_CRONS`를 순회하며 각 `job_key`의 **마지막 기록 시각**을 조회.
  - **기록이 아예 없다** → `계측 안 됨 또는 한 번도 안 돎` (빨강)
  - **마지막 기록이 `maxAgeHours` 초과** → `안 돈 지 오래됨` (주황) + 마지막 시각 표시
  - 정상 → 초록 한 줄(조용히)
  - **모두 정상이면 블록 자체를 접거나 한 줄로 축소** — 평상시 노이즈가 되면 아무도 안 본다.

> 이 장치가 있으면 **새 크론을 계측 없이 추가해도** `EXPECTED_CRONS`에 넣는 순간 "계측 안 됨"으로 즉시 드러난다. 넣지 않으면 목록에서 빠지지만, 그건 **vercel.json과 대조하는 습관**으로 커버한다(§4 가드).

### 3-4. 보존 정리 (90일)

- **유지보수 화면(`/admin/maintenance`)에 "작업 이력 정리" 버튼** 추가:
  - `POST /api/admin/job-runs/cleanup` — 90일 초과분 삭제, 삭제 건수 반환.
  - 어드민 role 직접 재확인. 확인 다이얼로그.
- 크론 자동화는 하지 않는다(수동으로 충분, 나중에 필요하면 추가).

## 4. 회귀 가드

- **계측 실패가 잡을 깨뜨리지 않는다**(289 원칙). `runJob`을 감싸기만 하고, 그 안의 격리 로직은 **건드리지 말 것.**
- **`job_runs` 미적용(42P01)에서도 모든 잡이 정상 동작**해야 한다(289가 이미 보장 — 유지).
- **기존 반환 JSON·인증(CRON_SECRET / admin role)·동작을 일절 변경하지 말 것.** 감싸기만 한다.
- **`competitor-weekly`의 `skipped`를 "안 돎"으로 오판하지 말 것** — 매시 돌면서 대부분 `not_scheduled`로 빠진다. **`skipped`도 "돌았다"로 친다.** 안 그러면 "안 돈 크론" 경고가 항상 켜져 노이즈가 된다.
- **평상시 조용해야 한다.** 이상이 없으면 크론 상태 블록은 한 줄로 축소. 매일 빨간 게 떠 있으면 아무도 안 본다(289 대시보드 카드와 같은 원칙).
- `EXPECTED_CRONS`는 **`vercel.json`과 1:1**로 유지. 파일 상단에 그 사실을 주석으로 남길 것.
- 보존 정리는 **삭제**다. 확인 다이얼로그 없이 실행되면 안 된다.
