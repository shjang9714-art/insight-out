# 지시서 236 — Vercel 함수 리전을 Supabase(시드니)에 co-location

목표: 서버 전환/로딩 지연의 **근본 원인(함수↔DB 리전 불일치)**을 제거한다. Vercel 서버리스 함수 리전을 Supabase(ap-southeast-2, 시드니)와 같은 **`syd1`(시드니)**로 지정해 DB 왕복 지연을 없앤다.

범위: 배포 설정(`vercel.json`) 한 줄. 코드 로직 변경 없음, SQL 없음.

---

## 1. 진단 근거 (실측, 2026-07-09)
- 프로덕션 `/dashboard` 실측: 엣지 TTFB **40ms**(hnd1 도쿄 엣지, 빠름)인데 **전체 서버 스트리밍 ~2.8초**(웜 리로드도 동일 → 콜드스타트 아님).
- 응답 헤더 `x-vercel-id: hnd1::iad1::...` → **함수 연산 리전 = iad1(미국 워싱턴)**.
- Supabase 리전 = **ap-southeast-2(시드니)**. 사용자 = 한국.
- ∴ 함수(미국)가 매 쿼리마다 Supabase(호주)로 **미국↔호주 ~200ms 왕복**. 홈(FeedSlot+섹션 다수 쿼리)에서 누적 → 2.8초.
- 231·234의 쿼리 병렬화는 쿼리 "개수"만 줄였고 **왕복 지연 바닥**은 그대로였음.
- 현재 `vercel.json`에 `regions` 미지정 → 기본 iad1.

## 2. 구현
`vercel.json`에 함수 리전 지정(Supabase와 동일 대도시권):
```json
{
  "regions": ["syd1"],
  "crons": [ ... 기존 그대로 ... ]
}
```
- `syd1` = 시드니(Vercel), Supabase `ap-southeast-2`(시드니)와 co-location.
- Vercel **Pro**라 단일/다중 리전 지정 가능.
- 기존 `crons` 배열은 그대로 유지(리전 키만 추가).
- 코드·env·쿼리 변경 없음.

## 3. 회귀 가드
- 전 서버 함수·API·cron이 syd1에서 실행됨 → **함수↔Supabase 로컬(~5ms)**. cron(크롤/브리핑 등)도 DB 근접이라 오히려 빨라짐.
- 사용자(한국)↔함수(시드니) 왕복은 요청당 1회(~130~150ms) 추가되나, DB 다중 쿼리 왕복 제거分이 압도 → 순 대폭 개선.
- 엣지(정적/이미지)는 여전히 사용자 근처(hnd1 등)에서 서빙 — 변화 없음.
- 인증·기능 동작 불변(리전만 이동).

## 4. 검증 (배포 후 실측)
- 배포 후 `/api/version` 응답 헤더 `x-vercel-id`가 **`...::syd1::...`**(함수 리전 syd1)인지 확인.
- `/dashboard` 전체 로딩(navigation load) 시간: **2.8초 → 목표 <0.6초**(브라우저 Performance 또는 체감).
- 홈·기업동향·콘텐츠 전환 체감 확인.

## 5. 라이브 체크리스트
- [ ] `x-vercel-id` 함수 리전이 syd1.
- [ ] 홈/전환 로딩이 눈에 띄게 빨라짐(2.8초 → 수백 ms).
- [ ] cron·API 정상.

## 참고: 더 이상적인 후속(선택, 큰 작업)
사용자가 한국이므로, 궁극적으로는 **Supabase를 서울(ap-northeast-2)로 마이그레이션 + Vercel `icn1`(서울)** 이 함수·DB·사용자 3자를 모두 근접시켜 최적. 단 Supabase 리전 이전은 데이터 마이그레이션이 필요한 큰 작업 → 지금은 **syd1 co-location(즉효)**, 서울 이전은 별도 검토.
