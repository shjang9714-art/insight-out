## 배경 — 무엇을 바꾸나

현재 홈의 "실시간 급상승 키워드"(#104)를 **"매일 크롤링되는 기사들 중 유사/동일 주제별 발행건수"** 기반으로 재구성한다. 즉 개별 키워드 문자열 빈도가 아니라, **주제(토픽) 클러스터 단위의 발행량과 급증세**로 급상승을 판정한다.

핵심 결정(사용자 확정): **신규 클러스터링을 만들지 않고 기존 `issues` 클러스터를 재사용한다.** 이유:
- `issues`는 이미 유사/동일 기사를 하나의 주제로 묶고 있고, AI 인사이트 탭에서 **최근 7일 건수·급증률(예: +3983%)·활동량**을 계산해 노출 중이다([[지시서_20260705_AI인사이트-브리핑이슈통합-이슈리스트정리-중복병합.md]] 참조).
- 별도 집계 파이프라인/신규 테이블 없이 **읽기 뷰 + 정렬**만으로 급상승 키워드를 만들 수 있고, AI 인사이트 탭과 데이터가 일관된다.
- 이미 근접 중복 병합·소프트 아카이브(`archived_at`/`merged_into`) 로직이 있어, 급상승 키워드도 **아카이브/병합 이슈를 자연히 제외**할 수 있다.

즉 "급상승 키워드 1개 = 활동 급증 중인 이슈 1개"로 매핑하고, 이슈의 대표 키워드/짧은 라벨을 칩으로 노출한다.

## §1. 급상승 판정 로직 (데이터 층)

### 1-1. 후보 집합
- 대상: **`status='published'` 이슈만**(기존 `fetchIssueActivity` 필터와 동일 — draft/archived 제외). `archived_at`/`merged_into` 컬럼은 존재하지 않으므로 사용하지 않는다(§0 실측).

### 1-2. 랭킹 메트릭 (실측 B1·B2 결과로 택1, 상수로 튜닝 가능하게)
"실시간 급상승"이므로 **짧은 창의 발행건수 급증**을 우선한다. 우선순위:

- **1순위(권장 기본):** 최근 **48시간 발행건수**(`recent_count`) desc.
  - 이유: 사용자 요구 "매일 크롤링되는 기사들 중 발행건수 기반" + "실시간"에 가장 직접적. 하루 1회 크롤이라 24h는 표본이 얇을 수 있어 48h를 기본값으로(상수 `TRENDING_WINDOW_HOURS=48`).
- **2순위(tie-break):** **급증률**(`recent_count` / 직전 동일창 대비) desc.
  - 단, 분모 0(신규 이슈)은 급증률이 무한대로 튀므로 상수 `MIN_BASELINE=1`로 클램프하거나 "신규" 배지로 별도 처리.
- **최소 노출 임계:** `recent_count >= MIN_TRENDING_COUNT`(초기 2). 발행 1건짜리 잡음 제거.
- 표시 개수: 상위 `TRENDING_LIMIT`(초기 8, 홈 레이아웃에 맞게 조정).

> B1에서 최근 N시간 창 집계가 **불가**(발행일/수집일 시각 컬럼 없음)하면, 폴백으로 AI 인사이트 탭이 이미 쓰는 **최근 7일 건수 + 급증률**을 그대로 재사용한다. 이 경우 "실시간"은 "최근 7일 급상승"으로 의미가 완화됨을 사용자에게 보고하고, 시각 컬럼 추가는 별도 차수로.

### 1-3. 구현 형태 — 읽기 뷰 권장
신규 테이블 대신 **읽기 뷰** `trending_keywords`를 생성해 프론트가 단순 SELECT만 하게 한다(집계 로직을 SQL에 고정, 앱 코드 단순화).

```sql
-- §0 실측 반영: collected_at 사용, status='published' 필터, archived_at/merged_into 미사용.
-- issue_contents가 collected_at을 직접 안 가지면 contents 조인(아래처럼).
create or replace view public.trending_keywords as
select
  i.id            as issue_id,
  i.title,
  count(c.id) filter (
    where c.collected_at >= now() - interval '48 hours'
  )               as recent_count,
  count(c.id) filter (
    where c.collected_at >= now() - interval '96 hours'
      and c.collected_at <  now() - interval '48 hours'
  )               as prev_count
from public.issues i
join public.issue_contents ic on ic.issue_id = i.id
join public.contents c        on c.id = ic.content_id
where i.status = 'published'
group by i.id, i.title
having count(c.id) filter (where c.collected_at >= now() - interval '48 hours') >= 2
order by recent_count desc;

-- ★ GRANT 필수 (기존 issue_evidence 뷰와 동일 패턴)
grant select on public.trending_keywords to anon, authenticated;
```
- 급증률은 뷰에서 `recent_count`/`greatest(prev_count,1)`로 계산하거나 프론트에서 계산.
- 대안: 뷰 신설 대신 **기존 `fetchIssueActivity`/`computeIssueActivity`에 48h 창 파라미터를 추가**해 앱코드로 처리해도 됨(현재가 KST 주 단위 집계이므로 창만 48h로 바꾸는 최소 변경). 뷰 vs 앱코드는 Claude Code 재량 — 단 홈/AI인사이트 이슈탭과 **집계 로직 중복이 안 생기게** 한 소스로 통일.
- **실행 주체:** DDL은 Claude Code가 `supabase/2026-07-08-trending-keywords-view.sql`(뷰 + **GRANT 포함**) 파일만 생성하고, **실제 실행은 수희가 Supabase SQL Editor에서 직접**(Claude Code는 대시보드 접근 없음). 수희 실행·검증(아래 확인 쿼리 동봉) 완료 보고 후 프론트 연결.
- 확인 쿼리도 같은 파일에 포함:
```sql
select issue_id, title, recent_count, prev_count
from public.trending_keywords limit 10;
```

## §5. 보강 (2026-07-08 추가) — 서브이벤트 클러스터링으로 특정성 확보

### 5-0. 왜 (배경)
§1~§2 v1은 급상승 단위가 **이슈 전체**라, `issues.title`이 "AI 경쟁·협업 확대" 같은 상록수 대분류면 매일 비슷한 항목이 상위권을 점유해 "실시간 급상승"의 이름값을 못 한다. 이슈 클러스터링 자체를 건드리는 건 리스크가 커서(§4 범위), **이슈는 그대로 두고 표시 층에서만** 최근 48h 기사를 **특정 사건 단위로 쪼개** 노출한다. 안 쪼개지는 이슈는 자연히 "대표 헤드라인 1개" 항목으로 degrade → 손해 없음.

핵심 아이디어: **이슈 내부(within-issue)의 48h 기사만** 서브클러스터링한다. 이렇게 하면 (a) 대상 N이 이슈당 소수라 계산이 가볍고, (b) 각 서브클러스터가 부모 이슈 1개로 깔끔히 매핑돼 클릭 목적지(`/dashboard/issues/[id]`)가 유지된다.

> ⚠️ §1의 `trending_keywords` 뷰는 그대로 유지(급상승 **후보 이슈 + 48h 건수** 식별용). 서브클러스터링은 그 위에 얹는 **표시 층 후처리**다. LLM 사용 없음(Cerebras 쿼터 이슈 [[project_crawl_architecture]] 회피).

### 5-1. Step 0-b 실측 (먼저 보고)
1. `content_entities` 스키마 — (content_id, entity_id, ...) 구조와 `entities`의 canonical_name 컬럼(서브클러스터 라벨용). 한 콘텐츠에 엔티티 다중 매핑 맞는지.
2. `contents.title` 존재·채움률, 매체명/브래킷이 제목에 섞여 있는지(정규화 필요 판단). `pg_trgm` 확장 활성 여부(기존 `2026-07-07-유튜브제목-trgm인덱스.sql`로 확장 자체는 켜져 있을 가능성 — 확인). **단, 서브클러스터링은 이슈당 소수 기사 대상이라 앱코드 in-memory로 하면 DB 인덱스 불필요.**
3. `trending.ts`가 이미 후보 이슈별로 48h 기사 rows(제목·collected_at·엔티티)를 가져올 수 있는지, 아니면 조인 1개 추가면 되는지.

### 5-2. 알고리즘 (앱코드, `trending.ts` 확장)
후보 = §1 뷰가 준 `status='published'` & 48h ≥2건 이슈. 각 후보 이슈에 대해:

1. **입력 수집:** 그 이슈의 **48h 기사 rows**(id, 정규화 title, collected_at, 대표 엔티티들, source, url).
2. **제목 정규화:** 매체 브래킷/말머리(`[속보]`, `[단독]`, `- OO신문` 등)·기호 제거, 공백 정리, 소문자화.
3. **서브클러스터링(연결요소):** 기사 쌍의 **제목 trgm 유사도 ≥ `SUBCLUSTER_SIM`(초기 0.35)** 이거나 **핵심 엔티티 공유** 시 같은 그룹으로 union-find. 유사도는 pg_trgm `similarity()` 또는 앱코드 trigram Jaccard 중 택1(이슈당 ≤ 수십 건이라 O(n²) 무방).
4. **서브클러스터 채택:** 그룹 크기 ≥ `MIN_SUBCLUSTER`(초기 2)면 **특정 급상승 이벤트**로 채택.
   - 라벨: 그룹의 **대표 헤드라인**(가장 짧거나 매체 신뢰도 높은 제목) + **지배 엔티티 칩**(그룹 내 최빈 canonical_name).
   - 크기(그룹 내 48h 건수)를 그 이벤트의 `recent_count`로.
5. **degrade(안 묶일 때):** 채택 서브클러스터가 없으면(전부 단발/비유사) 그 이슈는 **항목 1개**로, 라벨은 48h 기사 중 가장 최근 대표 헤드라인, `recent_count`=이슈 48h 건수(= 사실상 옵션 ① 동작).
6. **전역 랭킹:** 모든 이슈에서 나온 서브클러스터/degrade 항목을 **`recent_count` desc**(급증률 tie-break)로 합쳐 상위 `TRENDING_LIMIT`(8) 노출.
7. **중복 억제:** 서로 다른 이슈의 서브클러스터가 같은 지배 엔티티+유사 헤드라인이면 상위 1건만(옵션, 안전).

### 5-3. 표시 (UI 층, §2 갱신)
- 칩/행 라벨 = **특정 헤드라인 축약** + 보조로 **엔티티 칩**(예: `KT`) + 건수 + ▲급증/NEW.
- 클릭 → **부모 이슈 `/dashboard/issues/[issue_id]`**(서브클러스터의 다수결 이슈). 기존 목적지 유지.
- degrade 항목도 동일 UI(라벨만 대표 헤드라인) — 사용자는 차이를 의식하지 않음.
- 캐싱: 후처리는 크롤 주기(1일 1회) 대비 자주 바뀌지 않으므로 **짧은 revalidate(예: 10~30분) 또는 크롤 완료 훅 캐시**. 매 요청 재계산 지양(가벼워도 습관적으로).

### 5-4. 튜닝 상수 (한곳에 모아 노출)
`SUBCLUSTER_SIM=0.35`, `MIN_SUBCLUSTER=2`, `TRENDING_WINDOW_HOURS=48`, `MIN_TRENDING_COUNT=2`, `TRENDING_LIMIT=8`. 라이브 결과 보고 조정.
