## 배경 (David)

지식그래프 메뉴의 v1. David 예시 — "LG유플러스 클릭 → 관련 이슈·관련 기업·관련 기술·최근 변화". 엔티티(99)를 **노드**로, content_entities 공기출현으로 **관계**를 보여준다. 본격 그래프 렌더(노드-엣지 시각화)는 P2 — 이번엔 **엔티티 상세(노드 뷰) + 타입별 브라우즈**로 지식그래프를 사용 가능하게 만든다.

## 설계 결정 (Opus)

1. **관계 = content_entities 공기출현(co-occurrence)**. 같은 콘텐츠에 함께 링크된 엔티티 = 관련 엔티티. 별도 관계 테이블/LLM 불필요 — 순수 SQL 집계.
2. **신규 SQL 없음.** 엔티티당 바운디드 조회(최근 콘텐츠 N건)로 JS 집계. (대용량화 시 co-occurrence RPC 는 후속 최적화.)
3. **엔티티 칩 목적지 통일** → `/dashboard/entities/{id}`(현재 99 상세 칩은 임시로 토픽 타임라인行. 이제 엔티티 페이지로). 이를 위해 칩 쿼리에 엔티티 `id` 포함.
4. **그래프 시각화(노드-엣지 렌더)는 이번 범위 아님**(P2). 관계는 "관련 엔티티 칩"으로 표현.
5. 네비에 **"지식그래프"** 추가(David 최소변경안).

## 작업

### A. 엔티티 상세(노드 뷰) — `src/app/dashboard/entities/[id]/page.tsx` (신규, 서버)
- `params: Promise<{ id: string }>`. 엔티티 조회(없으면 notFound/빈 안내).
- 데이터(전부 서버 집계):
  1. **헤더**: canonical_name + 타입 배지(ENTITY_TYPE_LABEL·색, 기업 경쟁사 구분)·description·mention_count. 동의어(entity_aliases) 작은 칩.
  2. **콘텐츠 id 확보**: `content_entities` where `entity_id=this` → content_id 목록(최근순 바운디드, 예: 200). 이후 집계의 기준 집합.
  3. **관련 콘텐츠 by 카테고리**: 기준 콘텐츠를 `category`별 카운트(CONTENT_CATEGORY_LABEL) + 카테고리별 최근 몇 건(제목 링크 `/dashboard/contents/{id}`).
  4. **타임라인**: 기준 콘텐츠 시간순(98 패턴 — KST 일자 그룹·논조 배지). 상위 N(예: 40).
  5. **관련 엔티티(co-occurrence)**: `content_entities` where `content_id in (기준 집합)` and `entity_id != this` → entity_id별 카운트 → `entities` join(canonical_name·type) → 빈도순 상위 칩(타입색·클릭→`/dashboard/entities/{id}`). **지식그래프의 핵심.**
  6. **관련 이슈**: `issue_contents` where `content_id in (기준 집합)` → issue_id별 카운트 → `issues`(published) join → 상위 이슈 링크(`/dashboard/issues/{id}`). (101 미적용/빈이면 섹션 생략 graceful.)
  7. **논조 분포**: 기준 콘텐츠 sentiment 집계(긍/중/부).
- 데이터 0이면 각 섹션 graceful.

### B. 지식그래프 브라우즈 — `src/app/dashboard/entities/page.tsx` (신규)
- 타입 탭/필터(전체 + EntityType 6종, ENTITY_TYPE_LABEL) + 검색(이름·동의어) + mention_count desc 정렬. (search 페이지의 클라 필터 패턴 참고 — 타입 탭은 서버 `?type=` 또는 클라 leaf 중 단순한 쪽.)
- 목록: 엔티티 카드/행(타입 배지·canonical_name·mention_count·경쟁사 표시) → 클릭 `/dashboard/entities/{id}`.
- 헤더 "지식그래프" + 안내("기업·기술·인물 등 엔티티와 관계"). 빈 상태.

### C. 엔티티 칩 목적지 통일 — `src/app/dashboard/contents/[id]/page.tsx`
- 칩 쿼리 select 에 **`id` 추가**: `entities(id, canonical_name, entity_type, is_competitor)`. EntityRow 타입에 `id` 추가.
- 칩 `href` 를 `/dashboard/topics/...` → **`/dashboard/entities/${e.id}`** 로 변경.
- (101 머지돼 있으면) 이슈 상세의 "관련 엔티티" 칩도 동일하게 `/dashboard/entities/{id}` 로 — 단, 101 PR 과 충돌 피해서 이 지시서는 99 상세만 변경하고, 이슈 상세 칩 통일은 보고에 메모(후속 1줄 수정).

### D. 네비 — `src/components/dashboard/Sidebar.tsx`
- '이슈' 섹션 인근에 **'지식그래프'** 섹션/링크(`/dashboard/entities`, 아이콘 `Network` 또는 `Share2`). 활성표시 기존 패턴.

## 회귀 / 주의
- **신규 SQL 없음.** 99(content_entities)·101(issue_contents) SELECT만. 99 미적용이면 빈 상태(데이터 없음). 101 미적용이면 "관련 이슈" 섹션만 생략.
- co-occurrence 는 기준 콘텐츠 바운디드(예 200) 집계 — 인기 엔티티는 근사(전수 아님). 정확도/성능 더 필요하면 후속 RPC.
- 칩 링크 변경 시 엔티티 `id` 필수(쿼리 select 에 포함). id 없으면 링크 깨짐 — 반드시 추가.
- 서버 컴포넌트 유지(브라우즈 검색만 클라 leaf 가능). RLS는 인증 조회 충분(99/101 정책). UI 한국어(#1)·색 토큰(#9)·`any` 금지·lucide.
- 98 타임라인 KST 일자 헬퍼와 일치.
