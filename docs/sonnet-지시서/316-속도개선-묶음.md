## 1. ⚠️ v1 진단이 틀렸다 — 실측으로 정정 (기록을 남긴다)

### 1.1 v1이 주장한 것 (전부 틀림)
> *"브라우저(서울)가 Supabase(시드니)를 직접 부른다. 왕복 5회 × 170ms."*

**DevTools Network 실측: `supabase.co` 요청이 0개다.** 브라우저는 Supabase를 직접 안 부른다.
→ **v1의 §1.1·§3-2(`contents` 834줄 SSR 재구성)는 근거가 없다. 하지 말 것.**

**교훈: 코드를 읽고 세운 가설을 실측 없이 지시서로 만들었다.** 오늘 반복해서 경계한 그 실수를 플래너가 했다.

### 1.2 ⭐ 실측이 보여준 진짜 원인 — **prefetch 폭주**

DevTools Network (`?_rsc=` 필터, L1 탭 클릭 시):
```
UUID 이름의 fetch 요청  수십 개   각 550~700ms, 일부 1.4초
issues (실제 네비게이션)          1.37초 / 1.16초
전체 타임라인                     15초
```
UUID = `/dashboard/contents/{id}` — **콘텐츠 카드 링크의 `<Link>` prefetch**다.

```
prefetch={false}          →  앱 전체에 0곳
카드 링크                 →  뷰포트 진입 시 자동 prefetch (Next.js 기본)
/dashboard/contents/[id]  →  force-dynamic
```

**prefetch가 실제 서버 렌더 + DB 쿼리를 실행한다.** 그리고 그 상세 페이지는:
- 본문 + 관련 콘텐츠 + 관련 유튜브 + 관련 기업 + **313이 오늘 추가한 역참조 4종**
- **= 요청 하나당 DB 쿼리 7~8개**

**카드 20개 × 쿼리 8개 = 서버가 150개 쿼리를 돌린다.** 그게 서버를 점유해서 **실제 탭 이동이 1.37초** 걸린다.

### 1.3 ⚠️ v1의 `staleTimes`(3-1, 배포됨 `f819fdf`)가 이걸 증폭했다

Next 15에서 `staleTimes.dynamic = 0`(기본)이면 동적 페이지는 **`loading.tsx`까지만** prefetch한다.
**`staleTimes.dynamic > 0`으로 바꾸면 full prefetch**가 된다.

→ **3-1이 prefetch를 무겁게 만들었다.**
→ 그래서 David의 관찰이 정확히 갈렸다: **하위탭(같은 라우트, 카드 링크 없음)은 빨라졌고, L1 탭(카드가 깔린 목록에서 이동)은 오히려 느려졌다.**

**⛔ `staleTimes`를 되돌리지 말 것.** 하위탭 개선은 진짜다. **prefetch를 막는 게 맞는 수정이다.**

### 1.4 ISR·SSG는 못 쓴다 (v1에서 유효한 조사 — 다음에 또 나올 질문이라 남긴다)
- **SSG**: 로그인 필수 + 렌즈(개인화) + 매일 바뀌는 콘텐츠 → 빌드 시점에 만들 게 없다.
- **ISR**: 모든 서버 페이지가 `createClient()`(`@/lib/supabase/server`)로 **쿠키를 읽는다.**
  Next.js는 `cookies()`를 읽는 순간 **강제 동적 렌더**한다. ISR 불가.
  → **`force-dynamic` 13개를 지워도 아무것도 안 바뀐다. 건드리지 말 것.**
- **SSR**: 이미 쓰고 있다.

## 3. 구현

### 3-1. ⭐⭐ prefetch 폭주 차단 — **이게 본체다**

**목록에서 대량으로 렌더되는 `<Link>`에 `prefetch={false}`.**

대상: `/dashboard/contents/[id]`로 가는 모든 Link (**33곳**)
```
src/components/dashboard/ContentCard.tsx
src/components/dashboard/ContentListCard.tsx
src/components/dashboard/ContentRow.tsx
src/components/mypage/ArchivesTab.tsx          ← 아카이브도 목록이다
+ 분석·이슈·기업·경쟁사·사이드바·북마크·알림·관련기사 링크 전부
```

**⛔ 상단 네비 탭(`DashboardHeader`의 `NAV_TABS`)은 prefetch를 유지할 것.**
**5개뿐이고 이동이 잦다.** 여기서는 prefetch가 이득이다. **prefetch를 전부 끄는 게 목적이 아니다.**

> **원칙: 목록에 N개씩 깔리는 링크는 prefetch 끄고, 개수가 고정된 네비게이션은 켠다.**

### 3-2. ⭐ 상세 페이지 — 무거운 조회를 `<Suspense>` 밖으로

`src/app/dashboard/contents/[id]/page.tsx`가 렌더 전에 **전부 기다리는 것**:
- `getContentCitations` (313 역참조 — **4종 조회**)
- `getRelatedGrouped` · `getRelatedYoutube` (관련 콘텐츠)
- 관련 엔티티 조회

→ **`ContentSupplementSections`로 분리해 `<Suspense fallback={null}>` 아래로.**
- **본문이 먼저 뜬다.** 사용자는 기사를 읽으러 왔다.
- prefetch도 그걸 안 기다린다 → **prefetch 비용이 줄어든다**(3-1과 함께 작동).
- ⛔ `force-dynamic`은 **유지**한다.

### 3-3. 남은 항목 — **실측 후에 결정한다**

**⛔ 3-1·3-2를 배포하고 숫자를 본 뒤에 착수할 것. 지금 하지 말 것.**

### 3-4. `count: 'exact'` — 데이터가 커지면 가장 먼저 터진다

`src/app/dashboard/contents/page.tsx`의 `buildQuery()`:
```ts
.select(selectParts.join(', '), { count: 'exact' })   // ← 매 페이지마다
```
**"더 보기"로 20건을 받을 때마다 조건에 맞는 행을 전부 다시 센다.**

→ **첫 페이지에서만 count를 요청한다.**
- `total`은 첫 페이지 값을 유지. **필터·정렬·렌즈가 바뀌면 page가 1로 리셋**되므로(297·309) 자동으로 다시 센다.
- ⚠️ **`hasMore`(`items.length < total`)가 깨지지 않게 할 것.**
- ⛔ **`count: 'estimated'`를 쓰지 말 것.** 필터가 걸리면 *"총 3,000건"* 이라 해놓고 200건만 나온다.

**4,538건에선 수십 ms지만 B-6(과거 백필) 이후 10만 건이면 치명적이다.**

### 3-5. `313-역참조-인덱스.sql` — **수희 대기**
