## 0. 배경과 범위

**이 지시서는 기존 `daily-brief.ts` 를 고친다. 새 크론·새 발송 경로를 만들지 마라 — 메일이 두 통 나간다.**

## A. 오답 2건 (2026-07-29 발송분에서 실증)

### A-1. 「작업 실패 324건」 → 실제로는 그날 실행된 전체 작업 수
```
src/lib/ops/daily-brief.ts:38     .neq('status', 'success')
src/lib/ops/weekly-report.ts:40   .neq('status', 'success')
```
`job_runs.status` CHECK 허용값은 **`running | succeeded | failed | skipped`** — **`'success'` 는 없는 값**이라 `neq` 가 모든 행에 매치된다.
→ **`.eq('status', 'failed')`** 로 교체. `skipped` 는 실패가 아니다(`status-style.ts` 주석). **일일·주간 양쪽 다.**

### A-2. 「최고 매체 비중 5%」 → 집계 왜곡
```
src/lib/ops/daily-brief.ts:43  … .limit(10000)
```
30일치를 앱으로 끌어와 세는데 **1만 행에서 잘린다**(654건/일 × 30일 ≈ 2만). 경고 임계가 70% 라 **구조적으로 발동하지 않는다.**
→ **DB 집계로 교체**(RPC 신설 또는 기존 뷰 활용, **테이블 스키마 변경 금지**). 상위 매체 **이름**도 함께 표기 — 지금은 비중 숫자만 있어 어느 매체인지 모른다.

## B. 누락 3섹션 — 데이터는 이미 있다

### B-1. 발행 현황 ⭐ 최우선
**리포트·뉴스레터가 몇 건 나갔고 실패했는지가 메일에 한 줄도 없다.** 운영리포트에서 가장 중요한 지표다. 전일(KST) 기준:
- `ai_reports` — `published_at` 전일 범위 건수, `status='failed'`
- `briefings` — `briefing_date` 전일, `status`, `error_reason` 있는 건
- `competitor_weekly_reports` — 해당 주 `status`
- `daily_insights` — `day_of` 전일 건수, `needs_review=true`
- `newsletter_recipients` — 전일 `status` 분포(`sent`/`failed`/`delivered`/`bounced`)와 성공률

**실패·미발행은 상단 "오늘 반드시 확인"으로 올린다.**

### B-2. cron 상태
`src/lib/jobs/expected-crons.ts` 가 `vercel.json` 을 직접 import 해 `EXPECTED_CRONS` + `maxAgeHours` 로 `ok`/`stale`/`missing` 3단 판정을 한다(빌드 가드까지 있다). **`/admin/job-runs` 전용이고 메일에 연결만 안 돼 있다.**
→ 재사용해 **`정상 N / 주의 N / 미실행 N`** 요약 + 주의·미실행 건만 상세.

> ⚠️ **Vercel Hobby 제약 — 반드시 반영.**
> Hobby 는 크론이 **하루 1회만** 허용되고 **실행 시각이 ±59분 부정확**하다(`0 1 * * *` → 1:00~1:59 임의 실행).
> → **"예정 시각 대비 N분 지연"을 이상징후로 판정하지 마라.** 오탐이 쏟아진다. 판정은 **`maxAgeHours`(미실행) 기준만.**
> → 05:00 크롤 → 05:20 요약백필처럼 **20분 간격 크론은 순서가 뒤집힐 수 있다.** "선행 크론 미완료"를 실패로 단정하지 말 것.

### B-3. 검토대기 사유 분해
현재 `pending 7779건` 이 **맨 숫자 하나**다. 470 이 `review_reason` 7종(`body_missing`·`body_short`·`body_truncated`·`extract_failed`·`low_relevance`·`llm_irrelevant`·`excluded_rule`) 필터를 배포했으므로 분해 가능.

## D. HTML 리디자인 — 가시성·가독성

현재 `buildDailyBriefHtml()` 은 한 줄 템플릿 리터럴에 `<body>` 인라인 스타일 1개가 전부다. **전면 재작성한다.**

### D-1. 구조 (위에서 아래로 읽으면 판단이 끝나야 한다)
```
헤더    제목 · 집계 기간 · 생성 시각 · 전체 상태 배지
①      오늘 반드시 확인      (없으면 "주요 시스템 정상" 한 줄)
②      요약 카드 6~8개
③      발행 현황            (B-1)
④      수집·콘텐츠 건강      (검토대기 사유 분해 포함)
⑤      사용자
⑥      AI·외부 사용량        (토큰·소진율. 금액 없음)
⑦      cron 상태            (B-2)
⑧      조치 필요 항목 + 어드민 딥링크
```

### D-2. 이메일 HTML 제약 (반드시 지킬 것)
- **테이블 기반 레이아웃**, 최대 폭 **640px**, 모바일 단일 컬럼
- **인라인 CSS만.** 외부 CSS·JavaScript·Canvas·flex/grid 의존 금지
- 다크모드에서 글자가 사라지지 않게 **배경·글자색을 함께** 지정(현재 `color:#202124` 만 있어 다크모드에서 깨진다)
- 이미지 없이도 완전히 읽혀야 한다

### D-3. 요약 카드
`전체 상태 · 수집 · 게시 · 검토대기 · 발행 · 실패 작업 · 신규 가입 · 최고 매체 비중` 중 6~8개. 각 카드에 **값 + 비교값 + 상태색**.

### D-4. 상태 색 4단
```
normal      회색/기본
warning     주황   [주의]
critical    적색   [긴급]
unavailable 옅은 회색 — "데이터를 불러오지 못했습니다"
```
⚠️ **`unavailable` 을 0 으로 표시하지 마라.** 조회 실패와 실제 0건은 다르다.
⚠️ 지금은 **gemini 한도 100% 초과가 sambanova 7% 와 같은 불릿·같은 굵기**다. 임계 초과 항목은 색·굵기·`[긴급]` 표기로 구분되어야 한다.

### D-5. 메일 제목
```
[인사이트 아웃 운영리포트] 7월 29일 정상 · 발행 12건 · 신규 가입 8명
[주의][인사이트 아웃 운영리포트] 기사 수집 감소 · 번역 사용량 68% 증가
[위험][인사이트 아웃 운영리포트] 모닝브리핑 발행 실패 · cron 2건 미실행
```
최상위 심각도 접두 + **가장 중요한 정보 2개 이내.**

### D-6. 헤더 표기
`집계 기간: 2026.07.29 00:00~23:59 KST · 생성: 2026.07.30 08:00 KST`
⚠️ 현재 `dayStart()`(`daily-brief.ts:22`)는 **서버 로컬 기준**이다. Vercel 은 UTC 로 돌아 **지금 집계 범위가 KST 전일이 아닐 가능성이 크다.** **KST 로 고정**하고 표기와 실제 범위를 일치시킨다.

### D-7. 부분 실패에도 발송은 계속
한 영역 조회가 실패해도 **메일 전체 발송을 중단하지 마라.** 그 영역만 `unavailable` 로 표기한다.
