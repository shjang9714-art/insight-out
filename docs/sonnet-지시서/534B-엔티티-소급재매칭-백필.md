## 0. 실측 (재조사 금지)

534-A 로 앞으로 들어오는 콘텐츠는 정상 링크된다. **08-17~08-21 나흘치가 비어 있다.**

```
08-17 이후 콘텐츠            2,589건
  이미 링크됨                  359
  백필 대상                  1,924   ← 이번 작업
  matched_keywords 자체가 매칭 안 됨   306
```

**대상 1,924건은 `matched_keywords` 를 이미 갖고 있고 엔티티 링크만 없다.**
키워드 매칭은 정상이었고 엔티티 맵만 비어 있었다는 뜻이다 — LLM 재분류가 필요 없다.
`matched_keywords` 를 새 맵(`loadEntityAliasMap`, 120개)에 다시 통과시키기만 하면 된다.

## 작업

### 1) `src/lib/entities/relink-backfill.ts` (신규)

```ts
export async function drainEntityRelink(
  admin: SupabaseClient,
  opts: { limit: number; from?: string | null; to?: string | null }
): Promise<EnrichJobResult & { batchCapped: boolean }>
```

- `loadEntityAliasMap(admin)` 로 맵을 **한 번** 읽는다. 맵이 비면 즉시 중단하고
  그 사실을 결과에 담는다(조용히 0건 처리로 끝내지 말 것).
- 대상 조회: `contents` 에서 `deleted_at is null`, `matched_keywords` 비어 있지 않음,
  `collected_at` 이 from~to 범위. **`.limit(opts.limit)`** 로 배치.
- ⚠️ **이미 링크된 콘텐츠를 거른다.** PostgREST 에 `NOT EXISTS` 가 없으므로,
  배치의 id 목록으로 `content_entities.select('content_id').in('content_id', ids)` 를 한 번 조회해
  집합으로 빼낸다. `content_entities` 전체를 읽지 말 것(48,507행).
- 각 콘텐츠의 `matched_keywords` 를 `aliasMap.get(kw.toLowerCase())` 로 매핑해
  `content_entities` 에 `upsert(..., { onConflict: 'content_id,entity_id', ignoreDuplicates: true })`,
  `source: 'rule'`, `score: 1.0`. **크롤러와 같은 형태로 쓴다.**
- ⚠️ **`contents` 를 UPDATE 하지 않는다.** `content_entities` insert 만 한다.
  `contents` 에는 `WHEN` 절 없는 `BEFORE UPDATE` 트리거가 있어 대량 UPDATE 는 위험하다.
  이 작업은 그 트리거를 건드릴 이유가 없다.

### 2) 결과를 정직하게 반환한다

```ts
{ processed, succeeded, skipped, remaining, batchCapped }
```

- `processed` = 이번 배치에서 실제로 본 콘텐츠 수
- `succeeded` = 링크가 1건 이상 생긴 콘텐츠 수
- `skipped` = 이미 링크돼 있거나 매칭 0건이라 건너뛴 수
- `remaining` = **서버 집계**(`count:'exact', head:true`)로 남은 대상 수.
  전체 행을 select 해서 세지 말 것(PostgREST 1000행 상한).
- `batchCapped` = `processed >= limit`.
  ⚠️ **이 필드가 없으면 "500건 처리 성공"이 "다 끝났다"로 읽힌다.**
  이 코드베이스에서 열한 번 반복된 패턴이다.
- upsert 실패는 삼키지 말고 결과에 사유를 남긴다. `catch { return 0 }` 금지.

### 3) 라우트 — `src/app/api/admin/entity-relink/route.ts` (신규)

`src/app/api/admin/cluster-backfill/route.ts` 를 골격 그대로 따른다.
`verifyAdminRequest()` → `runJob(admin, { key: 'admin:entity-relink', trigger: 'admin',
startedBy: gate.userId }, …, { rejectIfRunning: true })` → `JobAlreadyRunningError` 는 409.
`maxDuration = 300`. `limit` 기본 200, 상한 500. `from`/`to` 쿼리 지원.

### 4) `enrich-jobs.ts` 등록

`EnrichJobKey` 에 `'admin:entity-relink'` 를 추가하고 메타를 넣는다:

```ts
{ key: 'admin:entity-relink', label: '엔티티 다시 연결', endpoint: '/api/admin/entity-relink',
  usesLlm: false, surface: 'data', kind: 'loop', method: 'POST', limit: 200, dateRange: true }
```

`surface: 'data'` 라 532 로 옮긴 **소스 관리 > 데이터 보강 재처리** 탭에 뜬다.
LLM 을 쓰지 않으므로 `usesLlm: false` 가 맞다.

## 하지 않을 것

- 크론 등록 — **수동 실행만.** pg_cron·vercel.json 둘 다 건드리지 않는다
- `contents` UPDATE, `matched_keywords` 재계산, LLM 재분류
- 크롤러 링킹 경로 변경(534-A 로 끝났다)
- 08-17 이전 데이터 손대기 — 그쪽은 이미 링크돼 있다
- `content_entities` 기존 행 삭제

## 검증

1. `npx tsc --noEmit` / `npx eslint`(경고 0건) / `npm run build`
2. **`limit=5` 같은 작은 값으로 먼저 돌려** 결과 형태를 확인한다
   — `processed`·`succeeded`·`skipped`·`remaining`·`batchCapped` 다섯 값이 다 나오는지
3. `batchCapped: true` 가 실제로 나오는 케이스를 만들어 확인할 것(대상이 limit 보다 많으므로 쉽다)
4. 같은 배치를 두 번 돌렸을 때 두 번째는 `skipped` 로 빠지는지(멱등)
5. `content_entities` 에 `source='rule'` 로 들어가는지, 중복 행이 안 생기는지
6. 실행 중 다시 누르면 **409** 가 뜨는지
