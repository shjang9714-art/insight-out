# 지시서 470 — 검토대기 적체 해소(사유별 필터 + 조건 기반 일괄 반려)

**SQL 0 · env 0 · 의존성 0.** 브랜치 `agent/470-review-queue-drain`.

## 배경
검토대기가 **7,730건**. 원인은 고장이 아니다 — 네이버 유입(0건 → 694건/일)이 시작되면서 관련도 게이트(`quality.ts` `RELATEDNESS_THRESHOLD = 0.3`)에 걸린 기사가 대량 `pending`으로 쌓인 결과다.
현재 일괄 처리는 `selectedIds` → `.in('id', ids)`로 **현재 페이지(최대 100건) 기준**이라 7,730건에 무력하다.
**이 지시서는 해소 수단만 만든다. 게이트 임계 조정은 매체 다양성과 한 손잡이라 별건(결정 대기).**

## 변경

### 1. 사유별 필터 + 건수 요약
`AdminContentManager`에 `review_reason` 필터 추가. 값은 `quality.ts`의 `ReviewReason` **7종을 그대로 사용**(새 라벨 체계 정의 금지):
`body_missing` · `body_short` · `extract_failed` · `body_truncated` · `low_relevance` · `llm_irrelevant` · `excluded_rule`
- 기존 필터(`category`·`sourceId`·`status`·`bodyFilter` 등)와 **동일한 방식**으로 조회 쿼리에 합류. URL 쿼리 동기화도 기존 패턴 따름.
- 상단에 **사유별 건수 요약**(어느 사유가 적체를 만드는지 보여야 판단이 된다). `head:true` count 조회.

### 2. 조건 기반 일괄 반려 API (핵심)
**신규 `POST /api/admin/contents/bulk-review`** — 기존 `body-backfill/by-ids` 라우트의 admin 검증 패턴 재사용.
- body: **현재 필터 조건**(category·sourceId·reviewReason·bodyFilter·todayOnly·searchTerm) + `action: 'reject'` + `expectedCount`
- 서버가 **같은 조건으로 직접 update** — id 배열을 주고받지 않는다.
- `runJob(admin, { key: 'admin:bulk-review', trigger: 'admin', startedBy }, …)`로 감싼다. 되돌리기 어려운 대량 작업은 `job_runs`에 흔적이 남아야 한다(운영철학).

**안전장치 — 전부 필수**
1. **`action`은 `reject`만.** `delete`·`publish`는 이 경로에서 **금지**. 반려는 status 되돌리기가 가능하지만 삭제는 불가능하다. 7,730건 오삭제는 복구 수단이 없다.
2. **필터 최소 1개 필수.** 조건이 전부 비면(=전체 대상) **400 거부**.
3. **`expectedCount` 일치 검사.** 클라이언트가 미리보기에서 본 건수를 함께 보내고, 서버가 실제 count와 비교해 다르면 **409 거부**(그 사이 유입된 신규 건이 휩쓸리는 것 방지).
4. **상한 10,000건.** 초과 시 400 거부.
5. `status = 'pending'` 인 행만 대상(이미 published/rejected는 건드리지 않는다).

### 3. UI 흐름
`대상 건수 미리보기` → 사유·건수를 명시한 확인 대화상자 → 실행 → 결과(처리 건수) 표시.
기존 페이지 단위 `selectedIds` 일괄 처리는 **그대로 유지**(소량 작업엔 그게 낫다). 조건 기반은 별도 액션으로 추가한다.
