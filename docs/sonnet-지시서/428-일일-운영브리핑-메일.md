## 1. 착수 전 확인 (재사용 자산)
- **집계 소스(이미 존재, admin/page.tsx 패턴)**: `contents`(총·오늘·pending/published/rejected·카테고리별·소스편중 source_id 30일), `sources`(활성/총), `crawl_logs`(오늘 failed/partial·어제 실패 소스), `users`(총·승인대기), `llm_usage`·`translation_usage`·`tts_usage`(period=월), 본문보강 백로그(`body_fetched_at IS NULL`), `job_runs`(크론 성공/실패).
- **발송**: `src/lib/email/brevo.ts` `sendBrevoEmail({ to, subject, html })`(HTML). `BREVO_FROM_EMAIL` 환경변수.
- **사용량 한도**: 417의 `getProviderKeyCount` × `monthly_token_limit` = provider별 실효 한도. `TTS_MONTHLY_CHAR_CAP` env.
- ⚠️ **피드백 시스템·운영이슈 fingerprint 는 아직 없음** → 이번 브리핑에서 **생략**(§6 후속). v1은 시스템·수집·사용량·사용자.

## 2. 구현

### 2.1 집계 lib `src/lib/ops/daily-brief.ts`
- `gatherDailyBrief(admin): Promise<DailyBrief>` — admin client(service_role)로 아래 집계(admin/page.tsx 쿼리 재사용/이식):
  - **시스템 건강도**: 오늘 crawl_logs failed/partial 수, 본문보강 대기(`body_fetched_at IS NULL`) 수, 최근 실패 job_runs(status!='success' & 오늘) 목록, 활성 소스 중 24h 기사 0건 수(가능하면).
  - **수집·게시**: 오늘 수집·published·rejected, pending 적체, **단일 매체 최고 비중**(source_id 30일 집계 → top1 %), 활성/게시 소스 수.
  - **사용량·한도**: provider별 used/실효한도(키개수×) %, 번역·TTS chars vs cap, **소진 예상일**(추세: 잔여/일평균) — 95%+ 는 긴급.
  - **사용자**: 총 가입, 오늘 신규, 승인 대기, (가능하면 last_seen_at 기반 7일 미접속).
- **심각도 판정**: 각 지표 임계값 → `critical|warning|notice`. 예: 오늘 수집 0건·사용량≥95%·수집 전면 실패 = critical; 보강 24h+ 적체 많음·사용량≥80%·일부 소스 0건 = warning.

### 2.2 HTML 빌더 `buildDailyBriefHtml(brief): string`
- 통합개선안 §14 구성: ① 오늘 반드시 확인(긴급·주의 나열) ② 시스템 건강도(정상/주의/긴급 배지) ③ 사용자 현황 ④ 수집·본문보강 ⑤ AI·외부 사용량(+소진 예상) ⑥ (전날 해결분은 데이터 없으면 생략).
- **운영 언어로**(§8.1): 기술 로그 그대로 X. 예 "본문 보강 지연 — 24h+ 대기 N건, 추정: 원문 서버 지연, 권장: 실패 로그 확인".
- 하단에 어드민 바로가기 링크(운영 대시보드·수집 건강도 등, 절대 URL).

### 2.3 크론 엔드포인트 `src/app/api/cron/ops-brief/route.ts`
- GET, `Authorization: Bearer CRON_SECRET` 인증(기존 크론 패턴). `runtime='nodejs'`, `maxDuration=60`, `dynamic='force-dynamic'`.
- `gatherDailyBrief` → `buildDailyBriefHtml` → 수신자에게 `sendBrevoEmail`.
- **수신자**: `users` 에서 `role='admin'` 이메일 목록(+ env `OPS_BRIEF_RECIPIENTS` 콤마 override 있으면 우선). 없으면 스킵/로그.
- **제목**: 문제 있으면 `[인사이트 아웃 운영 브리핑] 긴급 N · 주의 M · YYYY년 M월 D일`, 정상이면 `[인사이트 아웃 운영 브리핑] 주요 시스템 정상 · YYYY년 M월 D일`.
- `runJob`(기존)으로 감싸 실행 기록. 실패해도 500 반환(다음날 재시도).

### 2.4 스케줄 `vercel.json`
- 크론 추가: `{ "path": "/api/cron/ops-brief", "schedule": "0 23 * * *" }` (UTC 23:00 = KST 08:00).
- ⚠️ **하루 1회**(Hobby 준수 — 402 교훈). ⚠️ 배포 시 **크론 개수 상한**에 안 걸리는지 확인(현재 12개 동작 중이라 대개 OK, 실패하면 pg_cron(수희)로 대체 — §6).

## 3. 하지 말 것
- **새 테이블·SQL 금지**(전부 읽기). 스키마 변경 없음.
- 크론 스케줄 **하루 1회 초과 금지**(Hobby).
- 없는 데이터(피드백·운영이슈 fingerprint) 억지 표기 금지 — v1에서 생략.
- 기존 크론·발송·집계 로직 무수정(브리핑은 별도 경로).
- 개인정보(개별 사용자 이메일 나열 등) 메일 본문에 넣지 않기 — 집계·수치 위주(§10 원칙).

## 4. 회귀 가드
1. 크론 수동 호출(Bearer) → 관리자에게 브리핑 메일 발송.
2. 문제 없을 때 제목 "주요 시스템 정상", 있을 때 "긴급 N · 주의 M".
3. 시스템 건강도·수집·사용량·사용자 섹션이 실제 수치로 채워짐.
4. 사용량 95%+ 는 긴급으로 잡힘(임계값 동작).
5. 수신자 없으면(관리자 0·env 없음) 안전 스킵(에러 아님).
6. 기존 크론·어드민 무영향.
7. 하루 1회 스케줄, 배포 성공.
