## 1. 판단③ 확인 결과

### `daily-insights/relevance.ts:37` 상위 호출부 확인

`classifyPastArticleCategories(contentIds)` → 유일한 호출부는 `daily-insights/generate.ts:506`의 `buildRelatedPast()`.
`contentIds`는 `members[].pastArticles[].contentId`에서 오고, `pastArticles`는 `key-insights/candidates.ts:321`의 `pastByIssue.get(issueId)`에서 채워진다.
`pastByIssue`는 같은 파일 273행(`admin.from('contents')...in('id', chunk).lt('published_at', windowStart)`) 조회 결과다.

**결론**: 상위 호출부(`candidates.ts:273`)는 A로 분류해 이번에 `.is('deleted_at', null)`을 추가했다(§2 표 참고). 따라서 `relevance.ts:37`에 도달하는 `contentIds`는 이미 살아있는 콘텐츠로 좁혀진 상태이며, 지시서 판정(**C — 필터 불필요**) 그대로 적용했다(코드 변경 없음).

### `reports/generate-strategy` 재특정 결과

`src/app/api/reports/generate-strategy/route.ts:74`는 지시서 말대로 `contents` 조회가 아니라 보고서 유형(`REPORT_TYPES`) 검증 코드였다(직접 읽어 확인).

실제 `from('contents')` 호출은 **`src/lib/reports/generate-strategy.ts:74`**의 `collectContext()` 안에 있다 — 1단계 인벤토리가 원래 짚었던 바로 그 지점이다(`.select('title, summary_ko').in('id', contentIds)`, 사용자가 명시 선택한 근거 콘텐츠 조회). 애매한 지점이라 지시서 기본값(A)을 적용해 `.is('deleted_at', null)`을 추가했다.

## 3. 판단② — `dedup.ts` 정정 (인벤토리 뒤집음)

`src/lib/crawler/dedup.ts` 상단에 근거 주석을 남기고, `findByUrl`·`findByTitleHash`·`findByBodyHash` 3곳은 **의도적으로 필터를 추가하지 않았다**(B — 삭제분도 "이미 있음"으로 잡아야 재수집 무한반복을 막는다). `findSimilarCandidates`·`findSimilarCandidatesWithBody`(near-dup 클러스터 후보, 2곳)는 A로 유지해 `.is('deleted_at', null)`을 추가했다(삭제된 행이 클러스터 대표가 되면 안 되므로).

## 4. 작업 요약

- **A분류 필터 추가**: 서비스롤 72곳(1단계 76 A 중 `dedup.ts` B전환 3 + `relevance.ts` C 확정 1 제외) + 어드민 RLS 34곳(§2) = **106곳**에 `.is('deleted_at', null)` 추가. B·C는 손대지 않음.
- **`dedup.ts`**: 3곳 B 전환 + 근거 주석(§3).
- **삭제 경로 소프트 삭제 전환**: `src/app/api/admin/contents/delete/route.ts` — 하드 `delete()` → `update({ deleted_at: now(), deleted_by: userId }).is('deleted_at', null)`(이미 삭제된 행 재마킹 방지). 감사 로그 action `content.delete` → `content.soft_delete`(3곳 전부), payload 키를 `bookmarkCascadeCount`/`archiveItemCascadeCount` → `bookmarkPreservedCount`/`archiveItemPreservedCount`로 변경.
- **491 확인창 문구**: `AdminContentManager.tsx`의 단건/일괄 삭제 확인창에 "휴지통으로 이동합니다. 연결된 북마크·아카이브 항목은 보존됩니다." 설명 추가, 일괄삭제 `countLabel`을 "함께 삭제되는 북마크·아카이브" → "보존되는 북마크·아카이브"로 변경.
- **`get_recommended_feed` 수정 SQL**: `docs/sql-handoff/492-C-recommended-feed.sql` 생성(적용은 David). 1단계 문서의 원본 함수 본문을 그대로 두고 4개 분기의 `c.status = 'published'` 뒤에 `and c.deleted_at is null`만 추가 — 그 외 로직 무변경.
- **범위 밖 준수**: 휴지통 화면(3단계) · `purge` 라우트 · RLS 정책 · CASCADE · SQL A/B 임의생성 — 전부 손대지 않음.

## 5. 검증

1. **콘텐츠 삭제 시 CASCADE 미발화**: `delete()` → `update()`로 바뀌어 `contents` 행 자체가 지워지지 않으므로 `bookmarks`·`archive_items` FK CASCADE가 발화하지 않는다(코드 검토로 확인 — 실제 DB 조작 테스트는 배포 후 David 확인 필요).
2. **어드민 목록·운영 대시보드에서 삭제분 비노출**: `AdminContentManager.tsx` 메인 목록(739)·`admin/page.tsx` 전 집계(25곳)에 필터 추가 확인.
3. **재수집 시 중복 판정 유지**: `dedup.ts`의 `findByUrl`/`findByTitleHash`/`findByBodyHash`는 필터 없이 그대로 둬서, 삭제된 URL/제목/본문과 일치하면 여전히 "중복"으로 판정되어 재적재되지 않는다.
4. **`grep -rn "from('contents')" src` 중 A분류 지점 필터 존재**: 서비스롤 72곳 + 어드민 RLS 34곳 전수 addEdit 완료(§2·§4). `npx eslint`·`npx tsc --noEmit` 통과로 문법·타입 오류 없음을 재확인.
5. **감사 로그 `content.soft_delete` + "보존됨" 문구**: `delete/route.ts` 3개 completeAudit 호출 전부 `content.soft_delete`로 변경, payload 키 `*PreservedCount`로 변경, `AdminContentManager.tsx` 확인창 문구 변경 완료.
6. **`npm run lint` · `npx tsc --noEmit` · `npm run check:admin-auth` 통과**: 세 검사 모두 통과(신규 오류 0건 — 사전에 존재하던 `gdelt-bigquery.ts`/`@google-cloud/bigquery` 타입 에러는 이번 변경과 무관하며 main에도 동일하게 존재).
