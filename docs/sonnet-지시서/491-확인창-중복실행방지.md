## A. `AdminConfirm` — 공용 확인창 (G-16)

`AdminDataReset.tsx`의 2단계 패턴(`Phase = 'idle'|'confirming'|'working'` + 대상 건수 선조회 + `confirmLabel(count)`)을 **승격**한다. **새로 설계하지 마라.**

### A-1. 형태 — 명령형 훅 + 단일 호스트
33개 호출부의 diff를 최소화하기 위해 명령형 API로 만든다.

```ts
// src/components/admin/ui/AdminConfirm.tsx
const confirm = useAdminConfirm()

if (!(await confirm({
  title: '콘텐츠 삭제',
  description: '되돌릴 수 없습니다.',
  targets: ['제목 A', '제목 B', …],     // 최대 10개 표시 + "외 N건"
  loadCount: async () => number,        // 있으면 선조회 후 문구에 반영
  confirmLabel: '삭제',
  destructive: true,
}))) return
```

- `<AdminConfirmHost />`를 **`src/app/admin/layout.tsx`에 1회 마운트**한다. 489에서 이 파일에 서버 게이팅이 들어갔으므로 **인증 로직을 건드리지 말고 트리 안쪽에만 추가**하라.
- 기존 호출부 변환은 기계적이다: `if (!window.confirm(x)) return` → `if (!(await confirm({...}))) return`. 호출 함수가 이미 `async`가 아니면 `async`로 바꾼다.

### A-2. 필수 요구
- **대상 목록을 보여준다.** 지금 일괄 삭제는 건수만 알려주고 무엇이 지워지는지 말하지 않는다.
- **연쇄 삭제 건수를 함께 보여준다.** `contents` 삭제는 `bookmarks`·`archive_items` 등 **10개 테이블이 `ON DELETE CASCADE`로 딸려 삭제된다.** 콘텐츠 건수만 보여주면 실제 피해 규모를 숨기는 것이다. 486이 감사 로그에 이미 이 두 건수를 세고 있으니 **같은 조회를 확인창에서도 쓴다.**
- **확인 → 실행 중 → 성공/실패** 상태를 제공한다. 실행 중에는 확인 버튼을 잠근다.
- 성공은 토스트(488 규칙), 실패는 `AdminErrorBox` 인라인.

### A-3. `alert()` 제거
`NewsletterSendPanel.tsx:19` — 미리보기 실패를 `alert`로 띄운다. 같은 컴포넌트가 발송 결과는 인라인으로 보여주는 내부 불일치다. → `AdminErrorBox`로 교체.

## B. `runJob` 중복 실행 방지 (G-17)

### B-1. `src/lib/jobs/run-job.ts`
```ts
runJob(admin, ctx, fn, opts?: { rejectIfRunning?: boolean })
```
- `rejectIfRunning: true`이면 `reapStaleRunningJobs` 직후 같은 `job_key`의 `status='running'` 행을 조회해, 있으면 **`fn()`을 실행하지 않고** `JobAlreadyRunningError`(신설, `startedAt` 포함)를 던진다.
- **기본값은 `false`.** 15개 크론 라우트의 동작을 바꾸지 않는다 — 크론 중복 방지는 별건이다.
- 조회 실패(42P01 등)는 **삼키고 통과**시킨다. 가드 때문에 잡이 안 도는 게 더 나쁘다.

### B-2. 어드민 라우트 12곳
`runJob`을 쓰는 어드민 라우트 전부에 `rejectIfRunning: true`를 준다.
`body-backfill` · `canonical-backfill` · `cluster-backfill` · `competitor-weekly` · `contents/bulk-review` · `lgu-impact` · `pdf-cover-backfill` · `sentiment` · `signals-backfill` · `summary-backfill` · `thumbnail-backfill` · `translate-backfill`

`JobAlreadyRunningError`를 잡아 **HTTP 409**로 응답한다.
```json
{ "error": "이미 실행 중입니다. (시작: 2026-08-01 14:03)" }
```

### B-3. `crawl-now`
`runJob`을 쓰지 않는다. **`runJob`으로 감싸고**(`key: 'admin:crawl-now'`, `trigger: 'admin'`, `startedBy`) `rejectIfRunning: true`를 준다.
→ 이렇게 하면 `G-10`(494의 소스 재수집 실행 상태 표시)이 **같은 장치로 풀린다.** 494에서 별도 락을 만들지 마라.

## C. purge — 확인 토큰 (G-17)

`contents/purge` · `youtube/purge`는 `runJob`을 쓰지 않고 POST 한 번에 전량 삭제한다.

1. **`runJob`으로 감싼다**(`key: 'admin:purge:<대상>'`) + `rejectIfRunning: true`.
2. **`expectedCount`를 요구한다.** 클라이언트가 확인창에서 본 건수를 body에 실어 보내고, 서버가 삭제 직전에 다시 세서 **다르면 409로 거부**한다.
   ```json
   { "error": "대상 건수가 변경되었습니다(확인 시 1,204건 → 현재 1,207건). 다시 확인해주세요." }
   ```
   → HMAC·서명 토큰을 만들지 마라. 건수 대조만으로 "내가 본 것과 지우는 것이 같다"가 보장된다.
3. 거부(409·건수 불일치)도 **486의 `completeAudit`으로 `outcome='failed'`** + 사유를 남긴다.

## 검증

1. `grep -rn "window.confirm\|[^.]confirm(\|alert(" src/components/admin src/app/admin` → **0건**(주석 제외).
2. 콘텐츠 일괄 삭제 확인창에 **대상 제목 목록**과 **북마크·아카이브 연쇄 건수**가 보인다.
3. 확인창이 실행 중 확인 버튼을 잠그고, 성공은 토스트·실패는 인라인으로 나뉜다.
4. `body-backfill`을 동시에 두 번 호출하면 두 번째가 **409**를 받고 시작 시각이 문구에 있다.
5. `crawl-now`도 동일하게 409를 받는다.
6. purge에서 `expectedCount`를 일부러 틀리게 보내면 **409 + 건수 차이 문구**가 나오고 삭제되지 않는다.
7. 4~6의 거부가 `admin_audit_log`에 `outcome='failed'`로 남는다.
8. 크론 15곳의 동작이 바뀌지 않았다(코드상 `rejectIfRunning` 미지정 확인).
9. `npm run lint` · `npx tsc --noEmit` · `npm run check:admin-auth` · `npm run build` 통과.
