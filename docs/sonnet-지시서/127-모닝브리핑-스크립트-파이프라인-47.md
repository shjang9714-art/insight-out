## 배경·목표

데이터 계약상 **수희 트랙(#47)** = 매일 당일 기사를 선정해 LLM 으로 브리핑 스크립트를 만들고 `briefings` 에 `status='draft'` 로 적재하는 것이다. 현재 `briefings` 에는 스키마 시드 샘플 1건뿐이라 실데이터 파이프라인이 빠져 있다. 이 빈칸이 채워져야 TTS→플레이어 흐름이 실제로 돈다.

### 컨셉 (반드시 준수)
- **형태**: 1인 진행 팟캐스트/라디오. 뉴스 티커가 아니라 한 명의 진행자가 친근하게 풀어 주는 **3~5분 분량**의 모닝 라디오.
- **분량·건수**: 매일 **3~5건**의 기사를 묶어 **3~5분**(약 1,200~2,000자) 낭독.
- **선정 기준**: **통신·테크·AI 산업 전반**을 아우르는 핵심 콘텐츠. 특정 회사 동향이 아니라 **모든 임직원이 두루 알아야 할 산업 전반의 흐름**이 기준이다.
- **⚠️ B2B 한정**: 통신 영역은 **B2B(기업·엔터프라이즈) 산업 관점**만 다룬다. **B2C(요금제·단말·가입자 프로모션·소비자 마케팅 등 일반 소비자向)는 제외.** 테크·AI 도 가능하면 엔터프라이즈/B2B 활용 맥락 우선. 기존 `feed-blocklist`(홈 피드 B2B 무관 필터)와 동일 기준으로 후보에서 걸러낸다.
- **KA(주요 고객사)·경쟁사 개별 동향 가중은 이번 범위에서 제외**(KA 적용은 아주 나중). 회사 단위가 아니라 산업 주제(통신/테크/AI) 단위로 고른다.

목표는 세 가지다.
1. **기사 선정** — 최근 24시간 게시 콘텐츠 중 복합 점수로 3~5건을, **통신·테크·AI 주제 균형**과 중복 제거를 고려해 고른다.
2. **스크립트 생성** — 선정 기사 요약을 입력해 LLM 으로 TTS 친화적인 1인 팟캐스트 스크립트(3~5분)를 만든다.
3. **적재·트리거** — `briefings` 에 `draft` 로 upsert 하고, Cron(매일 자동) + admin(수동) 두 경로로 실행한다.

비용·안정성 원칙은 기존과 동일하다. LLM 호출은 `llmComplete` 의 사용량·캡 라우팅을 그대로 타고, 실패는 결정적으로(`status='failed'`) 처리해 다음 단계가 빈 스크립트로 진행하지 않게 한다.

## 파트 A — 기사 선정 복합 점수

### A-1. 후보 풀
- `contents` 에서 다음 조건으로 조회(service_role):
  - `status = 'published'`
  - 게시 윈도우: **최근 24시간** — 기준은 `published_at`, null 이면 `collected_at` 폴백. 윈도우 경계는 KST 기준 "어제 브리핑 시각 ~ 지금"(Cron 06:00 KST 가정 시 직전 24h). 환경변수 `BRIEFING_WINDOW_HOURS`(기본 24)로 조정 가능.
  - `category != '유튜브'` 권장(오디오 브리핑에 영상 카드 부적합 — 단 요약이 있으면 포함 허용, 팀 판단. 기본은 제외).
- **B2B 무관 필터 재사용(필수)**: `feed-blocklist` 의 제외 기준을 후보에서 동일 적용(홈 피드와 일관). 클라 전용 모듈이면 동일 판정 로직을 서버에서 재사용 가능한 형태로 추출하거나, 키워드 배열만 공유. 중복 구현 금지. **통신 B2C(요금제·단말 출시·가입자 프로모션·소비자 마케팅 등)는 여기서 반드시 걸러져야 함** — feed-blocklist 가 이를 충분히 커버하지 못하면 B2C 시그널 키워드를 보강(상수로 분리, 사유 1줄).
- 조회 컬럼: `id, title, summary_ko, category, importance_score, view_count, bookmark_count, is_editor_pick, cluster_id, matched_groups, published_at`.

### A-2. 복합 점수 공식
각 후보에 대해 `score` 를 계산한다(가중치는 상수로 모듈 상단에 명시, 추후 튜닝 가능하게). **회사(경쟁사·KA) 단위 가중은 넣지 않는다 — 산업 주제 단위로만 평가한다.**

```
score =
    importance_score                       // 베이스: 기존 관련도 점수
  + recencyBonus                           // 최근성: 24h 내 선형 감쇠 (예: (1 - hoursAgo/24) * W_RECENCY)
  + categoryWeight[category]               // 카테고리 가중 (뉴스/리포트/웹인사이트/AI보고서 별 상수)
  + (is_editor_pick ? W_EDITOR : 0)        // 에디터 픽 가산
  + log1p(view_count)   * W_VIEW           // 조회 (로그 스케일)
  + log1p(bookmark_count) * W_BOOKMARK     // 북마크 (로그 스케일)
  + (isCoreIndustry(matched_groups) ? W_INDUSTRY : 0)  // 통신·테크·AI 산업 주제 가산
```

- `isCoreIndustry`: `matched_groups` 에 **통신·테크·AI 산업 주제** 그룹이 포함되면 가산. 주제 그룹명 매핑은 기존 `keyword_groups`(tag_type `industry`/`tech` 등) 기준 재사용 — 하드코딩 키워드 나열 금지. **회사(`company`) 타입 그룹은 가중 제외**(KA·경쟁사 개별 동향은 이번 범위 아님).
- 모든 가중치(`W_*`)와 `categoryWeight` 는 **모듈 상단 상수 객체**로 모아 한눈에 보이게. 임의 매직넘버 금지.

### A-3. 선정 규칙
- 점수 내림차순 정렬 후 상위에서 선정하되:
  - **중복 제거**: `cluster_id` 가 같은 묶음은 대표 1건만(가장 높은 점수). `cluster_id` null 은 단독.
  - **카테고리 편중 방지**: 한 카테고리 최대 `MAX_PER_CATEGORY`건(기본 2). 다양성 확보.
  - **산업 주제 균형**: 가능하면 통신·테크·AI 세 갈래를 고루 담는다. 한 주제가 선정분을 독점하지 않도록(예: 한 주제 최대 절반), 점수 상위라도 주제가 겹치면 다음 후보로 넘겨 균형을 맞춘다. 후보가 한쪽으로 쏠려 있으면 있는 대로(억지 채움 금지).
  - 최종 **3~5건** 선정(환경변수 `BRIEFING_TOP_N`, 기본 4 / 하한 `BRIEFING_MIN_ARTICLES` 기본 3). 후보가 그보다 적으면 있는 만큼.
- 선정 결과: 정렬된 `content` 객체 배열(스크립트 입력) + `source_content_ids`(= 선정 id 배열, `briefings.source_content_ids` 에 저장 → "관련 기사" 링크용).

### B-2. 시스템 프롬프트 (예시 — 그대로 또는 미세조정해 사용)
```
당신은 LG유플러스 임직원을 위한 1인 모닝 라디오 '모닝브리핑'의 진행자다.
입력으로 오늘 선정된 통신·테크·AI 산업 기사 3~5건(제목·요약·카테고리)이 주어진다.
이를 한 명의 진행자가 친근하게 풀어 주는 한국어 팟캐스트 스크립트로 작성하라.

대상·목적:
- 청취자는 LG유플러스 전 임직원. 특정 부서가 아니라 모두가 알아야 할 산업 전반(통신·테크·AI)의 큰 흐름을 쉽게 전달한다.
- 특정 회사 동향 나열이 아니라, 오늘 업계에서 무슨 일이 있었고 왜 중요한지 맥락을 짚어 준다.
- 통신은 B2B(기업·엔터프라이즈) 관점이다. 요금제·단말·소비자 프로모션 같은 B2C 소식은 다루지 않는다.

스타일:
- 1인 진행 팟캐스트 톤. 따뜻하고 자연스러운 구어체로, 청취자에게 말 걸듯 진행한다.
- 구조: ① 짧은 인사·오늘 날짜·오늘 다룰 주제 한두 줄 예고 → ② 기사별 2~4문장 꼭지(중요도 높은 순, 자연스러운 연결어로 이어 가기) → ③ 한 줄 정리·마무리 인사.
- 딱딱한 보도체 금지. 그렇다고 과장·농담 과다도 금지. 차분하고 신뢰감 있는 진행자.

규칙:
- TTS 로 읽힐 글이다. 마크다운·이모지·불릿·따옴표·괄호 메모 금지. 순수 문장만.
- 영어 약어·숫자는 자연스러운 한국어 구어로(예: "AI" 는 "에이아이", "5G" 는 "파이브지"). 단위·금액도 읽기 쉽게.
- 사실만. 입력에 없는 내용 추측·창작 금지. 기사 출처/회사명은 입력대로.
- 전체 분량 1,200~2,000자(약 3~5분 낭독). 문장은 짧고 끊어 읽기 쉽게.
- 출력은 스크립트 본문만. 제목·머리말·설명 없이.
```

### B-3. 유저 프롬프트 구성
- 코드에서 선정 기사들을 다음처럼 직렬화해 전달:
```
오늘 날짜: 2026년 6월 21일

[기사 1] (카테고리: 뉴스)
제목: ...
요약: {summary_ko}

[기사 2] (카테고리: 리포트)
...
```
- `summary_ko` 가 없는 기사는 제목만 전달(또는 후보에서 제외 — 팀 판단, 기본은 제목만이라도 포함). 요약 본문이 길면 기사당 입력 상한(예 400자)으로 자른다.

### B-4. 출력 처리
- `llmComplete('briefing', system, user)` 호출. 반환 텍스트를 trim.
- **출력은 순수 스크립트 텍스트 한 덩어리**(JSON 아님 — TTS 가 그대로 읽음). 모델이 머리말·마크다운을 붙이면 코드에서 가벼운 정리(선행 "스크립트:" 류 라벨 제거) 정도만. 과한 후처리 금지.
- 빈 응답/`null` → 생성 실패로 간주(파트 D 엣지케이스).
- `title` 은 LLM 이 아니라 **코드에서 규칙 생성**: `` `${M}월 ${D}일 모닝브리핑` ``(KST). 시드 샘플과 톤 일치.

## 파트 C — 생성 모듈 `src/lib/briefing/generate-briefing.ts` (`server-only`)

`summarize.ts`·`synthesize-briefing.ts` 구조를 미러한다.

- 상단 `import 'server-only'`. `createAdminClient()`(service_role) 사용.
- 시그니처(예):
  ```ts
  export async function generateBriefing(
    opts?: { force?: boolean; date?: string }   // force=기존 draft 덮어쓰기, date=특정일(테스트용, 기본 오늘 KST)
  ): Promise<
    | { ok: true; briefingId: string; selectedCount: number }
    | { ok: false; reason: string }
  >
  ```
- 절차:
  1. 대상 `briefing_date` 결정(KST 오늘 또는 `opts.date`).
  2. **멱등 가드**: 해당 날짜 `briefings` 조회. `status in ('published','archived')` 면 `{ ok:false, reason:'이미 발행됨' }`(덮어쓰지 않음). `status='draft'|'failed'` 이고 `force` 아니면 `{ ok:false, reason:'이미 생성됨(force 필요)' }`.
  3. 후보 조회·점수·선정(파트 A). 선정 0건 → `{ ok:false, reason:'대상 기사 없음' }`(briefings 미생성 또는 `failed` 기록은 팀 판단 — 기본: 미생성, 로그만).
  4. 선정 `< BRIEFING_MIN_ARTICLES`(기본 3) → 스크립트는 만들되 짧을 수 있음. 0건과 구분만. (하한 미달 시 skip 으로 둘지 옵션화 가능.)
  5. `llmComplete('briefing', …)`(파트 B). 실패 → `briefings` upsert 하되 `status='failed'`, `script=null`, `source_content_ids`=선정분, `generated_at=now()` → `{ ok:false, reason:'스크립트 생성 실패' }`. (어드민이 #49 에서 재생성 트리거 가능.)
  6. 성공 → `briefings` **upsert**(`onConflict: 'briefing_date'`): `title`(코드 규칙), `script`, `source_content_ids`, `status='draft'`, `generated_at=now()`. `audio_url` 등 TTS 필드는 건드리지 않음.
  7. 반환 `{ ok:true, briefingId, selectedCount }`.
- **자동 TTS 호출 안 함.** 흐름은 `draft` → 어드민 검토/승인(#49) → TTS(#50) → published. (선택: env `BRIEFING_AUTO_TTS=true` 면 생성 직후 `synthesizeBriefingAudio` 연계 — 기본 false. 비용·검수 관점 기본 수동.)

## 파트 D — 트리거: Cron + Admin (#48 핸드오프)

### D-1. Cron 라우트 `src/app/api/cron/briefing/route.ts`
- `crawl/route.ts` 정본 미러: `runtime='nodejs'`, `dynamic='force-dynamic'`, `maxDuration=60`.
- 인증: `Authorization: Bearer ${CRON_SECRET}` 검증(동일 패턴). 실패 401.
- `GET` → `generateBriefing()` 호출 → 결과 JSON 반환.
- 쿼리: `?force=1`, `?date=YYYY-MM-DD`(인증된 호출자 디버그용) 허용.

### D-2. `vercel.json` 스케줄
- crons 배열에 추가. **crawl(05:00 KST=`0 20 * * *`) 이후**에 돌아야 당일 기사를 반영하므로 **06:00 KST=`0 21 * * *`** 권장:
  ```json
  { "path": "/api/cron/briefing", "schedule": "0 21 * * *" }
  ```
- (crawl 60초 내 종료 전제. 여유가 필요하면 0 22 * * * = 07:00 KST 로.)

### D-3. Admin 수동 트리거 `src/app/api/admin/briefings/generate/route.ts`
- `[id]/tts/route.ts` 의 `verifyAdmin` 패턴 재사용(`runtime='nodejs'`·`force-dynamic`).
- `POST` → body/query `force` 전달 → `generateBriefing({ force })`. 결과 JSON.
- BriefingManager(#49) 에 "오늘 스크립트 생성" 버튼 연결 지점만 명시(UI 구현은 별도 소규모 작업으로 분리 가능 — 이 지시서 범위 밖, 라우트는 그대로 호출되게 설계).

## 완료 기준 (검증)
