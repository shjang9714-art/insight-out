## 1. 현행 진단 (확인된 코드 사실)

**(a) 이 화면은 icn1 함수를 거치지 않는다.**
`src/app/dashboard/contents/page.tsx` 는 `<Suspense>` 로 감싼 껍데기이고, 실제 목록은 `src/components/contents/ContentsBoard.tsx`(`'use client'`, 654줄)가 **`useEffect` 안에서 브라우저 → Supabase 로 직접** 조회한다(337~410행). 서버가 보내는 HTML 에는 데이터가 0건이다.

```
HTML(빈 껍데기) → JS 번들 → 하이드레이션 → 그제야 쿼리 시작 → 응답 → 렌더
```

7/19 리전 이전이 개선한 구간은 "한국 사용자 → 함수(icn1)" 인데 **이 화면은 그 구간을 타지 않는다.** 다른 화면만큼 빨라지지 않은 것이 정상이다.

**(b) `count: 'exact'` 가 목록과 같은 쿼리에 묶여 있다.** (346·352행)
`shouldFetchCount = page === 1 || total === null` → 첫 진입마다 전체 COUNT. 237 인덱스(`contents_category_published_idx` 등)는 `LIMIT 20` 에는 듣지만 exact count 는 조건 만족 행을 전부 세야 하므로 인덱스로 회피할 수 없다. **"총 N건" 표시 하나 때문에 카드 20장이 count 완료까지 대기한다.**

**(c) `body_original` 을 목록 select 에 포함한다.** (345행)
소비처는 `toExcerpt(item.summary_ko, item.body_original)` 의 **폴백 120자** 뿐이고(169·181·211행), `summary_ko` 가 있으면 아예 쓰이지 않는다. 기사 원문 전체 × 20건을 그 폴백 하나 때문에 전송한다.

**(d) 스켈레톤이 두 종류다.**
`src/app/dashboard/contents/loading.tsx` = 16:9 이미지 블록이 **있는** 카드 6개. `ContentsBoard`의 `SkeletonCard`(123행) = 이미지 블록이 **없는** 카드 6개. 따라서 **스켈레톤A → 스켈레톤B → 실제 카드** 로 모양이 세 번 바뀐다. 디렉터가 스크린샷으로 지적한 박스는 B 단계다.

**(e) 조건부 이중 쿼리.** (272행)
`category = fixedCategory ?? searchParams.get('category') ?? ''` 이므로 `/dashboard/contents` 로 **카테고리 없이** 진입하면 `category=''` 로 1차 쿼리가 나간 뒤 `router.replace('?category=뉴스')` 로 2차 쿼리가 또 나간다. 상단 네비가 `?category=뉴스` 를 달고 들어오면 해당 없음 — **측정 M1 에서 확인할 것.**

**(f) 참고 선례.** `050b4a6`(#90, 병렬 레인)이 상단 네비 깜빡임을 **서버 확정** 방식으로 이미 해소했다. 목록 SSR(R1) 을 하게 되면 그 패턴을 참고할 것.

### M2. EXPLAIN ANALYZE (담당: 수희 · SQL 핸드오프, 읽기 전용)
```sql
-- ① 목록 쿼리 (count 없음)
explain analyze
select id, title, summary_ko, category, published_at, collected_at, thumbnail_url
from public.contents
where status = 'published' and category = '뉴스'
order by published_at desc nulls last
limit 20;

-- ② count 쿼리 (현재 목록에 묶여 있는 것)
explain analyze
select count(*) from public.contents
where status = 'published' and category = '뉴스';

-- ③ body_original 포함 시 전송량 감각
select
  count(*)                                        as rows,
  pg_size_pretty(sum(length(coalesce(body_original,''))))  as body_total,
  pg_size_pretty(sum(length(coalesce(summary_ko,''))))     as summary_total,
  count(*) filter (where summary_ko is null or summary_ko = '') as summary_missing
from (
  select body_original, summary_ko from public.contents
  where status='published' and category='뉴스'
  order by published_at desc nulls last limit 20
) t;
```
기록: ①과 ②의 **Execution Time** 각각, ③의 `body_total` vs `summary_total`, `summary_missing`.

## 8. 판정 (플래너, 2026-07-20)

### 8.1 🔴 기각된 내 가설 — `count: 'exact'` 는 범인이 아니다
§1(b) 에서 count 를 유력 범인으로 지목했으나 **틀렸다.** 대상이 **4,126행**이고 237 인덱스가 깔려 있어 count 는 수 ms 수준이다. **데이터 규모를 확인하지 않고 구조만 보고 추정한 것이 원인** — 인수인계 §5-2 의 재발이다. M2 EXPLAIN 은 실시하지 않는다.

### 8.2 확정된 범인

**① `/api/contents/keywords` — 2.24s, 최대 단일 병목**
`src/app/api/contents/keywords/route.ts` 는 칩 12개를 위해 **30일치 published 뉴스 전 행의 `matched_keywords` 를 1,000건씩 페이지네이션해 전부 앱으로 가져와 메모리에서 집계**한다(`while(true)` + `QUERY_PAGE_SIZE = 1000`). 응답 캐시 없음. **함수(icn1)를 타는데도 2.24s** — 리전으로 덮을 수 없는 알고리즘 문제. 게다가 **5회 호출**된다.

**② 요청 폭증 — 134건 / 16.0MB**
목록 화면 하나가 받는 양이다. 개별 쿼리 튜닝으로 해결되는 규모가 아니다.

**③ `contents` 중복 조회 10건 이상**
Supabase 직결 6건 + 자체 API 4건. 같은 테이블을 한 화면에서 열 번 친다. 호출 주체 규명 필요.

**④ 이미지가 최적화를 안 탄다**
`ContentCard.tsx:82` 주석: `next/image remotePatterns 미설정 → unoptimized로 빌드 에러 방지`. `<img>` 직접 사용으로 자체 도메인 원본 jpg 가 그대로 나간다. 16MB 의 상당 부분으로 추정.

**⑤ 목록 화면에서 브리핑 wav 를 받는다**
`FloatingBriefingMini` 가 `DashboardShell` 에 상시 렌더되며 `new Audio(briefing.audio_url)` 를 생성(74·91행). 재생 전에 다운로드가 시작된다.

**⑥ `body_original` 페이로드** — §1(c) 유효. 확정은 못 했으나 제거 근거는 충분(소비처가 폴백 120자뿐).

### 8.3 결론
체감 저하의 원인은 **목록 쿼리가 느려서가 아니라, 한 화면이 134요청·16MB 를 동시에 당기고 그중 칩 하나가 2.24초를 먹기 때문**이다. **연출(P 계열)로 덮을 수 없다.**
