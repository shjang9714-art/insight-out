## 1. 문제 — 전부 2026-08-27 라이브 DB로 실측했다. 재조사 금지.

### 1-1. 🔴 최우선: 랭킹이 실제 데이터의 6%로 계산되고 있다

```
select count(*) from public.trending_issue_articles
where issue_id in (select issue_id from public.trending_keywords);
→ 158,384
```

`fetchAllIssueArticles`(`src/lib/issues/trending.ts:572`)는
`ISSUE_ARTICLES_MAX_PAGES(10) × ISSUE_ARTICLES_PAGE_SIZE(1000) = 10,000`행에서 자른다(`:561-562`).
정렬이 `collected_at desc`이므로 **최근 약 4~5시간치 기사만** 보고 "오늘의 급상승"을
계산해 왔다. 하루치 사건 클러스터가 물리적으로 만들어질 수 없었다.

실화면(2026-08-27)의 증상 — 지역 뉴스(`박완수 경남지사`), 대학 간담회(`덕성여대`),
같은 사건 3칸 분산(`SK AX·SAP` 1·3·8위) — 은 대부분 여기서 파생된다.
**점수 공식을 아무리 손봐도 입력 데이터가 6%면 의미가 없다. 이것부터 고친다.**

캡 도달 시 `console.warn`(`:595`)만 남기고 그대로 진행하도록 되어 있어 **3주 넘게
아무도 몰랐다.** 경고 처리도 함께 강화한다(§2-4).

### 1-2. 행 폭발의 원인 2가지

| 원인 | 실측 |
|---|---|
| ① 이슈 멤버십 fan-out — 기사 1건이 여러 이슈에 태깅 | 72h 전체 기사 **2,383건**인데 상위 이슈 하나가 **1,408건**(59%)을 물고 있음. 2위 1,407 / 3위 1,371 |
| ② 엔티티 fan-out — `content_entities` left join | 기사당 평균 66행 (158,384 / 2,383) |

⇒ 선행 SQL의 `trending_basis_articles` 뷰가 **기사 1건 = 1행**으로 접는다
(`issue_ids`·`entity_names` 배열 집계). 약 2,383행 → 캡에 걸리지 않는다.

### 1-3. ⚠️ 이슈는 클러스터링 경계로 쓸 수 없다 (2단계 과제, 이번엔 완화만)

이슈 태깅이 무차별적이라(59%) "이슈 안에서 사건을 나눈다"는 현재 전제가 성립하지 않는다.
게다가 데이터가 온전해지면 이슈 하나에 기준일 기사 수백 건이 들어오는데,
`subclusterIssue`(`:258`)의 union 조건이

```ts
if (sim >= SUBCLUSTER_SIM || sharedEntity) uf.union(i, j)
```

라서 **공유 엔티티 하나로 전부 연쇄 연결된다.** "삼성전자"가 달린 기사 300건이
제목과 무관하게 한 덩어리가 되는 거대 블롭 위험. 지금까지는 데이터 잘림이 우연히
이걸 가려주고 있었으므로, §1-1을 고치면 **반드시 같이 터진다.** §2-3에서 막는다.

### 1-4. 🔴 사전에 없는 회사는 영원히 중복 노출된다

`isDuplicateEvent`(`:330`)의 `if (companyA === null || companyB === null) return false`.
`COMPANY_ALIASES`(`:140`)에 `SK AX`도 `SAP`도 없어 **키워드 겹침을 보기도 전에 병합 포기.**

### 1-5. ⚠️ 매체 등급(trust_tier)은 지금 못 쓴다

실측: 404개 매체 **전부 `trust_tier = 1`**. 아무도 등급을 설정한 적이 없다.
곱해봐야 전 슬롯 동일값이라 순위가 안 바뀐다. **컬럼은 받아두되 이번엔 점수에
반영하지 않는다.** 나중에 등급을 채우면 자동으로 살아나도록 §2-5 구조만 잡아둔다.

### 1-6. ⚠️ 해시태그 라벨 오류

`topHashtag = matched_keywords[0]`(`:291`)인데 `matched_keywords`는 관련도가 아니라
**매칭 순서**다. 본문에 "AI"가 한 번 스쳐도 `#AI`가 붙는다.

## 2. 작업 — 전부 `src/lib/issues/trending.ts` (별도 명시 제외)

### 2-1. 🔴 데이터 소스를 `trending_basis_articles`로 교체

`IssueArticleRow` / `fetchAllIssueArticles`를 아래로 갈아끼운다.

```ts
interface BasisArticleRow {
  content_id: string
  title: string
  collected_at: string
  matched_keywords: string[] | null
  cluster_id: string | null
  source_key: string | null
  source_trust_tier: number | null
  issue_ids: string[] | null
  entity_names: string[] | null
}
```

- 조회는 `.from('trending_basis_articles').select('*').order('collected_at', { ascending: false })`
  + 기존과 동일한 `range()` 페이지네이션(안전장치는 유지).
- **`.in('issue_id', issueIds)` 필터는 없어진다** — 뷰가 이미 기사 단위이고 발행 이슈에
  속한 기사만 담는다. 후보 이슈 매칭은 코드에서 `row.issue_ids`와 `issueIds` 교집합으로
  판정한다.
- `ArticleRow`의 `entities: EntityRef[]`는 `entity_names: string[]`로 단순화한다.
  뷰가 이미 `company·product·person`만 골라 담으므로 `concrete` 플래그와
  `CONCRETE_ENTITY_TYPES`는 **삭제**한다(전부 concrete).
- 기사→이슈 fan-in을 만들던 `byIssue` 이중 Map 루프(`:667-688`)는 폐기하고,
  `content_id → ArticleRow` 단일 Map + `issue_id → content_id[]` 인덱스로 재구성한다.
  **한 기사가 여러 이슈에 속해도 ArticleRow 객체는 1개만 존재해야 한다**(중복 집계 방지).

### 2-2. 🔴 cluster_id로 1차 묶기

크롤러가 수집 시점에 이미 "같은 기사" 판정을 끝내 두었다(`crawler/cluster.ts` —
대표는 `cluster_id=null`, 멤버는 대표 id를 가리킴). 제목 유사도로 재발견하지 말고 이걸 쓴다.

`subclusterIssue`의 Union-Find 초기화 **직전**에, 같은 클러스터 키를 가진 기사끼리
무조건 `union`한다. 클러스터 키 = `article.clusterId ?? article.contentId`
(대표는 자기 자신이 키, 멤버는 대표 id → 대표와 멤버가 같은 키로 만난다).

### 2-5. 매체 다양성 기반 점수

```ts
// ─── 랭킹 점수 (지시서 548) ──────────────────────────────────────────────────
// score = sourceCount^SOURCE_EXPONENT × burst
//  - sourceCount : 슬롯 내 distinct source_key 수 = "몇 개 언론사가 이 사건을 다뤘나"
//    기사 건수 대신 이걸 주 볼륨으로 쓴다. 한 매체가 후속기사 5건 쏟아낸 것과
//    서로 다른 5개 매체가 동시 보도한 것을 구분하기 위함(후자가 진짜 큰 뉴스).
//  - burst : 이슈의 72h 건수 / 직전 72h 건수 — "평소 대비 얼마나 튀었나".
//    이게 있어야 상시 대형 테마(#AI)가 상단을 독점하지 않는다.
// ⚠ source_trust_tier는 실측상 전 매체 1이라(§1-5) 이번엔 곱하지 않는다.
//   등급이 채워지면 여기에 가중을 얹는다.
const SOURCE_EXPONENT = 0.8
const BURST_MULTIPLIER_MIN = 0.5
const BURST_MULTIPLIER_MAX = 4   // 신규 이슈(prev=0)가 무한대로 튀는 것 방지
// 노이즈 게이트 — 최소 2개 언론사가 다룬 사건만 순위에 올린다(§1-1 지역·대학 기사 배제).
const MIN_SOURCE_COUNT = 2
```

```ts
function computeBurst(recentCount: number, prevCount: number): number {
  const raw = recentCount / Math.max(prevCount, 1)
  return Math.min(Math.max(raw, BURST_MULTIPLIER_MIN), BURST_MULTIPLIER_MAX)
}

function computeScore(sourceCount: number, burst: number): number {
  return Math.pow(Math.max(sourceCount, 1), SOURCE_EXPONENT) * burst
}
```

`InternalEvent`에 `sourceCount: number` · `burst: number` · `score: number`를 추가한다.

- `sourceCount` = 슬롯 `contentIds`의 distinct `source_key` 수
  (`source_key`가 null인 기사는 세지 않는다. 실측상 0건이지만 방어).
- `burst` = 슬롯이 흡수한 이슈들의 burst 중 **최댓값**.
- `mergeEventGroup`에서 병합 시 `sourceCount`는 반드시 **contentIds 합집합에서 재계산**
  (멤버 값 단순 합산 금지 — 같은 매체가 이중집계된다), `burst`는 최댓값, `score`는 재계산.
- `compareByRecentCountDesc`를 **`compareByScoreDesc`로 교체**하고 원함수는 삭제한다.
  1순위 `score` desc → 2순위 `sourceCount` desc → 3순위 `todayCount` desc →
  4순위 `changePct` desc(null 최우선). 참조 지점 3곳(`collapseDuplicateEvents`,
  `buildPrimaryEvents`, §main 정렬)을 전부 교체한다.

이슈 태깅이 무차별적이라(한 이슈가 72h 전체의 59%) **이슈를 클러스터링 경계로 쓰는 전제
자체가 틀렸다.** 2단계에서 이슈 경계를 버리고 기준일 전체 기사를 `cluster_id`로 1차 묶은
뒤 사건 단위로 재클러스터링한다. 이슈는 burst 계산용으로만 남긴다.
**이번 PR에서 선반영하지 말 것.** 1단계 결과를 실화면으로 확인한 뒤 결정한다.

## §6 후속: 뷰 성능 → statement timeout → 폴백 상시 노출 사고 (2026-08-30)

1단계 PR(#207)이 main에 배포되고 DB도 정상이었는데도, `/dashboard/trending`이 3주 넘게
비상 폴백(`fetchFallbackTop`) 화면만 노출했다. 코드도 DB도 문제가 없었고, 진짜 원인은
**Vercel Data Cache(`unstable_cache`)에 박힌 과거 null**이었다 — 뷰가 느려서(2,511ms)
`computeTrendingEvents()`가 statement timeout으로 실패하던 시절의 결과가 캐시에 남아,
이후 뷰를 아무리 빠르게 고쳐도 캐시가 만료되기 전까진 그 null이 계속 서빙됐다.

### 2단 진단 루틴 (다음에 같은 증상이면 이 순서로)

1. **화면의 항목 링크를 본다.** `/dashboard/issues/...`로 연결되면 폴백
   (`fetchFallbackTop` = `fetchIssueActivity` 기반), `/dashboard/contents/...`로
   연결되면 정상 경로(`computeTrendingEvents()`가 실제로 도는 중).
2. **Vercel Runtime Logs에서 `"[trending]"`을 검색한다.** 0건이면 `computeTrendingEvents()`
   자체가 호출되지 않고 있다는 뜻 — 즉 **코드·DB 문제가 아니라 캐시 문제**다. 여기서
   코드나 DB를 다시 뒤지면 시간만 버린다.

이번 사고에서 원인 파악이 오래 걸린 이유: 실패 당시 에러의 `code`/`message`/`details`가
로그에 전혀 남지 않아 "왜 실패했는지"조차 알 수 없었다. §2 재발 방지 로깅
(`logPostgrestError` + 성공 시 `"[trending] ok events=N candidates=M rows=K"` 한 줄)은
이걸 막기 위한 조치 — 로그에 그 줄이 없으면 곧바로 캐시를 의심하면 된다.

### 측정치 (뷰 튜닝 경로)

```
2,511ms(상관 서브쿼리)
  → 1,691ms(CTE로 전환)
  → 1,080ms(CTE에 `as materialized` 강제)
  → 7.845ms(materialized view + unique index + concurrently refresh)
```
행수는 전 구간에서 2,318 동일 — 성능만 달라졌고 데이터는 바뀌지 않았다.

### 🔴 반드시 기억할 것

- **Vercel Data Cache는 Redeploy로 지워지지 않는다.** 배포를 다시 해도 캐시 키가 같으면
  같은 stale 값이 그대로 나온다.
- **Hobby 플랜엔 Data Cache Purge UI가 없다** (`/settings/data-cache`가 404). 캐시를
  강제로 무효화하는 유일한 확실한 방법은 **캐시 키 bump**뿐이다(`unstable_cache`의 두
  번째 인자 배열 — 이번엔 `'trending-events-v9'` → `'v10'`).
- **pg_cron refresh가 죽으면 급상승 데이터가 에러 없이 조용히 멈춘다.** matview가
  갱신을 멈춰도 조회 자체는 계속 성공하기 때문에(오래된 값을 계속 반환) 애플리케이션
  레벨에선 아무 에러도 나지 않는다 — matview 최근 갱신 시각을 별도로 모니터링해야
  이 실패 모드를 잡을 수 있다.
- **Supabase SQL Editor의 timeout은 훨씬 길다.** anon 키로 실제 앱이 겪는 statement
  timeout(수 초)이 SQL Editor에서는 재현되지 않는다 — "SQL Editor에서 쿼리가 잘 돈다"는
  것만으로 프로덕션 성능을 검증했다고 보면 안 된다. 실제 검증은 anon 키로 PostgREST를
  직접 호출해서 응답 시간을 재야 한다.
