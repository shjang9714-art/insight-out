## 0. 결정된 방향

- **권한**: 역할 3종(`super_admin` / `admin` / `viewer`) + **능력맵은 코드 상수**. DB에는 `role` 하나만 저장한다.
- **설정**: **`ops_settings` 한 테이블만 신설**. 기존 도메인별 설정 테이블 5개(`crawl_settings`·`llm_settings`·`newsletter_settings`·`translation_settings`·`competitor_weekly_settings`)는 **그대로 둔다**. 비밀키는 옮기지 않는다.

485가 `hasCapability()`를 유일 판정 지점으로 만들어 뒀으므로 **호출부 83곳은 이번에도 손대지 않는다.**

## A. 선행 SQL ① — 역할 확장

```sql
-- 493-A: user_role enum 확장
alter type public.user_role add value if not exists 'super_admin';
alter type public.user_role add value if not exists 'viewer';
```
⚠️ `alter type ... add value`는 **트랜잭션 안에서 실행할 수 없다.** `begin/commit` 없이 그대로 실행한다.

기존 `admin` 5명은 그대로 `admin`으로 남는다. **`super_admin` 승격은 David가 별도 UPDATE로 지정한다**(아래 SQL ②의 주석 참조).

## B. 선행 SQL ② — 운영 설정 테이블

`ops_settings`는 **키-값 단일 행 구조가 아니라 컬럼형**으로 만든다. 값마다 타입·검증이 다르고, 범용 KV는 여섯 번째 설정 패턴이 되어 오히려 혼란을 키운다.

## C. `src/lib/admin/capabilities.ts` — 능력맵

```ts
export const ROLE_CAPABILITIES: Record<string, readonly AdminCapability[]> = {
  super_admin: ADMIN_CAPABILITIES,               // 전부
  admin: ['delete_content', 'manage_sources', 'send_broadcast'],
  viewer: [],
}

export function hasCapability(role, cap?) {
  if (role === 'super_admin') return true
  if (role !== 'admin' && role !== 'viewer') return false
  if (!cap) return role === 'admin'              // capability 미지정 = 일반 어드민 동작
  return ROLE_CAPABILITIES[role]?.includes(cap) ?? false
}
```

**`manage_admins` · `reset_data` · `manage_settings` 는 `super_admin` 전용**이다. 즉 일반 `admin`은 타인 권한 변경·데이터 초기화·운영 설정 변경을 못 한다.

⚠️ **`viewer`는 `capability` 미지정 호출도 막아야 한다.** 지금 어드민 API 대부분이 capability 없이 호출되므로, `viewer`가 통과하면 조회 전용이 아니라 사실상 admin이 된다. 위 구현의 `if (!cap) return role === 'admin'`이 그 지점이다 — **여기를 잘못 쓰면 viewer가 전권을 갖는다.**

`verifyAdminRequest`·`requireAdminAction`의 `role !== 'admin'` 체크도 **3종을 허용하도록** 바꾼다(`'user'`만 거부). 그 뒤 `hasCapability`가 실제 판정을 한다.

## D. `G-11` — 운영 설정

1. `src/lib/ops/settings.ts` 신설 — `ops_settings` 단일 행을 읽어 캐시하고, **없거나 조회 실패면 기존 env 값으로 폴백**한다. env는 지우지 마라.
2. 소비처를 이 헬퍼로 교체: `ops/recipients.ts` · `ops/detect-issues.ts` · `ops/daily-brief.ts` · `tts/synthesize-briefing.ts` · `api/admin/briefings/route.ts` · `admin/page.tsx`
3. `/admin/settings`에 **운영** 탭 추가. 저장은 `manage_settings` capability 필요.
4. 값 검증은 **서버에서** 한다(수신자 이메일 형식, 한도 양수, `briefing_top_n` 1~50 등). 범위를 벗어나면 저장 거부.
5. 변경은 486 감사 로그에 남는다(`verifyAdminRequest` 경유이므로 자동). **이전/이후 값을 `completeAudit` payload에 명시**할 것.

## 검증

1. `super_admin`으로 데이터 초기화·권한 변경·설정 저장이 된다.
2. **`admin`으로 위 셋이 전부 403**이고, 콘텐츠 삭제·소스 관리·뉴스레터 발송은 된다.
3. **`viewer`로 어떤 쓰기 API도 통과하지 못한다**(capability 미지정 라우트 포함). 조회는 된다.
4. 마지막 `super_admin`을 강등하려 하면 거부되고 사유가 보인다.
5. 3·4의 거부가 `admin_audit_log`에 `outcome='failed'`로 남는다.
6. `ops_settings` 행을 지워도 기존 env 값으로 동작한다(폴백).
7. 설정 저장 시 감사 로그 payload에 이전/이후 값이 남는다.
8. 잘못된 값(음수 한도·형식 틀린 이메일) 저장이 거부된다.
9. `npm run lint` · `npx tsc --noEmit` · `npm run check:admin-auth` 통과.
