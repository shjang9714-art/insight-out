## 1. 현행 진단 (검증된 코드 사실)

### 1.1 ⭐ 457건(67%)이 사라진다 — `rejected`가 **어디에도 기록되지 않는다**

```
크롤 결과:  가져옴 683 → 신규 47 + 중복 179 = 226        나머지 457건(67%)
```

| | 코드(`counts`) | `crawl_logs` 컬럼 | 토스트 |
|---|---|---|---|
| `inserted` | ✅ | ✅ `inserted_count` | ✅ 신규 |
| `duplicate` | ✅ | ✅ `duplicate_count` | ✅ 중복 |
| `held`(보류) | ✅ | ✅ `held_count` | ❌ **안 보임** |
| **`rejected`(제외)** | ✅ | 🔴 **컬럼 없음** | 🔴 **안 보임** |

**`counts.rejected`는 세기만 하고 버려진다.** `crawl_logs`에 `rejected_count` 컬럼이 없다.

`rejected`가 되는 조건 (`orchestrator.ts:390-397`):
```ts
isAdLike(qText)                                             // 광고성
|| isExcludedByGroups(item.title, groups)                   // keyword_groups.exclude_patterns
|| effectiveLength(title, body) < MIN_EFFECTIVE_LENGTH      // 유효 길이 미달
|| (!src.isSearchSourced && bodyLength(body) < minBodyLength) // 본문 최소 길이(어드민 설정, 기본 250)
|| exclusionMatch?.action === 'reject'                      // 제외 규칙
```
→ **어느 조건에 몇 건이 걸렸는지 전혀 알 수 없다.** 본문 최소 길이 설정 하나가 수백 건을 버리고 있을 수도 있다.

### 1.2 ⭐ 품질 지표가 전부 `—` — **RPC가 DB에 없다**
```ts
// src/app/api/admin/source-quality/route.ts:138
```

- `source_quality_stats` RPC는 **`docs/sql-handoff/186-source-quality.sql`에 있으나 적용되지 않았다.**
- → 발행률 · **본문확보율** · dead-link율 · 불량률 · 대표 불량사유가 **전부 `—`**.
- **코드는 멀쩡하다. SQL 하나가 안 돌았고, 실패가 완벽하게 조용하다.**

### 1.3 ⭐ 경고 피로 — 진짜 경고가 묻혔다
`SourceQualityManager.tsx:488`
```ts
if (src.is_active && s.inserted7d === 0) → "⚠️ 점검 필요"
```
- **87개 소스 중 약 60개가 ⚠️** (7일 신규 0건)
- 그 사이에 **🔴 연속실패 7 · 피드 HTTP 404 짜리 4개**(정부 소스)가 섞여 있었다

**"7일 신규 0"과 "피드가 죽음"은 완전히 다른 사건이다.**
- 조선일보·한겨레·매경 같은 종합지가 0건인 건 **필터가 거르는 것**일 수 있다(정상 동작).
- 정부 소스 404는 **사고**다.
- **지금 화면은 둘을 구분하지 않는다.**

## 3. 구현

### 3-1. `rejected` 기록 + 사유 분해

**`orchestrator.ts`**
- `counts.rejected`를 **사유별로 세분화**한다:
  ```ts
  counts.rejectedBy = { ad: 0, excludedGroup: 0, tooShort: 0, bodyTooShort: 0, excludeRule: 0 }
  ```
  `:390-397`의 5개 조건을 **if/else로 분리**해 어느 것에 걸렸는지 카운트할 것. (현재는 `||`로 묶여 첫 조건만 참이어도 나머지를 알 수 없다.)
- `crawl_logs.insert`에 `rejected_count` 추가.
- 사유 분해는 **`rejected_by jsonb`** 컬럼 하나로 넣는 편이 낫다(조건이 앞으로 늘어난다). SQL에 함께 포함할 것.

**⚠️ 회귀 주의**: `counts.rejected++` 후 `return {}` 하는 **동작 자체는 바꾸지 말 것.** 세는 방식만 바꾼다.

### 3-2. 크롤 결과를 **합이 맞게** 보여준다

토스트·`/admin/crawl-logs`에서:
```
가져옴 683
  ├ 신규     47
  ├ 중복    179
  ├ 보류      ?   ← held (지금 안 보임)
  └ 제외    457   ← rejected (지금 없음)
      광고성 12 · 길이미달 380 · 제외규칙 65 …
```
**`가져옴 = 신규 + 중복 + 보류 + 제외`가 맞아떨어져야 한다.** 안 맞으면 어딘가 또 새는 것이다 — **그 자체가 검증이다.**

### 3-3. 품질 지표 — **조용한 실패를 깨뜨린다**

`src/app/api/admin/source-quality/route.ts:140`
```ts
if (error) {
  return NextResponse.json({})    // ← 이게 오늘의 사고 원인
}
```
→ 고칠 것:
- **`console.error`를 남길 것.**
- 응답에 **`{ unavailable: true, reason: 'rpc_missing' }`** 같은 신호를 실을 것.
- 화면(`SourceQualityManager`)이 `—` 대신 **"품질 지표를 계산할 수 없습니다 (SQL 186 미적용)"** 를 **눈에 띄게** 표시할 것.

> **graceful이 silent면 안 된다.** 이 코드베이스가 오늘 하루에만 6번 같은 방식으로 실패했다.

### 3-4. ⭐ 경고 피로 해소 — **"저활성"과 "고장"을 분리**

`SourceQualityManager`의 수집 상태를 3단계로:

| 상태 | 조건 | 표시 |
|---|---|---|
| 🔴 **고장** | 연속실패 ≥ 3 **또는** 마지막 성공 > 3일 | **최상단 고정** |
| ⚠️ **저활성** | 7일 신규 0 **인데 크롤은 성공** | 접어두거나 하단 |
| ✅ **정상** | 7일 신규 ≥ 1 | |

- **상단에 요약 배너**: `🔴 고장 4 · ⚠️ 저활성 56 · ✅ 정상 27`
- **기본 정렬: 고장 먼저.** 지금은 이름순이라 정부 소스 4개가 목록 중간에 흩어져 있었다.
- **"고장"만 보기 필터** 제공.

> **경고가 60개면 경고가 아니다.** 진짜 사고 4건이 10일간 묻힌 게 그 증거다.

### 3-5. 저활성의 **원인**을 알려준다 (§3-1이 있어야 가능)

7일 신규 0인 소스의 최근 `crawl_logs`를 보면:
- `fetched > 0` 인데 `rejected`가 대부분 → **필터가 거르고 있다**(정상일 수 있다)
- `fetched > 0` 인데 `duplicate`가 대부분 → **이미 다른 소스로 들어온다**
- `fetched = 0` → **피드가 빈다**

→ 저활성 소스 행에 **`"가져옴 40 · 제외 40 (길이미달)"`** 처럼 한 줄로 보여줄 것. **이게 있으면 "왜 0건인지"를 클릭 없이 안다.**

## 4. 회귀 가드

- **크롤의 판정 로직을 바꾸지 말 것**(`isAdLike`·길이 게이트·제외 규칙). **세는 방식만** 바꾼다. 수집 결과가 달라지면 안 된다.
- **`가져옴 = 신규 + 중복 + 보류 + 제외`가 맞아야 한다.** 안 맞으면 안 센 경로가 있는 것이다.
- **`crawl_logs` 컬럼 미적용(42703) graceful** — SQL 전에 배포돼도 크롤이 깨지면 안 된다. 단 **조용히 넘기지 말고 `console.error`.**
- **RPC 미존재를 빈 객체로 삼키지 말 것**(§3-3). 화면에 드러나야 한다.
- 기존 "지금 수집"·"제외 규칙 관리" 동작 불변.
- 정렬 기본값을 바꾸되, **이름순 정렬 옵션은 남길 것.**
