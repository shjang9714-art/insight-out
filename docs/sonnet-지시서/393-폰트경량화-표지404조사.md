# A. 폰트 경량화

## A-1. 현행 진단 (확인된 사실)

**실측**(2026-07-20, production `3a7e3cd`, 캐시 비활성화):
```
PretendardVariable….woff2   2.06MB  (325ms)  initiator: 0.kf5d-6km1r5.js
PretendardVariable….woff2   2.06MB  (192ms)  initiator: contents:1
PretendardVariable….woff2   2.06MB  (132ms)  initiator: contents:2
```

**코드**: `src/app/layout.tsx:9`
```ts
const pretendard = localFont({
  src: "../../public/fonts/PretendardVariable.woff2",
  variable: "--font-pretendard",
  display: "swap",
  weight: "45 920",
})
```
- 실제 파일: `public/fonts/PretendardVariable.woff2` = **2,057,688 bytes**
- **`next/font/local` 은 서브셋을 하지 않는다.** `next/font/google` 과 달리 파일을 그대로 싣는다. 한글 전체 글리프가 통째로 나간다.
- 캐시 비활성화 측정이라 3회 모두 받았다. **실사용은 캐시로 1회지만 첫 방문 2.06MB 는 그대로다.**

## A-2. 구현

### A-2-1. 서브셋 적용 — 이 슬라이스의 본체

**권장: Pretendard 공식 dynamic subset 방식**(`unicode-range` 로 쪼갠 woff2 조각들). 브라우저가 **실제 쓰이는 글자 범위의 조각만** 내려받는다. 한글 전체를 싣지 않으면서 **없는 글자가 깨지지 않는다**는 게 핵심 장점이다.

- 조각 파일을 `public/fonts/pretendard/` 에 두고 `globals.css` 에 `@font-face` + `unicode-range` 를 선언한다.
- 이 경우 `layout.tsx` 의 `localFont()` 는 제거하고, CSS 변수 `--font-pretendard` 는 **동일한 이름으로 유지**한다(Tailwind `font-sans` 가 이 변수를 참조하므로).

**대안(조각 배포판을 못 쓸 경우): `pyftsubset` 단일 서브셋**
- 범위: 라틴 + 기호 + **한글 완성형 KS X 1001 2,350자** 최소. 예상 300~500KB.
- ⚠️ **위험**: 서브셋 밖 글자는 두부(□)로 깨진다. 이 서비스는 **기업명·인명·기술 용어**가 계속 유입되므로 희귀 글자가 나올 수 있다. 단일 서브셋을 택한다면 **폴백 폰트 체인을 반드시 두고**, 검증에서 희귀 글자를 직접 확인할 것.
- 그래서 **dynamic subset 을 권장한다.**

**어느 쪽이든 결정 근거와 최종 크기를 §A-4 에 기록할 것.**

### A-2-2. 3회 요청 원인 규명
초기화 프로그램이 셋 다 다르다(`0.kf5d-6km1r5.js` · `contents:1` · `contents:2`). **`@font-face` 가 여러 곳에서 중복 선언되고 있는지** 확인한다.
- `globals.css` · `layout.tsx` · 그 외 CSS 에서 폰트 선언을 **전수 검색**할 것.
- 세 URL 이 **완전히 동일한지** 다른지 확인(동일 URL 이면 캐시 비활성화로 인한 반복 요청 — 정상. 다른 URL 이면 진짜 중복).
- 결과를 §A-4 에 기록. **원인이 Next.js 내부 동작이면 고치지 말고 기록만 할 것.**

### A-2-3. 별건 관찰 — 고치지 말고 보고만
`src/components/dashboard/WelcomeGreeting.tsx:8`
```ts
const nanumMyeongjo = Nanum_Myeongjo({ weight: '400', subsets: ['latin'], display: 'swap' })
```
**한글 명조 폰트인데 `subsets: ['latin']` 만 지정**돼 있다. 한글 인사말에 이 폰트가 실제로 적용되는지 의심스럽다(적용 안 되고 폴백 중일 가능성). **이번 범위 밖 — 화면 확인 후 보고만 할 것.**

## A-3. 회귀 가드
1. **한글·영문·숫자·기호가 모두 정상 렌더**된다. 특히 카드 제목·요약의 한자·특수문자.
2. **굵기(weight) 가 유지**된다. 현재 `weight: "45 920"` 가변 범위 — 서브셋/조각 방식에서도 제목(semibold/bold)과 본문(regular)이 구분돼야 한다.
3. `--font-pretendard` **변수명 불변**. Tailwind `font-sans` 가 참조한다.
4. **FOUT 이 심해지지 않는다.** 현재 `display: "swap"`. 조각 방식에서도 동일 전략 유지.
5. 다크모드·인쇄(`print:`) 스타일 영향 없음.
6. `Geist_Mono`(코드용)·`Nanum_Myeongjo` 는 **건드리지 않는다.**

## A-4. 기록란
| 항목 | 값 |
|---|---|
| 채택 방식 (dynamic subset / pyftsubset) | **dynamic subset** (Pretendard 공식 배포, npm `pretendard@1.3.9`) |
| 채택 사유 | 권장안 그대로 채택. `pyftsubset` 단일 서브셋은 희귀 글자(기업명·인명) 깨짐 위험이 있어 배제. |
| 폰트 전송량 (기준 2.06MB × 3) | 조각 92개, 디스크 총합 3.0MB(전체 합) — **브라우저는 페이지에 실제 쓰인 글자의 unicode-range 조각만 받는다**(전부가 아님). 실측(라이브 측정)은 미실시, §검증 라이브 측정 항목 참고. |
| 3회 요청 원인 (§A-2-2) | 소스에 `@font-face` 중복 선언은 **없었다**(전수 검색 결과 next/font/local 이 내부적으로 청크별 로더를 주입하는 것으로 추정 — Next.js 내부 동작). 이번 변경으로 `next/font/local` 자체를 제거했으므로 이 메커니즘은 더 이상 존재하지 않는다. 재현 여부는 라이브 측정 필요. |
| Nanum_Myeongjo 관찰 (§A-2-3) | **확인**: `WelcomeGreeting.tsx`의 모든 인사말 문구(`phrase.main`)가 100% 한글인데 `Nanum_Myeongjo({ subsets: ['latin'] })`는 한글 글리프를 포함하지 않는다. 즉 이 폰트는 실제 렌더링에 **아무 효과가 없고** 항상 CSS 폴백 체인(사실상 Pretendard)으로 렌더된다. 고치지 않음(범위 밖) — 후속 슬라이스에서 `subsets: ['korean']` 추가 또는 폰트 자체 제거 검토 필요. |

# B. 표지 이미지 404 — **조사 전용, 고치지 말 것**

## B-1. 현상

391 후 측정에서 **일부 표지만 404**(0B, 유형 `txt`)다.

| 정상 | 404 |
|---|---|
| `AIDC-7.jpg` 84.73KB · `AI기술-2.jpg` 180.75KB | `AIDC.jpg` · `AI기술.jpg` · `통신 b2b.jpg` · `뉴스.jpg` · `뉴스-5.jpg` |

## B-2. ⚠️ 기각된 가설 — "미커밋이라 프로덕션에 없다"

플래너가 처음 이렇게 판단했으나 **틀렸다.** 확인 결과:

```
public/topic-covers/AIDC.jpg        추적됨 / 파일있음
public/topic-covers/AIDC-7.jpg      추적됨 / 파일있음
public/topic-covers/AI기술.jpg      추적됨 / 파일있음
public/topic-covers/뉴스.jpg        추적됨 / 파일있음
public/topic-covers/통신 b2b.jpg    추적됨 / 파일있음
```
**전부 git 추적 중이고 파일도 존재한다.** 추적 73개 / 미추적 36개인데, **404 나는 것들이 추적된 쪽에 있다.** 미커밋은 원인이 아니다.

> 플래너의 네 번째 오진(390 §8.1 count · 393-A "요청 많음=중복" · body_original · 이번). **또 크기·상태를 확인하지 않고 추정했다.**

## B-3. 조사할 것

**① 실제 HTTP 상태 코드를 확인한다.** 이게 첫 단추다.
Network 탭에서 해당 행을 클릭해 **상태 코드와 `Content-Type` 응답 헤더**를 본다. 또는 브라우저 주소창에 직접:
```
https://insight-out-app.vercel.app/topic-covers/AIDC.jpg
https://insight-out-app.vercel.app/topic-covers/AIDC-7.jpg   ← 정상 대조군
```
404 인지 / 200인데 본문 0바이트인지 / 다른 코드인지에 따라 원인이 완전히 갈린다. **여기서부터 시작하지 않으면 또 추측이 된다.**

**② 파일명 정규화(NFC/NFD)** — 인수인계 §3-3 이 경고한 그 문제다. macOS 는 한글 파일명을 NFD 로 저장한다. 브라우저는 NFC 로 요청하고 Vercel 은 바이트 단위로 매칭하므로 불일치 시 404 다.
- 다만 **`AIDC.jpg` 는 순수 ASCII 인데도 404** 다 → NFD 만으로는 설명되지 않는다. 한글/ASCII 실패 사례를 **나눠서** 봐야 한다.
- `git ls-files public/topic-covers/ | cat -A` 등으로 저장된 바이트를 확인.

**③ 공백 포함 파일명** — `통신 b2b.jpg` 는 공백이 있다. URL 인코딩 처리 확인.

**④ 요청 URL 생성부** — `src/lib/contents/topic-cover.ts` 의 `coverUrlFor()` 가 실제로 어떤 문자열을 만드는지. `encodeURIComponent` 적용 여부와 대소문자.

**⑤ 대소문자** — Vercel 은 대소문자를 구분하고 macOS 는 기본 구분하지 않는다. 저장된 이름과 요청 이름의 대소문자가 일치하는지.

## B-4. 산출
**원인을 확정해 §B-5 에 기록하고 보고한다. 이번 슬라이스에서 고치지 않는다.**
원인에 따라 조치가 완전히 달라진다(파일명 정규화 일괄 변경 / URL 인코딩 수정 / 파일 재커밋 / Vercel 설정). 잘못 고치면 **73개 표지가 한꺼번에 깨진다.**

| **확정 원인** | **미확정.** 유력 가설: 측정 시점(391 배포 직후) **Vercel CDN 엣지 캐시 전파 지연** — 신규 배포 직후 일부 POP이 구 배포의 네거티브(404) 캐시를 짧게 들고 있다가 이후 전파·만료로 정상화됐을 가능성. 코드·파일·인코딩 어느 쪽에도 결함이 발견되지 않았고, 시간이 지난 지금은 100% 재현되지 않는다는 점이 이 가설과 부합한다. **확정을 위해서는 최초 보고 시점과 가까운 시각의 실제 브라우저 Network 탭 재현이 필요**하나 이번 조사에서는 그 시점이 지나 확보할 수 없었다. |
