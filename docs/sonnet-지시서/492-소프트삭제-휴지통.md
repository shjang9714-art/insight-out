## 0. 왜 조심하는가

`contents`를 지우면 **10개 테이블이 `ON DELETE CASCADE`로 함께 삭제**된다 —
`bookmarks` · `archive_items` · `ai_report_sources` · `company_documents` · `content_entities` · `content_keywords` · `content_services` · `content_signals` · `content_views` · `issue_contents`.

소프트 삭제로 바꾸면 CASCADE가 아예 발화하지 않아 관계가 보존된다. **대신 조회 측 부담이 크다.**

| 경로 | 지점 수 | 차단 방법 |
|---|---|---|
| 사용자 (RLS 적용) | 147 | **RLS 정책 2개**에 조건 추가 — 한 번에 덮인다 |
| 어드민 (service_role, RLS 우회) | **77** | **명시 필터 필요** → 1단계 인벤토리 |
| 비어드민 service_role (lib·cron) | **32** | 명시 필터 필요 → 1단계에 포함 |
| `get_recommended_feed` RPC | 1 | SECURITY DEFINER라 RLS 우회 — 함수 본문 수정 필요 |

`deleted_at`은 현재 스키마에 **전례가 0건**이다. 관례를 새로 만드는 일이다.

## 2단계 — 스키마 + 차단 (SQL 선적용 후)

1. **RLS 정책 2개 교체** — SQL로 처리(아래 §SQL B). 사용자 147곳이 한 번에 덮인다.
2. **`get_recommended_feed`** 함수 본문에 `and c.deleted_at is null` 추가 — SQL B에 포함.
3. **1단계 A분류 지점에 `.is('deleted_at', null)` 추가.** B·C는 손대지 않는다.
4. 삭제 경로를 `update … set deleted_at = now(), deleted_by = <userId>`로 바꾼다.
   대상: `api/admin/contents/delete` · `AdminContentManager` 단건/일괄 · `contents/purge`
   ⚠️ **`purge`는 예외** — "영구 삭제"의 의미가 있으므로 **휴지통 비우기**로 재정의한다(§3단계).

## 3단계 — 휴지통 화면

`/admin/contents`에 **휴지통 탭**(또는 `?deleted=1` 필터). `AdminTable` v2를 그대로 쓴다.

- 컬럼: 제목 · 카테고리 · 삭제 시각 · 삭제자 · 복원 · 영구삭제
- **복원**: `deleted_at = null`. 성공 토스트.
- **영구 삭제**: 실제 `delete`. `AdminConfirm`으로 **대상 목록 + 연쇄 삭제 건수**를 반드시 표시(491이 이미 하는 방식).
- **30일 자동 정리**: 새 cron을 만들지 마라. 기존 `ops-brief` 또는 `link-health` 안에서 `deleted_at < now() - interval '30 days'`를 정리하고 `job_runs`에 건수를 남긴다.
- 모든 동작은 486 감사 로그에 남긴다(`content.soft_delete` · `content.restore` · `content.purge`).

## SQL A — 컬럼 추가 (1단계 승인 후 적용)

```sql
begin;

alter table public.contents
  add column if not exists deleted_at timestamptz,
  add column if not exists deleted_by uuid references public.users(id) on delete set null;

comment on column public.contents.deleted_at is
  '492: 소프트 삭제 시각. null 이면 정상. 30일 후 자동 영구 삭제.';

create index if not exists contents_deleted_at_idx
  on public.contents (deleted_at) where deleted_at is not null;

-- 살아있는 행 조회가 대다수이므로 부분 인덱스로 기존 인덱스를 보완
create index if not exists contents_alive_collected_idx
  on public.contents (collected_at desc) where deleted_at is null;

commit;
```

## SQL B — RLS + RPC (SQL A 이후, 코드 배포 직전)

⚠️ **SQL B를 적용하면 삭제된 콘텐츠가 사용자에게서 즉시 사라진다.** 코드 배포와 가깝게 적용할 것.

```sql
begin;

drop policy if exists "contents: 인증 사용자 조회" on public.contents;
create policy "contents: 인증 사용자 조회" on public.contents
  for select using (
    auth.role() = 'authenticated'
    and status = 'published'
    and deleted_at is null
  );

drop policy if exists "contents: 익명 공개 조회(뉴스레터)" on public.contents;
create policy "contents: 익명 공개 조회(뉴스레터)" on public.contents
  for select to anon using (
    status = 'published'
    and deleted_at is null
  );

commit;
```
> `contents: admin 전체 조회`·`admin 관리` 정책은 **그대로 둔다** — 어드민은 휴지통을 봐야 한다.
> `get_recommended_feed` 함수 수정은 본문 확인 후 별도 제공한다(1단계 보고에 현재 본문을 첨부할 것).

## 검증

1. 콘텐츠 1건 삭제 → `deleted_at` 채워지고 **`bookmarks`·`archive_items` 행이 그대로 남는다**(CASCADE 미발화).
2. 삭제된 콘텐츠가 사용자 목록·검색·추천에서 사라진다(RLS + RPC).
3. 어드민 일반 목록에서도 사라지고 **휴지통 탭에서만 보인다**.
4. 복원하면 원래대로 돌아온다(북마크·아카이브 연결 유지).
5. 영구 삭제 시 확인창에 대상 목록 + 연쇄 건수가 보이고, 실행 후 관계 행도 사라진다.
6. 30일 초과분 자동 정리가 돌고 `job_runs`에 건수가 남는다.
7. 삭제·복원·영구삭제가 `admin_audit_log`에 남는다.
8. **재수집이 삭제된 URL을 중복으로 판정하지 않는다**(`orchestrator.ts` 확인).
9. `npm run lint` · `npx tsc --noEmit` · `npm run check:admin-auth` 통과.
