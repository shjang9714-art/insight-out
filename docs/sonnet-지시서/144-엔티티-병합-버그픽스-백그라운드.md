## 배경 (David 검증 중 발견)

정규화 "병합 적용"이 실패:
```
merge ...: 관리자만 병합할 수 있습니다.   (×N)
alias insert: there is no unique or exclusion constraint matching the ON CONFLICT specification
```
+ 요청: **병합을 전체/순차 어느 쪽이든 백그라운드로** 돌려 UI가 막히지 않게.

---

## A. 버그 1 — 권한 ("관리자만 병합")
- 원인: `apply-normalization`이 `createAdminClient()`(**service_role**)로 `rpc('merge_entities')` 호출 → RPC 내부 `is_admin()`는 `auth.uid()` 기반인데 service_role엔 `auth.uid()`가 없어 false.
- **고침**: `verifyAdmin()`이 **인증된 쿠키 클라이언트(supabase)를 반환**하도록 리팩터 → 그 클라이언트로 `merge_entities`·alias 작업 수행. (이미 admin 확인됨 + RLS `entity_aliases: admin 관리` 통과.) `createAdminClient`는 이 경로에서 제거.

## B. 버그 2 — alias ON CONFLICT
- 원인: `entity_aliases` 유니크가 `unique (lower(alias))`(함수형 인덱스)인데 `.upsert(..., { onConflict: 'alias' })`는 컬럼 `alias`의 제약을 찾아 실패.
- **고침**: upsert/onConflict 제거. **기존 alias 선조회 후 새 것만 plain insert**:
  ```ts
  const cands = group.newAliases.map(a => a.trim()).filter(Boolean)
  const lowers = cands.map(a => a.toLowerCase())
  const { data: existing } = await supabase
    .from('entity_aliases').select('alias').in... // lower 비교: 가능하면 ilike/exact set
  // 클라이언트에서 lower 집합 만들어 미존재만 필터
  const fresh = cands.filter(a => !existingLowerSet.has(a.toLowerCase()))
  if (fresh.length) await supabase.from('entity_aliases').insert(fresh.map(alias => ({ entity_id: group.canonicalId, alias })))
  ```
  - (대안: 행별 insert + `23505` 무시. 단 select-filter가 에러 스팸 없음.) 글로벌 unique라 다른 엔티티가 이미 그 alias를 가지면 skip(정상).

## C. 백그라운드 실행 (전체/순차)
`crawl-now`(#P9)의 **`progress.ts` 스토어 + 폴링** 패턴 미러:
- `POST /api/admin/entities/apply-normalization` 입력을 **`{ groups: NormalizationGroup[] }`(배치)** 수용(단일도 1개 배열로). `maxDuration 300`.
- 작업을 백그라운드 잡으로: **jobId 발급 → progress 스토어에 {total, done, merged, aliasAdded, errors[]} 기록** → 즉시 jobId 반환. (Vercel에서 응답 후 작업 유지가 필요하면 #P9와 동일 기법 사용: `progress.ts` 폴링/`waitUntil` 등 기존 방식 재사용.)
- `GET /api/admin/entities/apply-normalization?jobId=` → 진행 상태 반환.
- 각 그룹: B의 merge 루프 + alias. **그룹 단위 오류는 errors에 누적**하고 계속(부분 실패 graceful).
