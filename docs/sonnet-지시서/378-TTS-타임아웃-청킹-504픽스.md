# 지시서 378 — 브리핑 TTS 504 타임아웃 픽스 (maxDuration 상향 + 스크립트 청킹)

> 대상: 구현 에이전트 · 관리자 전용 · **신규 SQL 없음** · 375(Gemini TTS) 후속 버그픽스
> ⚠️ 읽을 것: `src/app/api/admin/briefings/[id]/tts/route.ts`(현 `maxDuration = 60`) · `src/lib/tts/synthesize-briefing.ts`(375 — Gemini 호출·`AbortSignal.timeout(60_000)`·PCM→WAV·월 캡) · 참고: `src/app/api/admin/insights/route.ts`·`competitor-weekly/route.ts`(둘 다 `maxDuration = 300`) · `AGENTS.md`

## 증상 (David, 콘솔)
`POST /api/admin/briefings/{id}/tts` → **504(Gateway Timeout)**(직전 500). "TTS 요청 중 네트워크 오류". 긴 모닝브리핑 스크립트를 한 번에 Gemini TTS로 합성하다 **60초 함수 한도 초과**. (competitor-weekly/analysis 404는 별개·무관.)

## 원인
- TTS 라우트 `maxDuration = 60` + 내부 fetch `AbortSignal.timeout(60_000)` → 긴 스크립트 합성이 60초를 넘겨 타임아웃. 다른 무거운 라우트는 300초.
- 스크립트 **청킹 없음** — 단일 요청이 Gemini TTS의 시간·입력길이 한도에 취약.

## 작업 (`synthesize-briefing.ts` + tts route)

### 1. maxDuration 상향
- tts route `export const maxDuration = 300`(60→300). 다른 장시간 라우트와 동일.

### 2. 스크립트 청킹 합성 (핵심)
- 브리핑 `script`를 **문장/문단 경계 기준으로 안전한 크기 청크**(예: 청크당 ~1,000~2,000자, Gemini TTS 단일요청 한도 내)로 분할.
- 각 청크를 **순차 합성**(무료 티어 rate limit 고려 — 청크 간 소폭 간격·429 시 백오프 재시도 1~2회). 각 응답 PCM(base64)을 디코드해 **PCM 버퍼들을 이어붙인 뒤 마지막에 한 번 WAV 헤더로 래핑**(375의 WAV 래퍼 재사용, 샘플레이트 동일 가정·응답 mime로 검증). → 단일 `.wav` 산출.
- 청크별 **개별 timeout**(예: 각 60초)로 두고 전체는 maxDuration(300) 안에서 완료. 한 청크 실패 시 명확한 에러(어느 청크·사유)로 중단.
- voice/model/캡 로직은 유지. 캡은 전체 `script.length` 기준 1회 체크(기존대로).

### 3. 에러 표면화(500 원인 규명)
- 실패 시 `reason`에 **구체 원인**(Gemini HTTP 상태·429·업로드 버킷 없음·청크 인덱스) 포함해 반환/로그. 특히 **`briefings` Storage 버킷 부재**면 그 안내(report-covers 때처럼) — 버킷 없으면 업로드 500. (버킷 생성은 ops.)

## 회귀 / 주의
- 짧은 스크립트(단일 청크)도 정상 동작(청킹이 1개면 기존과 동일 경로). WAV 이어붙임 시 **샘플레이트·채널 일관성** 확인(청크마다 동일).
- 월 캡·`increment_tts_usage`(provider='gemini')·`audio_url` 갱신 유지. verifyAdmin 유지.
- 무료 티어 429는 청크 단위 백오프 후에도 지속되면 명확 에러. 색 토큰·한국어.
- 검증: `tsc`·ESLint·`check-prefetch`·`build` + (키·버킷 준비 후 dev)긴 브리핑 오디오 생성 → 504 없이 완성·재생, 짧은 것도 정상, 버킷 없으면 명확 안내.
