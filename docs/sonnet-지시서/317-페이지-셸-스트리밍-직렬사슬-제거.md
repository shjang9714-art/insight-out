**페이지 함수 안의 `await` 는 화면 전체를 막는다.** 그걸 자식 컴포넌트로 내려 `<Suspense>` 아래에 두면 **껍데기가 먼저 뜬다.**

## 1. 현행 진단 (검증된 코드 사실)

### 1.1 316이 한 일과, 그래서 드러난 것

**316으로 prefetch 폭주는 죽었다** — DevTools에 UUID 이름 RSC 요청이 **0개**. ✅
**가려져 있던 진짜 비용이 이제 보인다:**

```
entities   816ms · 791ms      ← 실제 대기시간
contents   958ms · 506ms      ← 브라우저 → Supabase 직접(§6)
services   292ms / sources 237ms

```

### 1.2 🔴 `await` 가 페이지 함수 본문에 있으면 Suspense 는 무력하다

`<Suspense>` 는 **자식 컴포넌트**만 구한다. **페이지 함수 자신이 `await` 로 멈추면 껍데기조차 못 나간다.**

| 페이지 | 페이지 본문 `await` | Suspense | 판정 |
|---|---|---|---|
| **`trending`** | `:64` `:70` `:92` `:109` `:112` | **0** | 🔴 전부 막힘 |
| **`entities`** | `:35` `:39` `:55` `:60` `:68` `:75` | 1개(`EntityTabs`만) | 🔴 **데이터가 Suspense 밖** |
| **`briefings`** | `:19` `:20` `:36` | **0** | 🔴 |
| **`reports`** | `:17` `:33` | **0** | 🟡 |
| `issues` | `:1` | 3 | ✅ 이미 됨 |
| `dashboard` 홈 | `:55` | 4 | ✅ 이미 됨 |

**`issues`·`dashboard` 홈이 정답 형태다. 그걸 나머지에 복사하는 것이 이 슬라이스다.**

### 1.3 🔴 `entities` 는 5회 **직렬** 왕복이다

`view=watchlist`(기본값) 경로:
```
entities/page.tsx:55   await getUser()                        ⛔ 끝나야
entities/page.tsx:60   await getMajorCompaniesData(...)       ← 시작한다
  major-companies.ts:42   Promise.all([curated_groups, curated_companies])
  major-companies.ts:74   await insight_cards
  major-companies.ts:98   await contents          ← rawCards 의 id 가 필요(진짜 의존)
  major-companies.ts:121  await user_watchlist    ← userId 만 필요(의존 아님) ⛔
```
- **`:121 user_watchlist` 는 `:74`·`:98` 을 기다릴 이유가 없다.** `userId` 만 있으면 된다.
- **`:98 contents` 는 `:74` 의 결과가 필요하다.** 이건 진짜 의존이라 못 푼다.
- ⚠️ **`view` 3개(`watchlist`/`competitor`/`trend`)는 배타적이라 요청당 하나만 돈다.** 6개가 다 도는 게 아니다.

### 1.4 ⚠️ `dashboard` 2.07초를 쫓지 말 것

홈은 **이미 전부 Suspense**다(`dashboard/page.tsx:59-51`). **스트리밍 응답에서 DevTools "시간" 열은 스트림이 닫힌 시각**이지 사용자가 기다린 시간이 아니다.
→ **317이 성공하면 다른 페이지도 저렇게 "느려 보이게" 된다.** 그게 정상이다. **숫자가 아니라 체감으로 판단할 것.**

## 3. 구현

### 3-0. ⭐ 먼저 **어디에 시간이 있는지** 본다 — David, 코드 0

**816ms 중 네트워크(서울↔Vercel 시드니 ~170ms)와 서버 렌더가 각각 얼마인지 우리는 모른다.**

> **Vercel → 프로젝트 → Observability → Functions** 에서 `/dashboard/entities` 의 **실행 시간(p75/p95)** 을 본다.

| 서버 실행 시간 | 뜻 | 다음 |
|---|---|---|
| **~50ms 이하** | 시간은 **네트워크**에 있다 | 3-1(체감)만 하고 **리전 이전**으로 간다 |
| **300ms 이상** | 시간은 **서버**에 있다 | 3-1 + **3-2(직렬 사슬)** 둘 다 |

**이 숫자 없이 3-2를 하면 또 헛다리다.** 3-1은 어느 쪽이든 이득이라 **지금 해도 된다.**

### 3-1. ⭐⭐ 페이지 셸을 먼저 내보낸다 — **4개 페이지, 같은 수술**

**`contents/[id]`(316 §3-2)에 한 것과 동일한 패턴이다.** 그걸 그대로 복사한다.

**패턴:**
```
page.tsx (서버)
  - searchParams 파싱만 (await 지만 네트워크 아님 — 그대로 둔다)
  - 즉시 껍데기 렌더: PageContainer + 탭 + 제목
  - 데이터는 자식 컴포넌트로:
      <Suspense fallback={<스켈레톤/>}>
        <XxxContent {...파라미터} />     ← 여기서 await 한다
      </Suspense>
```

**대상 4개:**

| 파일 | 껍데기(즉시) | Suspense 안으로 |
|---|---|---|
| `dashboard/trending/page.tsx` | 제목·날짜 선택 UI | `:92` `:109` `:112` 의 데이터 조회 전부 |
| `dashboard/entities/page.tsx` | `PageContainer` + `EntityTabs` | `:55` `:60` `:68` `:75` — **뷰별 컴포넌트로 분리** |
| `dashboard/briefings/page.tsx` | 제목 | `:36` supabase 조회 |
| `dashboard/reports/page.tsx` | 제목 | `:33` `getPublishedReports` |

⚠️ **`fallback={null}` 을 남발하지 말 것.** 목록 페이지는 **스켈레톤**을 준다 — 빈 화면이 번쩍이면 오히려 느껴 보인다.
**`dashboard/loading.tsx` 의 기존 스켈레톤 톤을 재사용할 것.** 새 스타일을 짓지 말 것.

⚠️ **`entities` 는 뷰가 3개다.** 뷰마다 다른 데이터를 부르므로 **뷰별로 컴포넌트를 나눠** 각각 Suspense 로 감싼다. **탭(`EntityTabs`)은 껍데기에 남긴다** — 탭이 즉시 보여야 사용자가 클릭할 수 있다.

⛔ **`force-dynamic` 을 지우지 말 것.** 모든 페이지가 `cookies()` 를 읽어 어차피 동적이다.

### 3-2. `entities` 직렬 사슬 — **3-0에서 서버 시간이 300ms 이상일 때만**

`src/lib/entities/major-companies.ts`

**`:121 user_watchlist` 를 `:74 insight_cards` 와 병렬로 돌린다.** `userId` 만 필요하고 `rawCards` 에 의존하지 않는다.

```ts
const [rawCardsRes, watchRes] = await Promise.all([
  supabase.from('insight_cards')...,
  userId ? supabase.from('user_watchlist')... : Promise.resolve({ data: [] }),
])
// :98 contents 는 rawCards 의 id 가 필요하므로 이 뒤에 그대로 둔다 — 진짜 의존이다.
```

⛔ **`:98 contents` 를 병렬로 옮기려 하지 말 것.** `rawCards` 의 id 가 있어야 조회할 수 있다. **억지로 풀면 전체 스캔이 된다.**

⚠️ **`userId` 가 없을 때(비로그인) `user_watchlist` 를 아예 부르지 말 것.** 지금 코드의 조건 분기를 유지한다.

### 3-3. `trending` 폴백 사슬

`trending/page.tsx:92` → 실패 시 `:109 fetchFallbackTop()` → 그 안에서 `cookies()` + `fetchIssueActivity()`.
**폴백이 타면 왕복이 2배가 된다.** 3-1로 Suspense 안에 들어가면 **껍데기는 안 막히므로 급하지 않다.** 지금은 건드리지 말 것.

## 4. 회귀 가드

- ⛔ **`force-dynamic` 을 지우지 말 것.** `cookies()` 때문에 어차피 동적이고, 실수로 캐시되면 **사용자 데이터가 섞인다.**
- ⛔ **`staleTimes`(`next.config.ts`)·316의 `prefetch={false}` 를 되돌리지 말 것.**
- ⛔ **`:98 contents` 를 `:74 insight_cards` 와 병렬화하지 말 것**(§3-2). 진짜 의존이다.
- **`entities` 의 탭 3개(주요기업·경쟁사 최근 뉴스·경쟁사 주간) 동작 불변.** 뷰별 배타 분기를 유지할 것 — **3개를 다 부르게 만들면 3배 느려진다.**
- **비로그인 상태에서 죽지 않을 것.** `getUser()` 가 null 을 반환하는 경로가 이미 있다(`entities:90` `{user && …}`).
- **빈 상태 UI 불변**(`entities:92-98` "준비 중"·"동향이 아직 없습니다").
- **`trending` 의 날짜 파라미터·폴백 경로 불변.**
- ⚠️ **스켈레톤을 새로 디자인하지 말 것.** `dashboard/loading.tsx` 톤 재사용.
