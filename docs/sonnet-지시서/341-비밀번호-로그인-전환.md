## 0. 한 줄

**OTP는 "가입 시 이메일 인증" 1회용으로 강등하고, 상시 로그인은 비밀번호로 바꾼다.** 비번 미설정자와 비번을 잊은 사람은 **같은 경로**(코드 받기 → 비번 설정)를 걷는다.

---

## 1. 현행 진단 (2026-07-13 워킹트리 확인)

### 1.1 지금은 **완전 패스워드리스**다
`src/components/login/LoginCard.tsx` (321줄)
- `:101` `signInWithOtp({ email, options: { shouldCreateUser: true } })` → `:139` `verifyOtp({ type: 'email' })` → `/dashboard`
- `:192` `signInWithOAuth({ provider: 'google' })` → `/auth/callback` (관리자 보조)
- ⛔ **`signInWithPassword` — 전수 grep 0회.** 비밀번호가 **아예 없다.**

### 1.2 🔴 "비번 설정 여부"를 앱이 알 수 없었다 → **340이 해결한다**
- `auth.users.encrypted_password` 는 **앱에서 못 읽는다**(auth 스키마).
- `public.users` 에 관련 컬럼 **0건**.
- → **340 [STEP 1]** 이 `public.users.has_password` 를 만들고, `auth.users` 트리거로 미러링한다.

### 1.3 미들웨어 게이트 순서 (`src/middleware.ts`)
```
:46-48   미로그인 → /login
:107-109 onboarding_completed === false → /onboarding
:115-122 approved 아님 && admin 아님   → /pending
:128-130 /admin/* && role !== 'admin'  → /dashboard
```
게이트 값은 **서명 쿠키 캐시**(`profile-cache-cookie.ts`, TTL **15분**)에서 읽고, 없으면 DB 조회(`:78`).
→ **비밀번호 게이트는 `onboarding` 보다 앞**에 와야 한다(스펙 §7 — 비번 설정 후에만 ACTIVE).

### 1.4 ⚠️ **Supabase 기본 OTP를 그대로 쓴다** — 커스텀 OTP 테이블을 만들지 말 것
스펙의 인증번호 정책(목적별 구분 · 해시 저장 · 실패 5회 · 60초 재전송)은 **Supabase Auth가 내부에서 처리**한다.
- **목적 구분**: Supabase가 이미 `type: 'email'`(가입/로그인) vs `type: 'recovery'`(비번 재설정)를 분리한다
- **해시 저장 · 일회용 · consumed**: Supabase 내부 처리. 우리가 원문을 저장하지 않는다
- **rate limit**: Supabase 대시보드 설정 (Auth → Rate Limits)
→ ⛔ **`auth_otp_codes` 같은 테이블을 만들지 말 것.** 이미 있는 걸 다시 만드는 것이다(인수인계 §4-2).

### 1.5 기존 사용자 9명 **전원 비번 미설정**
→ 340 [STEP 4] 에서 **어드민 3명만 남기고 6명 삭제**한다(David 결정). 별도 마이그레이션 코드 불필요.

## 3. 구현

### 3-1. 로그인 화면 재구성 (`LoginCard.tsx` 전면 재작성)

**단계(step) 4개:**

```
① password   이메일 + 비밀번호 + [로그인]
             하단: "비밀번호를 잊으셨나요? / 처음이신가요?"  → ② 로 이동

② otp-send   이메일 확인 → [인증 코드 받기]

③ otp-verify 6자리 코드 입력 (자동 제출 · 재전송 60초 쿨다운 · 이메일 변경)

④ set-password  새 비밀번호 + 확인
```

**핵심 — 단일 경로 (David 결정):**
- `signInWithPassword` 실패 시 **"비번 틀림"과 "미설정"을 구분해 알리지 않는다.**
  ```
  "비밀번호가 올바르지 않거나, 아직 설정되지 않았습니다."
  [이메일로 인증 코드 받기]
  ```
- **미설정자·비번 잊은 사람이 같은 길을 걷는다.** 계정 존재 여부가 유출되지 않는다.
- ⛔ **`has_password` 를 이메일 입력 시점에 조회하지 말 것.** 그러면 계정 열거(enumeration)가 된다.
  `has_password` 는 **로그인한 세션의 미들웨어 게이트에서만** 쓴다(§3-3).

**②③ 은 기존 `LoginCard` 의 OTP 로직을 그대로 재사용한다** — `signInWithOtp` · `verifyOtp` · 재전송 쿨다운 · 6자리 자동 제출 · `mapAuthError`.
> ⚠️ **재전송 쿨다운을 30초 → 60초**로 (스펙 권장값).
> ⚠️ `shouldCreateUser: true` **유지** — 최초 가입도 이 경로를 탄다. 도메인 게이팅은 **DB(339) + Hook** 이 막는다.

**④ 비밀번호 설정:**
```ts
await supabase.auth.updateUser({ password })   // OTP 로 인증된 세션에서만 가능
```
- 검증: **최소 8자** · 비밀번호 확인 일치. (스펙에 복잡도 요건 없음 — 과하게 만들지 말 것)
- **`updateUser` 성공 → 340 트리거가 `has_password = true` 로 미러링한다.** 앱이 직접 쓰지 않는다.

**⭐ 가입 vs 재설정의 분기 (스펙 §2-8 ↔ §5-10):**
| 상황 | 비번 설정 후 |
|---|---|
| **최초 가입** (`has_password` 였던 값이 `false`) | **세션 유지 → `/onboarding` 또는 `/dashboard`** (스펙 §2-8 "정상 로그인 세션 발급") |
| **비번 재설정** (이미 `true` 였음) | **`signOut({ scope: 'global' })` → `/login`** (스펙 §5-9,10 "기존 세션 무효화 · 자동 로그인 금지") |

→ **④ 진입 시점의 `has_password` 값**으로 분기한다. `/api/me/has-password` (신설, 세션 기반) 로 조회.
> ⛔ 이 API는 **자기 자신만** 조회한다(`auth.getUser()`). 이메일을 파라미터로 받지 말 것 — 열거 구멍이 된다.

### 3-2. 관리자 Google 진입 — **유지**
`:188-200` `signInWithOAuth` 를 **그대로 둔다.** allowlist 계정만 Hook·DB(339)를 통과한다.
- ⚠️ **Google 계정은 비밀번호가 없다.** `has_password = false` 인데 게이트에 걸리면 **어드민이 로그인 못 한다.**
- → **§3-3 게이트에서 OAuth 사용자를 면제**해야 한다. **이게 이 슬라이스에서 가장 조용히 깨지기 쉬운 지점이다.**

### 3-3. 미들웨어 게이트 — `onboarding` **앞**에 끼운다

```
:46-48   미로그인 → /login
⭐ 신규   has_password === false && OAuth 사용자 아님 && pathname !== '/set-password'
              → /set-password
:107-109 onboarding_completed === false → /onboarding
:115-122 approved 아님 → /pending
:128-130 /admin/* → role 검사
```

- 게이트 값은 `profile-cache-cookie.ts` 의 서명 쿠키에 **`hasPassword` 를 추가**한다(TTL 15분 그대로).
  → ⚠️ **비번을 방금 설정한 사용자가 15분간 `/set-password` 에 갇히면 안 된다.**
  → **비번 설정 성공 시 쿠키를 즉시 무효화**하거나 갱신할 것. **이게 안 되면 아무도 못 들어간다.**
- **OAuth 사용자 판별**: `user.app_metadata.provider === 'google'` (또는 `identities` 에 google 포함).
  **미들웨어에서 세션의 user 객체로 판별 가능하다.**
- `has_password` 컬럼 미적용(42703) 시 → **게이트를 끈다**(전원 통과). *배포 순서가 어긋나도 로그인이 안 죽게.*

### 3-4. `/set-password` 라우트 신설
`src/app/set-password/page.tsx` — 비밀번호 설정 화면(§3-1 ④).
- **미들웨어 `publicPaths` 에 넣지 말 것.** 로그인된 세션에서만 접근한다.
- 이미 `has_password === true` 인데 들어오면 → `/dashboard` 로 되돌린다.

### 3-5. "로그인 유지" — **이번엔 만들지 않는다**
스펙 §3에 있지만, `@supabase/ssr` 는 **쿠키 기반 세션**이라 런타임 토글이 간단하지 않다.
**"동작하는 척"하는 체크박스를 만들면 그게 인수인계 §4-1의 graceful-silent다.**
→ **§6 후속으로 뺀다.** 지금은 Supabase 기본(지속 세션)을 쓴다.

## 4. 회귀 가드

- 🔴 **어드민 Google 로그인이 깨지면 아무도 어드민에 못 들어간다.** OAuth 사용자는 **`has_password` 게이트 면제**(§3-2·3-3). **가장 위험한 지점이다.**
- 🔴 **비번 설정 직후 쿠키 갱신**(§3-3). 안 하면 15분간 `/set-password` 에 갇힌다.
- ⛔ **커스텀 OTP 테이블을 만들지 말 것**(§1.4). Supabase Auth가 이미 다 한다.
- ⛔ **`has_password` 를 이메일로 조회하는 공개 API를 만들지 말 것.** 계정 열거 구멍이다.
- ⛔ **`updateUser({ password })` 외의 방법으로 비번을 쓰지 말 것.** `public.users` 에 비번을 저장하지 말 것.
- ⛔ **`lib/users/update-profile.ts` 의 화이트리스트를 건드리지 말 것**(335). `has_password` 는 **트리거가 쓴다** — `SELF_WRITABLE` 에 넣지 말 것.
- **`shouldCreateUser: true` 유지.** 최초 가입 경로다. 도메인은 DB(339)가 막는다.
- **`/auth/callback` 유지** — Google OAuth가 쓴다.
- **`has_password` 컬럼 미적용(42703) 시 게이트를 끈다.** 배포 순서가 어긋나도 **로그인이 죽으면 안 된다.**
- **`middleware.ts` 의 `publicPaths`(`/login`·`/auth/callback`·`/api/cron`·`/api/mcp` 등)를 건드리지 말 것.**
- **온보딩·`/pending`·`/admin` 게이트 순서를 바꾸지 말 것.** 비번 게이트만 **맨 앞**에 추가한다.
