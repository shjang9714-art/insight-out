## 0. 한 줄
경쟁사 주간 브리핑 생성은 **유일하게 `EnrichJobs` 체계 밖**(생짜 `fetch`)이라, 화면을 떠나면 진행이 사라진다. `briefing-tts` 패턴대로 등록해 **Dock 에서 진행이 유지**되게 한다.

---

## 1. 착수 전 확인 결과 (직접 코드 확인 2026-07-22)

### 1.1 "제3 그룹"은 필요 없다 — `itemScoped` 가 답
백로그 §1.3 에서 *"ai-jobs 목록에 뜰까 봐 제3 그룹이 필요할 수 있다"* 고 우려했으나, **확인 결과 이미 있는 메커니즘으로 해결된다.**
```ts
// enrich-jobs.ts:343
export function getEnrichJobs(surface): EnrichJobMeta[] {
  return ENRICH_JOBS.filter(j => j.surface === surface && !j.itemScoped)  // ← itemScoped 는 목록에서 제외
}
```
- `admin:briefing-tts` 가 `itemScoped: true` 라 `/admin/ai-jobs`·`/admin/enrich` **목록에 안 뜬다.**
- 반면 `EnrichJobsDock` 은 `runs.values()` **전체**를 표시한다(`itemScoped` 무관). 확인함(`EnrichJobsDock.tsx:27`).
- → **주간 브리핑 생성을 `itemScoped: true` 로 등록하면 목록엔 안 뜨고 Dock 엔 뜬다.** 정확히 원하는 동작.

### 1.2 갈아끼울 지점
`AdminCompetitorWeeklyGenerate.tsx:37` — 로컬 `isGenerating` state + 생짜 `fetch('/api/admin/competitor-weekly', POST)`. 화면 언마운트 시 진행 소실.

### 1.3 ⚠️ "배선만"이 아니다 — 결과 표시 설계가 하나 있다
현재 이 화면은 **398 에서 공들인 인라인 성패 표시**를 한다: `reason` 유무로 성패를 가르고, 성공 시 `사업영역 N개 — AIDC · 보안 · 클라우드` 를 보여준다(`areas`).

`EnrichJobs` 러너(`executeJob`)는 **표준 잡 결과**(`{processed, succeeded, ...}`)를 다루지, competitor-weekly 의 커스텀 응답(`{weekStart, areas, reason}`)을 인라인으로 보여주지 않는다. `briefing-tts` 도 완료 후 상세를 인라인 표시하지 않고 **`BriefingManager` 가 목록을 refetch** 해 결과를 반영한다.

→ **이 슬라이스의 유일한 판단: 398 의 인라인 결과 표시를 어떻게 할 것인가.** §3 에서 방향을 정한다.

## 2. 구현 — A. 레지스트리 등록

`src/lib/admin/enrich-jobs.ts`

### 2.1 key 추가
```ts
export type EnrichJobKey =
  | ...
  | 'admin:competitor-weekly'   // 신규
```

### 2.2 메타 추가 (`briefing-tts` 와 같은 형태)
```ts
{
  key: 'admin:competitor-weekly',
  label: '주간 브리핑 생성',
  endpoint: '/api/admin/competitor-weekly',   // {id} 치환 없음 — 그대로 POST
  usesLlm: true,
  surface: 'ai',
  kind: 'once',
  method: 'POST',
  itemScoped: true,   // ← 목록 제외 + Dock 표시의 핵심
  confirm: '최근 완결된 주(월~일)의 경쟁사 동향을 사업영역별로 종합한 주간 브리핑을 생성하시겠습니까? (LLM 호출)',
}
```
- `getJobCopy`(ai-jobs) 의 `switch` 는 **건드리지 않는다.** `itemScoped` 라 그 목록에 안 오므로 렌더러가 필요 없다. (없으면 `default: throw` 를 타는지 확인 — ai-jobs 페이지가 `getEnrichJobs('ai')` 로 목록을 만들고 itemScoped 는 필터되므로 `getJobCopy` 에 도달하지 않는다. **확인만.**)

### 2.3 ⚠️ `executeJob` 의 `once` 경로가 이 응답을 수용하는지 확인
`briefing-tts` 도 `once`·`itemScoped`·POST 라 **이미 검증된 경로**다. competitor-weekly 응답이 그 경로에서 성공/실패로 처리되는지 `executeJob` 을 읽고 확인한다. **러너를 competitor-weekly 때문에 고치지 말 것** — 고치면 다른 잡이 깨진다. 응답이 안 맞으면 §3-B(서버에서 표준 필드 겸용 반환)로 우회.

## 3. 구현 — B. 화면 전환

`AdminCompetitorWeeklyGenerate.tsx`

### 3.1 `startJob` 으로 전환
```ts
const { runs, startJob } = useEnrichJobs()
const runId = buildEnrichRunId('admin:competitor-weekly')   // itemId 없음 — 동시 1개
const run = runs.get(runId)
const isGenerating = run?.status === 'running'

// 버튼:
onClick={() => startJob('admin:competitor-weekly', undefined, undefined, '주간 브리핑 생성')}
```
- `itemId` **없음**(고정 단일 실행). 주간 생성은 동시에 하나만 돌면 된다 — `startJob` 이 `runs.get(runId)?.status === 'running'` 이면 무시하므로 중복 클릭 방어가 공짜다.
- `confirm` 은 **메타의 `confirm` 이 startJob 안에서 뜬다.** 화면의 `window.confirm` 은 **제거**(이중 확인 방지).
- 로컬 `isGenerating` state 제거, `run?.status` 로 대체.

### 3.2 🔴 결과 표시 — 두 방향 중 택1 (구현자 판단, §7 기록)

**방향 A (권장 — briefing-tts 답습):** 인라인 상세를 **목록 refetch 로 이전**.
- 생성 완료(`run?.status === 'done'`) 시 `CompetitorWeeklyHub` 의 `발행 브리핑` 목록을 refetch 해 새 초안이 뜨게 한다.
- 화면엔 진행/완료 간단 문구만("생성 중… / 완료 — 발행 브리핑 탭 확인"). 상세(areas)는 목록 항목에서 본다.
- 장점: briefing-tts 와 일관. 러너 표준 흐름. 단점: 398 의 `areas` 인라인 표시가 사라진다.

**방향 B (인라인 유지):** 서버 응답을 표준 잡 결과에 **겸용 필드로 실어** 러너 완료 상태에서 꺼내 인라인 표시.
- `generate.ts` 응답에 `{ processed:1, succeeded: sections>0?1:0, ..., areas, reason }` 를 함께 반환.
- `run` 의 완료 페이로드에서 `areas`·`reason` 을 읽어 398 문구를 그대로 유지.
- 장점: 398 표시 보존. 단점: API 응답 형식 변경(범위 밖 살짝), 러너 페이로드 구조 의존.

→ **A 를 기본으로 하되, `executeJob` 이 완료 결과 페이로드를 화면에 노출하지 않으면 A 로 확정.** 노출하면 B 도 가능. **어느 쪽을 택했는지 §7 에 기록.**

### 3.3 하지 말 것
- `generate.ts` 의 **생성 로직·판정을 바꾸지 않는다**(방향 B 라도 응답 필드 추가만).
- `EnrichJobsProvider`·`EnrichJobsDock`·`executeJob` **무수정**(9개 화면 공용).
- `getJobCopy` 에 competitor-weekly 렌더러를 **추가하지 않는다**(itemScoped 라 불필요, §2.2).
- 396 의 탭 4개 구성을 건드리지 않는다.

## 4. 회귀 가드
1. **생성 버튼 → Dock 에 "주간 브리핑 생성" 진행이 뜬다.**
2. **다른 탭·다른 어드민 화면으로 이동해도 Dock 진행이 유지된다**(이 슬라이스의 목적).
3. 새로고침 시 `interrupted` 로 복원된다(`EnrichJobsProvider` 기존 동작).
4. 생성 완료 후 **발행 브리핑 목록에 새 초안이 뜬다**(A) 또는 인라인 결과가 뜬다(B).
5. **실패 시 사유가 보인다**(398 의 `reason` — A면 Dock/목록, B면 인라인).
6. `admin:competitor-weekly` 가 **`/admin/ai-jobs`·`/admin/enrich` 목록에 뜨지 않는다**(itemScoped).
7. 중복 클릭 시 두 번 실행되지 않는다(`running` 가드).
8. `briefing-tts`·`briefing-highlights` 등 **기존 잡이 그대로 동작**한다(러너 무수정).
9. 크론(`/api/cron/competitor-weekly`)은 **영향 없다**(별도 경로, 402 로 하루 1회).

## 7. 기록란 (구현자가 채울 것)

| 항목 | 결과 |
|---|---|
| `executeJob` 의 `once` 경로가 competitor-weekly 응답을 수용하는가 | **수용한다.** `normalizeEnrichResult`에 성공(`sections>0`) 표준 결과를 추가했고, `reason` 또는 `sections=0`은 오류로 변환해 기존 Provider가 Dock에 실패 사유를 표시한다. 성공·실패 계약을 `tsx`로 실행 확인. |
| 결과 표시 방향 A(목록 refetch) / B(인라인 유지) 중 택 | **A.** 완료 상태를 Hub가 감지해 `router.refresh()`하고, 보고서 ID·`generated_at` key로 목록을 새 서버 props에 맞춰 갱신한다. 생성 패널에는 간단한 완료 안내만 남긴다. 인앱 브라우저 미가용으로 라이브 왕복은 미확인. |
| B라면 `generate.ts` 응답에 추가한 필드 | 해당 없음. API·`generate.ts` 무수정. |
| `getJobCopy` 도달 여부(itemScoped 필터로 미도달 확인) | **미도달.** `getEnrichJobs('ai')` 결과에 `admin:competitor-weekly`가 포함되지 않음을 실행 확인했다. |
| 러너·Dock 무수정 확인 | **확인.** `EnrichJobsProvider.tsx`·`EnrichJobsDock.tsx`의 `origin/main` 대비 diff 0건. |
