## 3. 구현

### 3.1 재생 시점까지 다운로드를 미룬다 (두 파일 공통)

`new Audio(url)` 로 즉시 생성하지 말고, **`preload='none'` 을 src 지정 *전에* 설정**한다. 순서가 중요하다 — `new Audio(url)` 처럼 생성자에 URL 을 넘기면 preload 를 나중에 바꿔도 이미 로드가 시작된 뒤다.

```ts
const audio = new Audio()
audio.preload = 'none'      // ← src 보다 먼저
audio.src = briefing.audio_url
```

이것만으로 **재생 전 전송량 0** 이 된다. 객체·이벤트 리스너·ref 구조는 그대로 두므로 나머지 로직을 건드릴 필요가 없다.

> 대안(재생 클릭 시 객체 생성)은 채택하지 않는다. `togglePlay`·`handleSeek`·`handleRestart` 가 모두 `audioRef.current` 존재를 전제하므로 분기가 늘고 회귀 위험이 커진다.

### 3.2 총 재생시간 표시가 깨지지 않는지 확인
`preload='none'` 이면 `loadedmetadata` 가 재생 전까지 발화하지 않는다. 그러나 **`FloatingBriefingMini.tsx:93` 이 이미 DB 의 `audio_duration_seconds` 로 duration 을 세팅**한다:
```ts
if (briefing.audio_duration_seconds) startTransition(() => setDuration(briefing.audio_duration_seconds!))
```
따라서 진행 바와 `--:--` 표시는 그대로 동작한다. **`MorningBriefingPlayer` 도 같은 폴백이 있는지 확인하고, 없으면 동일하게 추가할 것.**

### 3.3 이중 다운로드 원인 규명
`preload='none'` 을 넣으면 증상은 사라지지만 **원인은 남는다.** 재생을 눌렀을 때 또 두 번 받으면 안 된다.

- 오디오 생성 `useEffect` 의 의존성은 `[briefing?.audio_url, briefing?.audio_duration_seconds]` 다. `setBriefing` 한 번으로 둘이 동시에 바뀌므로 **정상이라면 1회 실행**이다.
- `FloatingBriefingMini` 와 `MorningBriefingPlayer` 가 **동시에 마운트되는 경로가 있는지** 확인할 것(`DashboardShell` + `RightRail` 동시 렌더 여부). 있다면 같은 오디오를 두 객체가 각각 받는다.
- 확인 결과를 §6 에 기록. **원인이 동시 마운트라면 이번 슬라이스에서 고치지 말고 보고만 할 것**(범위 밖).

### 3.4 하지 말 것
- `briefings` **조회 자체는 유지**한다. 버튼 상태(브리핑 있음/없음)와 제목·날짜 표시에 필요하다. 3.01KB 로 가볍다.
- UI·레이아웃·스타일 변경 금지.
- 다른 성능 항목(폰트·표지·키워드 API)에 손대지 말 것. 각각 392·393 이다.

## 4. 회귀 가드
1. **재생 버튼을 누르면 정상 재생**된다. 첫 재생 시 로딩 지연이 생기는데, 그동안 버튼이 죽은 것처럼 보이지 않아야 한다(필요하면 후속 과제로 보고만).
2. **일시정지 · 처음으로(SkipBack) · 진행 바 seek** 이 모두 동작한다. 특히 **재생 전 seek** 은 `preload='none'` 에서 동작이 달라질 수 있다 — 눌러서 확인하고 깨지면 보고할 것.
3. **총 재생시간**이 `--:--` 로 굳지 않고 DB 값으로 표시된다.
4. 오디오가 없는 브리핑(`audio_url` null)의 **스크립트 폴백 UI** 가 그대로 뜬다.
5. 브리핑이 없는 날의 "오늘 브리핑이 없습니다" 표시 유지.
6. `MorningBriefingPlayer` 를 쓰는 `/dashboard/briefings`(BriefingArchive) 도 동일하게 동작한다.

**🔧 §3.3 결론 정정 — "개발 모드 React effect 이중 실행" 은 원인이 될 수 없다**
해당 측정은 **프로덕션**에서 수행됐다(`insight-out-app.vercel.app`, `/api/version` → `env: production`). React StrictMode 의 effect 이중 호출은 **개발 모드 전용**이므로 프로덕션 이중 다운로드를 설명하지 못한다.

**유력 가설(미확정)**: Safari 의 미디어 byte-range 요청 동작. 관측 패턴(8.63MB + 9.42MB 중단 + 50.14KB + 634B)은 Audio 객체 2개보다 **단일 객체가 요청을 중단하고 재요청하는 모양**에 가깝다.
- 확정된 것: **동시 마운트는 원인이 아니다**(RightRail 미사용).
- 미확정: 나머지. **§6 재생 후 측정에서 판별한다** — 재생 시 wav 가 1건이면 Safari range 동작, 2건이면 객체 중복.

### 6.1 목표 미달 사유 — 폰트가 새로운 1위
전송량 목표는 1MB 이하였으나 8.53MB 다. 잔량의 정체는 **폰트**다.

```
PretendardVariable….woff2   2.06MB  (325ms)  initiator: 0.kf5d-6km1r5.js
PretendardVariable….woff2   2.06MB  (192ms)  initiator: contents:1
PretendardVariable….woff2   2.06MB  (132ms)  initiator: contents:2
```
**6.18MB = 잔량의 72%.** 초기화 프로그램이 셋 다 달라 **`@font-face` 중복 선언**이 의심된다.
※ 캐시 비활성화 측정이라 3회 모두 받았다. 실사용은 캐시로 1회지만 **첫 방문 2.06MB** 는 그대로다.
→ **393 로 이관.** 391 의 책임 범위가 아니다.

### 6.2 미실시 — 후속 확인 필요
