## 1. 실측 사실 — 재조사 금지

### 1-1. 버그 증상

키워드 분석 화면(`/dashboard/issues?view=keyword`)에서:

```
급상승 0 · 신규 30 · 관심 지속 0 · 하락 0
급상승 랭킹 → "해당 기준의 키워드가 없습니다"
엔티티 카드 전부 NEW 배지
상단 경고 → "집계 대상 콘텐츠가 상한을 넘어 일부 구간이 잘렸습니다"
```

### 1-2. 원인 — 분류 산식이 아니라 `prev` 집계가 비어 있다

`src/lib/keywords/ranking.ts` 의 산식은 **정상이다.**

```
급상승   = !isNew && changePct > 0
신규     = isNew                       // isNew = (prev === 0 && cur > 0)
관심 지속 = cur > 0 && prev > 0
```

**모든 키워드의 `prev` 가 0이면 전부 `신규`가 되고 나머지 셋은 정의상 0이 된다.**

`prev` 가 비는 이유 — `AiInsightsView.tsx:143-148`:

```ts
.select('matched_groups, matched_keywords, collected_at', { count: 'exact' })
.eq('status', 'published')
.gte('collected_at', fourteenDaysStart)
.order('collected_at', { ascending: false })   // ← 최신 우선
.limit(TREND_ROWS_LIMIT)                        // ← 20000
```

**클라이언트 `.limit()` 위에 서버측 행 상한(PostgREST max-rows)이 있다.**
정렬이 내림차순이므로 **잘리는 쪽은 오래된 구간 = 직전 7일**이다 → `prev` 전멸.

### 1-3. DB 실측 (2026-08-22 01:00 KST, `status='published'`)

| 구간 | 콘텐츠 |
|---|---|
| 14일 전체 | **7,025** |
| 이번 7일 | 3,045 |
| 직전 7일 | **3,980** |

**14일치가 7,025건이라 `limit(20000)` 에는 애초에 걸릴 수 없다.**
그런데 경고가 뜬다는 것은 응답 행이 7,025보다 적게 온다는 뜻이다.

### 1-4. 지시서 525 의 수정은 효과가 없었다

`AiInsightsView.tsx:17-24` 주석이 같은 증상을 기록하고 `limit(1000) → 20000` 으로 올렸다.
**서버 상한이 위에 있으면 클라이언트 상한을 올려도 아무 일도 일어나지 않는다.**
같은 방식(상한 더 올리기)을 다시 시도하지 말 것.

### 1-5. RPC 는 이미 만들어졌고 검증됐다

```sql
public.keyword_week_buckets(p_days integer DEFAULT 14, p_top integer DEFAULT 30)
RETURNS TABLE(name text, total bigint, cur bigint, prev bigint)
-- GRANT EXECUTE TO authenticated 완료
```

**검증 결과 (2026-08-22 실행):**

```
SELECT sum(prev), sum(cur) FROM public.keyword_week_buckets(14, 30);
→ 직전7일합 = 11,905 · 이번7일합 = 8,954
```

**같은 데이터를 DB 에서 세면 `prev` 가 멀쩡히 나온다.** 진단 확정.

### 1-5-1. ⚠️ RPC 는 v3 가 정본이다 — 구간 정의가 앱과 다르다

**v3 의 구간 (David 결정 2026-08-22):**

- 기준일 = KST 자정
- `cur`  = `[오늘-7일, 오늘)`  ← **완료된 7일. 오늘은 들어가지 않는다**
- `prev` = `[오늘-14일, 오늘-7일)` ← 완료된 7일
- 정렬 = 창 전체 빈도(`total`) 내림차순 → 상위 `p_top` 개

**즉 진행 중인 오늘은 집계에서 빠진다.**

기존 앱 코드는 `cur = [오늘-6일, ∞)` 로 **오늘을 포함**하고 `prev` 만 꽉 찬 7일이라
**항상 6.x일 대 7일로 비교**하고 있었다. 이번에 그것도 같이 고친 것이다.

실측 검산 (2026-08-22 01:10 KST):

```
창: 08-08 00:00 ─ 08-15 00:00 ─ 08-22 00:00 (KST)
cur = 12,000 · prev = 13,840 · 고유 키워드 212
```

(구 정의로는 8,954 대 11,905 였다 — 격차의 상당 부분이 오늘이 섞인 탓이었다.)

### 1-5-3. 🔴 v3 는 표기 변형을 묶고 **기사 수**로 센다

`keyword_groups.include_patterns` 에 **같은 대상이 두 표기로 등록돼 있었다.**
매칭(`patternHit`)이 양쪽을 소문자로 낮춰 비교하므로 **항상 둘 다 걸린다.**

| 소문자 | 표기 변형 | 소속 그룹 |
|---|---|---|
| kt | `kt` / `KT` | 경쟁사 · 통신 B2B |
| skt | `skt` / `SKT` | 경쟁사 · 통신 B2B |
| sk텔레콤 | `sk텔레콤` / `SK텔레콤` | 경쟁사 · 통신 B2B |
| sk브로드밴드 | `sk브로드밴드` / `SK브로드밴드` | 경쟁사 · 통신 B2B |
| anthropic | `anthropic` / `Anthropic` | AI 기술 · 빅테크 |
| azure | `azure` / `Azure` | AI 기술 · 빅테크 |
| nvidia | `nvidia` / `NVIDIA` | AI 기술 · 빅테크 |

**실측: `kt`·`KT` 를 가진 기사 510건 중 한쪽만 가진 기사는 0건이다.** 전부 둘 다 갖고 있다.

그래서 v3 는 이렇게 센다:

- **`GROUP BY lower(kw)`** — 표기 변형을 한 줄로 묶는다
- **`count(DISTINCT c.id)`** — `count(*)` 로 세면 같은 기사를 두 번 세서 **510이 1,020이 된다**
- 표시 이름은 **대문자를 포함한 변형**을 고른다 (`kt`/`KT` → `KT`)

효과 실측 — 밀려나 있던 실제 키워드가 상위로 올라온다:

```
v2 Top10: … KT(510) · kt(510)          ← 같은 회사가 두 칸
v3 Top12: … KT(510) · AX(483) · 스마트팩토리(470) · AI 인프라(433)
```

**사전(`keyword_groups`)도 같은 표기로 정규화한다**(David 실행 SQL ②).
그래야 앞으로 새로 들어오는 기사에 중복이 안 박힌다.
⚠️ **`contents.matched_keywords` 과거분은 백필하지 않는다** — `contents` 에는 `WHEN` 절 없는
`BEFORE UPDATE` 트리거가 있어 대량 UPDATE 가 위험하다. **v3 의 읽기 시점 병합으로 커버된다.**

### 1-5-2. 🔴 앱은 구간을 다시 계산하지 않는다

`AiInsightsView.tsx` 의 `thisWeekStartMs`·`prevWeekStartMs`(`:267-268`)로 구간을
**다시 계산하지 말 것.** 구간의 유일한 정의는 RPC 안에 있다. 앱은 `cur`·`prev` 를
받아 쓰기만 한다. **두 벌로 갈라지면 반드시 어긋난다**(이 코드베이스에서 반복된 사고다).

### 1-6. `trendRes` 는 키워드 집계 말고도 쓰인다

같은 응답이 `computeTrendingTopics(...)`(뜨는 토픽, `:257-260`)에도 들어간다.
**`trendRes` 쿼리 자체를 지우면 뜨는 토픽이 죽는다.**

## 2. 작업

### 2-1. 키워드 집계를 RPC 로 전환

`src/components/analysis/AiInsightsView.tsx`

1. `keyword_week_buckets` RPC 를 호출한다. 인자는 `(14, 30)` — 현재 `TOP_KEYWORDS_N = 30` 과 같은 값.
2. RPC 결과로 `topKeywords` · `kwCurFreq` · `kwPrevFreq` 를 대체한다.
   - `name` → 키워드 이름
   - `total` → 기존 `kwFreq[name]` (= `KeywordItem.count`)
   - `cur` → 기존 `kwCurFreq[name]`
   - `prev` → 기존 `kwPrevFreq[name]`
3. `classifiedKeywords` 의 나머지 계산(`changePct`·`isNew`·`direction`·`bucket`·`watched`)은
   **그대로 둔다.** 입력만 RPC 로 바뀌는 것이다.
4. `trendRes.data` 를 순회하며 `kwFreq`/`kwCurFreq`/`kwPrevFreq` 를 만들던
   루프(`:270-280`)에서 **`matched_keywords` 집계 부분만** 제거한다.

⚠️ **RPC 호출이 실패하면 조용히 빈 배열로 떨어뜨리지 말 것.**
`error` 를 `console.error` 로 남기고, 키워드 섹션에 **에러 상태를 표시**한다.
`catch { return [] }` 로 삼키면 지금과 똑같이 "데이터가 없는 것처럼" 보인다.

### 2-2. 절단 경고 UI 제거

`AiInsightBoard.tsx:287` 의 문구와 그 배너, 그리고 이를 넘기는
`trendWindowTruncated` prop(`AiInsightBoard.tsx:68`)·계산부(`AiInsightsView.tsx:254-256`)를 제거한다.

**이 경고는 키워드 집계가 잘렸다는 뜻이었고, 2-1 로 원인이 사라진다.**

⚠️ 단 `trendRes` 는 뜨는 토픽에서 계속 쓰이므로 **`count: 'exact'` 자체를 지울지는
`trendWindowTruncated` 외에 `trendRes.count` 를 쓰는 곳이 없을 때만** 판단한다.
쓰는 곳이 있으면 남긴다.

### 2-3. `insight_cards` 주차 조회에 `.limit()` 추가

`src/lib/entities/major-companies.ts:100`

```ts
const { data: rawPeriods, error: periodsError } = await supabase
  .from('insight_cards')
  .select('period_start, period_end')          // ← .limit() 이 없다
```

**현재 `insight_cards` 785행 / PostgREST 상한 1,000 = 78%.**
넘는 순간 주차 목록이 조용히 잘려 **기업동향 주간 아카이브에서 과거 주차가 사라진다.**

- 명시적 `.limit(5000)` 을 붙인다.
- `.order('period_start', { ascending: false })` 를 명시해 잘리더라도 최신 주차가 남게 한다.
- `count: 'exact'` 로 실제 건수를 받아, **수신 건수보다 크면 `console.error` 로 남긴다.**
  (사용자 화면에는 노출하지 않는다.)

## 3. 하지 않을 것

- ❌ **`trendRes` 쿼리를 삭제하지 않는다.** 뜨는 토픽(`computeTrendingTopics`)이 쓴다.
- ❌ **뜨는 토픽 로직을 건드리지 않는다.** 같은 절단이 거기에도 걸려 있지만 **이번 범위가 아니다.**
- ❌ **`ranking.ts` 의 분류 산식을 바꾸지 않는다.** 산식은 정상이다.
- ❌ **키워드 이름을 `lower()` 로 통합하지 않는다.** `Naver`/`OpenAI`/`AI전환`/`AI 전환` 이
  실제로 공존하지만, 통합은 표시 이름까지 바뀌는 별도 결정이다.
- ❌ **앱에서 `cur`/`prev` 구간을 다시 계산하지 않는다.** 구간의 정의는 RPC 안에만 있다(§1-5-2).
  `thisWeekStartMs`·`prevWeekStartMs` 를 키워드 집계에 쓰지 말 것.
- ❌ `.limit()` 을 더 큰 숫자로 올리는 방식으로 해결하지 않는다(§1-4).
- ❌ 죽은 코드 정리·리팩터 확장 금지.
- ❌ **DDL·SQL 작성 금지. 스키마 변경이 필요하면 구현하지 말고 플래너에게 요청할 것.**
  (`keyword_week_buckets` 는 이미 존재한다 — 호출만 한다.)

## 5. 참고 — 화면 수치가 달라진다

두 가지 이유로 수정 후 숫자가 눈에 띄게 바뀐다. **이상한 게 아니다.**

1. **`prev` 가 처음으로 채워진다.** 지금까지 전부 `신규`로만 나오던 것이
   급상승·관심 지속·하락으로 갈라진다.
2. **`하락`이 많게 나올 수 있다.** 수집량 자체가 줄었다 —
   `cur` 12,000 대 `prev` 13,840. 실제 흐름이지 버그가 아니다.
3. **`kt` 같은 소문자 중복 항목이 사라지고** 그 자리에 `AX`·`스마트팩토리` 같은
   실제 키워드가 올라온다(§1-5-3).

또한 `cur` 에서 오늘이 빠지므로 **화면이 "어제까지"를 말한다.**
화면 문구(`최근 7일 기준 · 직전 7일과 비교`)가 이 의미와 맞는지 확인하고,
어긋나면 **문구만** 조정한다(예: `완료된 7일 기준 · 이전 7일과 비교`).
구간을 문구에 맞추지 말고 문구를 구간에 맞춘다.
