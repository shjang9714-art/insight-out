# [04] 추천 점수 SQL 함수 + 피드 API 지시서

## 작업 목적

사용자별 추천 콘텐츠를 슬롯 단위로 반환하는 SQL 함수와 Next.js API 엔드포인트를 구현한다.

## 산출물

- `supabase/2026-06-16-추천점수-함수.sql`
- `app/api/feed/recommended/route.ts`

## 점수 모델 (재확인)

```
score(user, content) =
    0.35 * keyword_match
  + 0.20 * service_match
  + 0.25 * recency_decay
  + 0.10 * source_weight
  + 0.10 * behavioral_boost
  - already_seen_penalty
```

### 컴포넌트 정의

- **keyword_match**: `content_keywords` ∩ `user_preferences.keyword_id`, 일치 키워드들의 weight 합
  - 정규화: `LEAST(sum(up.weight) / 5.0, 1.0)`
- **service_match**: 콘텐츠의 `content_services.service_id` ∩ `user_service_prefs.service_id`이면 weight, 없으면 0 → `LEAST(usp.weight, 1.0)`
  - 한 콘텐츠가 여러 service에 매핑돼 있으면 일치한 prefs의 max(weight) 사용
- **recency_decay**: `EXP(-LN(2) * hours_since_publish / 168)` (7일 반감기). published_at이 없으면 created_at 사용
- **source_weight**: 콘텐츠 source별 사전 가중치 매핑
  - 가트너=1.0, KRG=0.9, 뉴스=0.7, 유튜브=0.6, 기타=0.5
  - 실제 source 컬럼 값(표기 한/영)에 맞춰 CASE 작성. 04 작업 전 distinct 확인 필수.
  - 초기엔 SQL 내 CASE, 추후 `source_weights` 테이블로 분리 가능
- **behavioral_boost**: 사용자가 아카이브/장기 체류한 콘텐츠와 키워드 자카드 유사도
  - 1차 구현: 0 고정 (스킵) — view/archive 누적 후 활성화
  - 또는 최근 7일 view 이력 중 같은 service/source 비율
- **already_seen_penalty**: 최근 14일 내 `content_views` 존재 시 `-0.5`

### Cold start 가중치 조정

Day 0 사용자(view 0건):
- behavioral_boost와 already_seen_penalty 비활성
- 0.35, 0.20, 0.25, 0.10을 그대로 적용해 최대 0.9 스코어

## SQL 함수 시그니처

```sql
CREATE OR REPLACE FUNCTION get_recommended_feed(
  p_user_id UUID,
  p_slot    TEXT,    -- 'personalized' | 'trending' | 'editor' | 'explore'
  p_limit   INT DEFAULT 6
)
RETURNS TABLE (
  content_id     UUID,        -- contents.id 컨벤션 따라 uuid
  score          NUMERIC,
  slot           TEXT,
  reason_keys    TEXT[]       -- 디버그/툴팁용 (매칭된 키워드 이름)
)
LANGUAGE plpgsql
SECURITY DEFINER       -- RLS 우회. 함수 내부에서 user_id 일치 검증 필수.
SET search_path = public
AS $$
BEGIN
  -- ...
END;
$$;
```

### 슬롯별 로직

- **personalized**: 위 점수식 상위 N건
- **trending**: 최근 3일 `content_views` COUNT(*) 상위 N건 (개인 무관)
- **editor**: source IN ('가트너','KRG') AND published_at >= NOW() - INTERVAL '14 days' (또는 수동 큐레이션 플래그 컬럼 신설)
- **explore**: personalized 결과에서 사용한 키워드 집합 **밖**의 키워드를 가진 콘텐츠 중 점수 상위 1~2건

### 보안 (SECURITY DEFINER 사용 시)

함수 첫 줄에서:
```sql
IF p_user_id IS DISTINCT FROM auth.uid() THEN
  RAISE EXCEPTION 'user_id mismatch';
END IF;
```
**GRANT EXECUTE ON FUNCTION get_recommended_feed(...) TO authenticated;**
(anon에는 부여하지 않음)

## API 엔드포인트

`GET /api/feed/recommended?slot=personalized&limit=6`

```ts
// 의사 코드
const supabase = createServerClient(...)
const { data: { user } } = await supabase.auth.getUser()
if (!user) return 401

const slot = searchParams.get('slot') ?? 'personalized'
const limit = Number(searchParams.get('limit') ?? 6)

const { data, error } = await supabase.rpc('get_recommended_feed', {
  p_user_id: user.id,
  p_slot:    slot,
  p_limit:   limit
})

// content_id를 contents 테이블과 join해서 카드 렌더용 데이터 반환
```

## 성능 고려

- `content_keywords`/`content_services` 인덱스 활용도 확인
- 사용자 수 < 100, 컨텐츠 < 10k 가정 → 함수 호출당 < 200ms 목표
- 초과 시 materialized view + 1시간 주기 갱신으로 전환 (후속 작업)

## 검증 기준

- [ ] 함수가 4개 슬롯 모두에 대해 정상 반환
- [ ] `auth.uid()` 불일치 호출 시 예외 발생
- [ ] view 14일 이내 콘텐츠는 결과 상위에서 제외(또는 페널티 적용)
- [ ] 신선도 감쇠: 7일 지난 콘텐츠 점수가 < 0.5로 낮아짐
- [ ] explore 슬롯이 personalized와 키워드 중복 안 되는지
- [ ] API 응답 200ms 이내 (로컬 데이터 기준)
- [ ] EXECUTE GRANT 확인:
  ```sql
  SELECT routine_name, grantee, privilege_type
  FROM information_schema.routine_privileges
  WHERE routine_name = 'get_recommended_feed';
  ```

## 주의사항

- SECURITY DEFINER 함수는 RLS를 우회하므로 user_id 검증이 누락되면 권한 누수. 반드시 첫 줄 검증.
- `search_path = public` 설정 누락 시 search_path injection 위험.
- 점수 가중치는 SQL 내 상수로 둘 것. 운영 중 조정 빈도 높아지면 `recommendation_weights` 테이블로 분리.
- SQL 파일은 `supabase/` 폴더, 컨벤션 유지.
- 위임 시점 커밋 금지.
