# 지시서 232 — 성능 후속(미들웨어 왕복 제거 + 콘텐츠 초기 데이터 서버 렌더)

목표: 231(스켈레톤·병렬화·페이로드) 이후 남는 **구조적 병목**을 줄인다. ① 미들웨어의 매 요청 profile 조회 왕복 제거 ② 콘텐츠 페이지 초기 목록을 서버에서 렌더(브라우저 부팅+fetch 지연 제거). **리스크가 231보다 큼 → 231 배포·체감 측정 후, 여전히 느린 구간만 착수** 권장. 두 파트는 독립.

범위: 인증·필터 동작 결과 불변, 지연만 단축. SQL은 Part A 옵션에 따라 선택.

---

## 1. 현행 진단 (검증된 코드 사실)

### 미들웨어 (`src/middleware.ts`)
- 매 non-API 페이지 요청마다: `getUser()`(Supabase auth 서버 검증, 1왕복) **+ `users` profile 조회**(`onboarding_completed, role, approval_status`, 1왕복). → **모든 이동에 2왕복(≈200ms) 기본 지연.**
- API 라우트는 이미 profile 조회 제외됨(주석 확인). 페이지 이동만 대상.
- gating 로직: 온보딩 미완→/onboarding, 미승인(비관리자)→/pending, /admin은 role 확인.

### 콘텐츠 페이지 (`src/app/dashboard/contents/page.tsx`)
- `'use client'`. searchParams(category/date/svc/src/relevant/page/sort) 읽어 **브라우저 supabase로 목록·카운트 fetch**(useEffect). 상태 다수(items/total/catCounts/scopedSourceIds/services/sources/view/groupByDay), 클라이언트 클러스터링.
- 첫 진입 시 **클라이언트 부팅 → 브라우저 fetch** 순서라 초기 표시 지연(231 loading.tsx가 그사이 스켈레톤만 커버).

## 2. 구현

### Part A — 미들웨어 profile 왕복 제거 (권장·효과 큼, 저~중 위험)
gating 필드를 매번 DB 조회하지 않도록 캐시:

**A안(권장) — 서명 쿠키 캐시**
- 로그인/온보딩완료/승인 변경 시점에 `{ onboarding_completed, approval_status, role }`를 **httpOnly 서명 쿠키**(예: `uo`)로 기록(짧은 TTL, 예 10~30분).
- 미들웨어는 쿠키가 있으면 **DB 조회 생략**하고 쿠키값으로 gating. 쿠키 없거나 만료면 1회 조회 후 재기록.
- 상태 전이(온보딩 완료·승인 승격)에서 **쿠키 무효화/갱신** 필수(안 하면 낡은 gating).
- `getUser()`는 보안상 유지(또는 `getClaims`/로컬 JWT 검증 대체는 별도 검토).

**B안(더 견고, 인프라 필요) — JWT 클레임**
- Supabase `app_metadata`에 `role`·`approval_status`를 심고(로그인 훅/트리거), 미들웨어가 JWT 디코드로 판단 → **DB 왕복 0**. 세팅 파이프라인 필요(범위 큼) → 후순위.

**최소안** — 최소한 **일반 authed 사용자의 반복 조회를 캐시로 제거**(A안 1단계). 미승인 차단 정확성 위해 쿠키 캐시 방식이 안전.

- 회귀 가드: 온보딩/승인/관리자 gating이 **모든 전이에서 정확**해야 함(승인 취소·강등 포함). 쿠키 TTL 짧게 + 전이 시 갱신. 테스트: 미온보딩·미승인·관리자·일반 각 케이스.

### Part B — 콘텐츠 초기 데이터 서버 렌더 (중 위험, 초기 로드 개선)
전면 재작성 대신 **"서버 래퍼 + 클라이언트 인터랙티브 자식"** 패턴:
- `contents/page.tsx`(서버 컴포넌트, 신규 얇은 래퍼): `searchParams`로 **초기 목록·카운트·services/sources**를 서버에서 조회.
- 기존 로직을 `ContentsClient`(클라이언트)로 이동하고 **초기 데이터를 props로 하이드레이션** → 첫 페인트에 데이터 존재(브라우저 fetch 대기 제거).
- 이후 필터 변경은 **router push(서버 재조회)** 또는 기존 클라이언트 fetch 유지 — 택1(초기만 SSR로도 큰 이득).
- 서버 조회는 `createServerClient`(쿠키 인증) 사용 → 브라우저 auth 부팅 제거.
- 리스크: 상태·클러스터링·catCounts가 얽혀 분리 설계 필요 → **초기 목록만 SSR**로 최소 스코프, 나머지 상호작용은 그대로 두는 게 안전.
- 대안: 231로 충분히 빨라지면 **Part B 보류**.

## 3. 회귀 가드
- **미들웨어**: 모든 gating(온보딩·승인·관리자) 정확·전이 반영. 쿠키 위·변조 방지(서명·httpOnly). API 라우트 영향 없음.
- **콘텐츠**: 목록·필터·페이지네이션·카운트·클러스터링 결과 불변. 초기 SSR 데이터와 이후 클라이언트 상태 일치(중복 fetch 방지).
- 로그인/로그아웃·세션 만료 흐름 정상.
- 다크/라이트·모바일 무관.
