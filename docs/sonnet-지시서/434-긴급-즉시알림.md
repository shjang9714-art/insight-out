**critical 운영 이슈가 새로 뜨면 일일 브리핑을 기다리지 않고 즉시 메일.** 429 탐지 재사용, `alerted_at` 로 중복 알림 방지. 트리거는 수희 pg_cron(자주).

## 1. 착수 전 확인
- 429 `detectOpsIssues(admin)`(`src/lib/ops/detect-issues.ts`) — upsert + 자동해결·재발.
- 428 `ops-brief` 라우트(`src/app/api/cron/ops-brief/route.ts`) — 수신자(override or role='admin')·`sendBrevoEmail` 패턴.
- `ops_issues.alerted_at`(수희 434 SQL) — 알림 발송 시각.
- CRON_SECRET 인증(기존 크론 패턴).

## 2. 구현

### 2.1 수신자·발송 공용화 (중복 제거)
- 428 라우트의 수신자 로직(override env → admin 이메일, 없으면 스킵)을 **공용 헬퍼로 추출**: `src/lib/ops/recipients.ts` `getOpsRecipients(admin): Promise<string[]>`. 428·434 공유.
- (부담되면 434에서 복제 가능하나, 추출 권장.)

### 2.2 엔드포인트 `src/app/api/cron/ops-alert/route.ts`
- GET, `Bearer CRON_SECRET`. `runtime='nodejs'`, `maxDuration=60`, `runJob` 래핑(key='cron:ops-alert').
- 흐름:
  1. `await detectOpsIssues(admin)` (최신 탐지·해결 반영).
  2. **신규 critical 조회**: `ops_issues` where `severity='critical' AND status='open' AND alerted_at IS NULL`.
  3. 없으면 `{ ok:true, alerted:0 }`(메일 없음, 조용히).
  4. 수신자 `getOpsRecipients` — 없으면 skip.
  5. **즉시 메일 1통**(여러 건이면 묶어서): 제목 `[인사이트 아웃 🔴 긴급 N건] {대표 title}`, 본문에 각 이슈(title·추정원인·권장조치·발생횟수) + **`/admin/ops-issues` 링크**(절대 URL).
  6. 발송 성공 시 알린 이슈들 `alerted_at = now()` 업데이트.
- graceful: 오류 시 500(다음 실행 재시도), 수신자·critical 없으면 skip.

### 2.3 재발 시 재알림 (429 소폭 수정)
- 429 `detectOpsIssues` 의 **재발(resolved→open) upsert 시 `alerted_at = null`** 로 리셋 → 해결됐다 재발한 critical 은 다시 알림.
- ⚠️ 그 외 429 로직(자동해결·사람 status 보존) **무변경**. `alerted_at` 리셋만 추가.

## 3. 하지 말 것
- **warning/notice 즉시 알림 금지** — 긴급은 critical만(나머지는 일일 브리핑 §428).
- 이미 알린 critical **재발송 금지**(`alerted_at` 가드) — 스팸 방지.
- 428 일일 브리핑·429 자동해결 로직 무변경(수신자 추출·alerted_at 리셋 외).
- 새 스키마 코드에서 만들지 않기(alerted_at 은 수희 SQL).
- pg_cron 은 수희(코드 아님).

## 4. 회귀 가드
1. 새 critical 이슈 발생 → **즉시 메일**(다음 pg_cron 실행 때), `/admin/ops-issues` 링크 포함.
2. 같은 critical 재실행 시 **재발송 안 됨**(alerted_at).
3. critical 없으면 메일 없음(조용).
4. 해결됐다 **재발한 critical 은 다시 알림**(재발 시 alerted_at null).
5. warning/notice 는 즉시 알림 안 감(일일 브리핑에만).
6. 수신자 없으면 skip, 428 일일 브리핑·429 무영향.
