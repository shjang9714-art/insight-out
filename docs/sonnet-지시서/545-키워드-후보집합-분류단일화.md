## 2. 선행 SQL — David 실행 (`키워드주간집계-RPC-v4-2026-08-22.sql`)

**v3 와 시그니처가 같다.** `CREATE OR REPLACE` 로 덮이며 인자도 그대로라
**앱 수정 전에 실행해도 화면이 깨지지 않는다.** v4 의 유일한 차이는 `HAVING` 한 줄이다.

```sql
CREATE OR REPLACE FUNCTION public.keyword_week_buckets(
  p_days integer DEFAULT 14,
  p_top  integer DEFAULT 30
)
RETURNS TABLE(name text, total bigint, cur bigint, prev bigint)
LANGUAGE sql
STABLE
SECURITY INVOKER
SET search_path TO 'public'
AS $$
  WITH b AS (
    SELECT
      ((date_trunc('day', now() AT TIME ZONE 'Asia/Seoul')
        - make_interval(days => (greatest(p_days,2)/2) * 2)) AT TIME ZONE 'Asia/Seoul') AS start_ts,
      ((date_trunc('day', now() AT TIME ZONE 'Asia/Seoul')
        - make_interval(days => (greatest(p_days,2)/2)))     AT TIME ZONE 'Asia/Seoul') AS mid_ts,
      ((date_trunc('day', now() AT TIME ZONE 'Asia/Seoul'))  AT TIME ZONE 'Asia/Seoul') AS end_ts
  ),
  src AS (
    SELECT c.id, unnest(c.matched_keywords) AS kw, c.collected_at
    FROM public.contents c CROSS JOIN b
    WHERE c.status = 'published'
      AND c.deleted_at IS NULL
      AND c.collected_at >= b.start_ts
      AND c.collected_at <  b.end_ts
      AND c.matched_keywords IS NOT NULL
  )
  SELECT
    (array_agg(src.kw ORDER BY (src.kw = lower(src.kw)), src.kw))[1]::text                  AS name,
    count(DISTINCT src.id)::bigint                                                          AS total,
    count(DISTINCT src.id) FILTER (WHERE src.collected_at >= (SELECT mid_ts FROM b))::bigint AS cur,
    count(DISTINCT src.id) FILTER (WHERE src.collected_at <  (SELECT mid_ts FROM b))::bigint AS prev
  FROM src
  GROUP BY lower(src.kw)
  HAVING count(DISTINCT src.id) >= 3     -- ★ v4: 최소 노출량 (1~2건 노이즈 제외)
  ORDER BY 2 DESC, 1
  LIMIT greatest(p_top, 1)
$$;

-- 검증) p_top 을 크게 주면 153개 안팎이 나오고, 신규 후보(prev=0,cur>0)가 포함돼야 한다
SELECT count(*) AS 키워드수,
       count(*) FILTER (WHERE prev=0 AND cur>0) AS 신규후보
FROM public.keyword_week_buckets(14, 500);
```

### 2-1. ⚠️ RPC 성능 — 이미 실측했다. 느리지 않다

첫 시도에서 `keyword_week_buckets(14, 300)` 이 `statement timeout(57014)` 로 실패했다.
플래너가 원인을 실측했다.

| 측정 조건 | 실행 시간 |
|---|---|
| 인라인 쿼리 | 151 ms |
| 함수 호출, 세션 첫 회 | 3,636 ms |
| 함수 호출, 이후 | 142 ms |
| **함수 호출, `authenticated` 롤 + RLS 적용** | **265 ms** |

**운영과 같은 조건에서 265ms** 다. `authenticated` 의 `statement_timeout = 8s` 대비 3% 다.
`count(DISTINCT)` 를 제거한 대안도 175ms 로 차이가 없어 **본문은 그대로 둔다.**

⇒ **타임아웃은 함수 설계 문제가 아니다.** 05:00 KST 크롤이 `contents` 에 쓰는 시간대와
겹쳐 경합했을 가능성이 크다. **다시 호출하면 된다.**
또 실패하면 **구현하지 말고 실패 시각과 오류 원문을 그대로 보고할 것.**

## 3. 작업

### 3-1. 후보 집합 확대 — `AiInsightsView.tsx`

RPC 호출 인자를 바꾼다.


`TOP_KEYWORDS_N` **30 → 300** 으로 올린다. 상수 이름도 의미에 맞게
`KEYWORD_CANDIDATE_CAP` 정도로 바꾸고, **왜 300 인지 한 줄 주석**을 남긴다
(실측 153개, 안전 여유. 상한이지 목표치가 아니다).

⚠️ **비용 가드 확인** — `getKeywordDailyCounts` 온디맨드 집계는
`rankKeywords(classifiedKeywords, 'rising')` 결과(**최대 10개**)에만 돈다.
후보가 늘어도 **이 호출 수가 10을 넘지 않는지 반드시 확인**한다(351-D 가드).
넘으면 구현하지 말고 보고할 것.

### 3-2. 🔴 분류 기준을 한 곳으로 — `src/lib/keywords/ranking.ts`

**분류 함수를 하나 만들고 타일 카운터와 랭킹이 그것만 쓰게 한다.**

```ts
export type KeywordTrendClass = 'new' | 'rising' | 'sustained' | 'falling' | 'none'

/** 관심 지속 완충폭(%) — 이 안이면 "변화 없음"으로 본다. David 결정 2026-08-22. */
export const SUSTAINED_BAND_PCT = 20

export function classifyKeyword(k: KeywordItem): KeywordTrendClass {
  const cur = k.cur ?? 0
  const prev = k.prev ?? 0
  if (prev === 0) return cur > 0 ? 'new' : 'none'
  const pct = ((cur - prev) / prev) * 100
  if (pct >  SUSTAINED_BAND_PCT) return 'rising'
  if (pct < -SUSTAINED_BAND_PCT) return 'falling'
  return 'sustained'
}
```

- `rankKeywords()` 의 필터를 `classifyKeyword(k) === mode` 로 바꾼다.
- `AiInsightBoard.tsx:269-276` 의 카운터 네 개도 **같은 함수로** 센다.
- ⚠️ **두 곳에 조건을 각각 쓰지 말 것.** 이 지시서의 핵심이다.

정렬 규칙은 현행 유지 — `sustained` 는 `cur+prev` 합 내림차순, 나머지는
`changePct` 내림차순 → `cur` 내림차순.

### 5-1. 🔴 핵심 불변식 — 네 분류의 합 = 후보 개수

**브라우저 대신 스크립트로 확인한다.** RPC 를 직접 호출하고, 그 결과에
`classifyKeyword()` 를 그대로 적용해 네 분류를 센다.

- 워크트리에 임시 스크립트를 만들어 실행한다(`tsx`/`ts-node`/`node --experimental-strip-types` 중 되는 것).
- **이 스크립트는 커밋하지 않는다.** 실행 후 지운다.
- Supabase 접속은 저장소의 기존 환경변수를 쓴다. 새 키를 만들지 않는다.

확인할 것:

```
RPC 응답 행 수                     = N
new + rising + sustained + falling = N   ← 정확히 같아야 한다
```

**두 값과 네 분류 각각의 수를 보고에 적는다.** 안 맞으면 분류가 잘못된 것이다.

참고 — 2026-08-22 02:00 KST 플래너 실측(데이터가 바뀌면 달라진다):

```
키워드 153 = 신규 6 + 급상승 59 + 관심 지속 22 + 하락 66
```

### 5-2. 신규가 0이 아닌지

`classifyKeyword` 결과 중 `new` 가 **1개 이상**이어야 한다.
2026-08-22 실측 기준 `SK이노베이션`(cur 35) 등 6개가 나온다.
**0이면 후보 상한(§3-1)이 안 올라간 것이다.**

### 5-3. 판정 기준이 한 곳인지

`classifyKeyword` 를 쓰는 호출부를 전부 나열한다.
`ranking.ts` 의 랭킹 필터와 `AiInsightBoard.tsx` 의 타일 카운터가
**둘 다 이 함수만** 쓰고, 조건식을 따로 쓴 곳이 없어야 한다.

`grep -rn "changePct\|isNew" src/` 결과에서 **분류 판정에 쓰인 곳이
`classifyKeyword` 안뿐인지** 확인해 보고한다.
