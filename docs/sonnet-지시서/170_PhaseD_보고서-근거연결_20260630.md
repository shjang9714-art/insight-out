## 1. Step 0 — 보고서 스키마 라이브 실측 (★차단 단계, 먼저 보고)

**구현 전, 아래를 라이브 Supabase에서 실측하고 결과를 보고할 것.** 레포의 마이그레이션 파일이 아니라 실제 DB를 본다(과거 #54 무음실패·proxy.ts 죽은코드 교훈).

```sql
-- A. 보고서 관련 테이블 존재 확인
select table_name from information_schema.tables
where table_schema='public' and table_name ilike '%report%';

-- B. 보고서 본체 컬럼 (테이블명은 A 결과로 치환, 예: reports)
select column_name, data_type, is_nullable
from information_schema.columns
where table_schema='public' and table_name='reports'
order by ordinal_position;

-- C. 보고서-콘텐츠/이슈 연결 테이블이 이미 있는지 (report_contents, report_sources, report_evidence 등)
select table_name from information_schema.tables
where table_schema='public'
  and (table_name ilike '%report%content%' or table_name ilike '%report%source%'
       or table_name ilike '%report%evidence%' or table_name ilike '%report%section%');

-- D. 보고서 섹션 구조가 별도 테이블인지 / 본문이 JSON 컬럼인지 (B의 컬럼에서 sections/body/content jsonb 여부 확인)

-- E. 라이브 건수
select count(*) from reports;   -- 테이블명 치환
```

**보고할 분기 질문:**
1. 보고서 본문이 **JSON/구조화 컬럼**인가, **섹션 테이블**인가? (근거를 어디에 붙일지 결정)
2. 보고서↔근거 **연결 테이블이 이미 있나?** 있으면 컬럼·건수, 없으면 신설 필요.
3. 보고서가 **이슈 기반**으로 생성되나(issue_id 보유), **콘텐츠 직접 선택**인가, 둘 다인가? (#P56 워크벤치 동작 확인)
4. 라이브 보고서 건수 ≥ 1 (검증용 샘플 확보).

> Step 0 결과에 따라 아래 2장이 **Case A(연결 테이블 신설)** 또는 **Case B(기존 구조 재사용)**로 갈린다. 결과 보고 후 구현 진행.

## 2. 데이터 구조 (Step 0 결과로 확정)

### Case A — 연결 테이블이 없을 때: 신설
파일: `supabase/2026-06-30-report-evidence.sql`

```sql
-- 보고서 근거 연결: 보고서 ↔ (콘텐츠 또는 이슈)
create table if not exists public.report_evidence (
  id          uuid primary key default gen_random_uuid(),
  report_id   uuid not null references public.reports(id) on delete cascade,
  content_id  uuid references public.contents(id) on delete cascade,
  issue_id    uuid references public.issues(id) on delete cascade,
  note        text,
  created_at  timestamptz not null default now(),
  -- 콘텐츠 또는 이슈 중 하나는 있어야 함
  constraint report_evidence_target_chk check (content_id is not null or issue_id is not null)
);

create index if not exists idx_report_evidence_report on public.report_evidence(report_id);

-- ★ GRANT 필수
grant select, insert, update, delete on public.report_evidence to anon, authenticated;
```

> RLS 사용 중이면 보고서 소유자만 쓰도록 정책 추가(기존 reports RLS 패턴 따를 것). RLS 미사용이면 GRANT만으로 충분.

### Case B — 이미 연결 구조가 있을 때
신규 테이블 만들지 말고 기존 컬럼/테이블 재사용. Step 0 결과를 지시서에 주석으로 남기고 아래 UI/뷰어만 진행.

### (공통) 읽기 편의 뷰 — 보고서 근거 펼치기
이슈를 근거로 넣은 경우 그 이슈의 근거 콘텐츠까지 한 번에 보이게 하려면 `issue_evidence`(Phase A)와 조인. 보고서 상세에서는 클라이언트 쿼리로 충분하므로 **신규 뷰는 선택**. 표면 최소화 원칙상 우선 클라이언트 쿼리 권장.

## 3. 워크벤치 — 근거 선택·연결 UI

위치: `/dashboard/reports/new`(및 편집 화면이 있으면 그쪽도).

요구사항:
- 보고서 작성 중 "근거 추가" 영역: 콘텐츠 검색/선택(기존 콘텐츠 목록 재사용) 또는 이슈 선택

## 4. 뷰어 + PDF — "근거" 섹션

위치: 보고서 상세/뷰어, 그리고 PDF 내보내기(#P57) 출력.

요구사항:
- 보고서 하단 "근거" 섹션: 연결된 콘텐츠 카드(title, source_name, published_at, 원문 링크) + 연결된 이슈(제목 → 이슈 상세 링크)
- 이슈 근거는 `issue_evidence`로 그 이슈의 근거 콘텐츠 건수/배지도 요약 표시(선택)
- PDF 출력에도 동일 "근거" 섹션 포함(텍스트·링크). 썸네일은 PDF에선 생략 가능
- 0건일 때 빈 상태 문구

> 논조 배지는 이번 차수 제외(sentiment 미채움).
