## 0. 한 줄
실제 시간은 **17.9MB → 2.80MB, 1.18초 → 761ms** 로 줄었다. 이제 **남은 건 연출**이고, 핵심은 **스켈레톤이 실제 카드와 다르게 생겨서 데이터 도착 시 화면이 뛰는 것**이다.

## 1. 원칙

> **최초 로딩 = 정확한 스켈레톤 / 재조회 = 기존 목록 유지 + 진행선**

스켈레톤은 **정확할 때만** 스피너보다 낫다. 부정확한 스켈레톤은 스피너보다 나쁘다 — 지금이 그 경우다.

(참고: Firebase 콘솔이 중앙 스피너 하나를 쓰는 건 **본문 모양을 예측할 수 없기** 때문이다. 우리는 항상 카드 그리드라 모양이 확정적이므로 스켈레톤이 맞다. **단, 약속한 모양이 실제와 같아야 한다.**)

## 2. 현행 진단 (확인된 코드 사실)

**스켈레톤이 두 개이고, 둘 다 실제 카드와 다르다.**

| | 썸네일 | 패딩 | 구성 |
|---|---|---|---|
| **실제 카드** (`ContentCard.tsx:131~`) | `aspect-[16/9]` **있음** | `p-4` | 배지·출처 → 해시태그 → 제목 2줄 → 요약 2줄 → 발행일(`mt-auto`) |
| `contents/loading.tsx` (라우트) | **있음** | `p-5` | 제목 2줄 → 요약 2줄 |
| `ContentsBoard.SkeletonCard`(123행) | **없음** ❌ | `p-5` | 배지 2개 → 제목 2줄 → 요약 3줄 → 하단 1줄 |

따라서 **스켈레톤A → 스켈레톤B → 실제 카드**로 모양이 세 번 바뀐다. 특히 B에는 썸네일 영역이 없어서, 데이터가 오는 순간 **없던 16:9 사진이 카드마다 튀어나오며 레이아웃이 크게 뛴다.** 디렉터가 지적한 깜빡임의 정체다.

**그 밖에**
- **칩 영역이 조건부 렌더**다(`{keywordChips.length > 0 && ...}`, 550행). 칩은 `/api/contents/keywords` 응답 후 나타나므로 **늦게 등장하며 아래 목록을 밀어낸다.** (392로 빨라져도 없어지지 않는다.)
- **전환 시 목록을 비운다.** `isLoading && page === 1`(589행)이면 `items` 유무와 무관하게 스켈레톤으로 전환된다.
- **초기 카테고리 이중 쿼리**(272행) — `/dashboard/contents` 무파라미터 진입 시 `category=''` 로 1차 쿼리 후 `router.replace('?category=뉴스')` 로 2차 쿼리.
- 카드↔목록 전환은 **이미 재조회하지 않는다**(`newsView` 가 fetch effect 의존성에 없음). 건드리지 말 것.

## 3. 구현

### 3.1 스켈레톤 한 종류로 통일 — 이 슬라이스의 본체

**공용 컴포넌트 신규**: `src/components/contents/ContentCardSkeleton.tsx`

`ContentCard` 의 실제 DOM 구조를 그대로 따른다.

```
<div class="flex h-full flex-col rounded-2xl border border-border bg-card overflow-hidden">
  <div class="aspect-[16/9] bg-muted" />              ← 썸네일 (필수)
  <div class="flex flex-1 flex-col p-4">              ← p-5 아님, p-4
    배지 2개 (rounded-full, h-[18px])
    해시태그 2~3개 (rounded-full)
    제목 2줄
    요약 2줄
    발행일 1줄 (mt-auto)
```

- `contents/loading.tsx` 와 `ContentsBoard` **양쪽이 이 컴포넌트를 쓴다.** 모양 정의가 두 곳에 존재하면 안 된다.
- 그리드 클래스도 실제와 동일하게: `grid gap-5 grid-cols-[repeat(auto-fill,minmax(300px,1fr))]`

**막대 길이 변주** — 현재 6개가 완전 복제본이라 인공적이다. `index` 를 받아 제목 길이·요약 줄 수·메타 폭을 3~4가지 패턴으로 순환시킨다. 랜덤 금지(하이드레이션 불일치).

**명암 규칙** — `배경 < 스켈레톤 면 < 카드 경계`. 현재 흰 배경 대비가 너무 낮아 "로딩 중"이 아니라 "덜 그려진 페이지"로 읽힌다. **진하게 만들기보다 미세한 펄스**로 전달한다. **좌우로 흐르는 shimmer 는 쓰지 않는다**(뉴스 화면에서 산만).

### 3.2 전환 시 이전 목록 유지

`isLoading && page === 1` 조건(589행)을 **`items.length === 0` 일 때만** 스켈레톤으로 가도록 바꾼다.

- 이미 목록이 있으면: `setItems` 를 비우지 않고 목록에 `opacity-[0.85]` + **콘텐츠 영역 상단 2px 진행선**(브랜드 마젠타) + 새 데이터 도착 시 120~180ms 페이드.
- 적용: 카테고리 탭 전환 · 키워드 칩 선택 · 검색 · 페이지네이션 · 상세→목록 복귀.
- **원형 스피너를 쓰지 않는다.** 목록 *전체*가 갈리는 상황이라 우상단 소형 스피너는 "국소 갱신" 신호가 되어 범위가 맞지 않는다. 진행선이 "이 영역 전체가 갱신 중"을 정확히 말한다.
- 결과가 0건이면 그때 기존 빈 상태 UI를 보여준다(이미 있음).

### 3.3 로딩 사다리

| 경과 | 표시 |
|---|---|
| ~200ms | **아무것도 표시하지 않는다** |
| 200ms ~ | 스켈레톤 (뜨면 **300~400ms 최소 유지**) |
| 1.5s ~ | 섹션 제목 옆 `최신 콘텐츠를 불러오는 중` |
| 5s ~ | `데이터 응답이 평소보다 늦어지고 있습니다` + `다시 시도` |

⚠️ **200ms~1.5s 구간에 문구를 함께 띄우지 않는다.** 스켈레톤이 이미 "로딩 중"을 말하므로 신호가 중복된다. **문구는 1.5s 이후에만.**
⚠️ 최소 유지시간이 없으면 경계값에서 반대 방향 깜빡임이 남는다. 지연과 최소 유지는 **세트로** 넣을 것.

### 3.4 칩 영역 높이 예약
`{keywordChips.length > 0 && ...}` 를 **항상 렌더**하되 비어 있을 때 최소 높이를 갖도록 바꾼다(칩 한 줄 높이 기준). 칩이 늦게 도착해도 아래 목록이 밀리지 않아야 한다.

### 3.5 초기 카테고리 확정
`/dashboard/contents` 무파라미터 진입 시 1차 쿼리(`category=''`)가 나가지 않도록 한다. 서버에서 확정하거나(`050b4a6`/#90 의 서버 확정 패턴 참고) 카테고리가 정해지기 전 첫 쿼리를 미룬다.
**⚠️ `?category=뉴스` 로 직접 진입하는 경로(nav 4개 링크)는 지금도 1회이므로 회귀시키지 말 것.**

### 3.6 보이는 상태와 실제 동작의 일치
로딩 중에도 **검색창을 비활성화하지 않는다.** 확인 결과 현재 검색은 URL 파라미터를 바꾸는 방식이라 로딩 중에도 정상 동작한다. **활성 유지가 맞다.**

## 4. 회귀 가드
1. `?category=` 4개 진입(뉴스·웹인사이트·유튜브·외부리포트)이 그대로 동작한다.
2. **카드↔목록 뷰 전환 시 재조회가 발생하지 않는다**(현재 정상 — 회귀시키지 말 것).
3. 검색·키워드 칩·페이지네이션(`더 보기`)이 모두 동작한다.
4. 결과 0건일 때 빈 상태 UI가 정상 표시된다.
5. `queryError` 분기(587행)가 그대로 동작한다.
6. 리스트 뷰(`ContentRowList`)에도 전환 연출이 일관되게 적용된다.
7. 하이드레이션 경고가 새로 생기지 않는다(막대 변주에 랜덤 금지).

## 6. (끼워넣기) 경쟁사 주간 브리핑 — 인용 마커 정규식 보강

> 별건이지만 한 줄짜리라 이 커밋에 함께 넣는다(디렉터 결정 2026-07-20).

**현상**: 경쟁사 주간 브리핑 본문에 UUID 인용 마커가 그대로 노출된다.

**원인**: `src/lib/text/strip-llm-artifacts.ts` 의 정규식이 **단일·정형 UUID 하나**만 잡는다.
```js
const INLINE_UUID_MARKER = /\s*\[[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}\]/g
```

실제 본문으로 테스트한 결과:

| 본문 | 결과 |
|---|---|
| `[2693b1e-ff49-47e3-9ac5-6838ed2152a6]` | ❌ 첫 그룹 **7자리** (LLM 오기) |
| `[e803d5da-…, 0122e121-…]` | ❌ **콤마로 2개 나열** |
| `[a355428-d6f9-…]` | ❌ 첫 그룹 **7자리** |
| `[e803d5da-d0ff-4130-aec1-65e92b450608]` | ✅ 정상 제거 |

**조치**: 정규식을 **복수 나열**과 **자릿수 흔들림**까지 견디도록 보강한다. 대략 이런 형태 — hex 그룹을 범위로 두고, 콤마+공백 구분 반복을 허용한다.
```js
const UUIDISH = /[0-9a-fA-F]{6,8}(?:-[0-9a-fA-F]{3,4}){3}-[0-9a-fA-F]{10,12}/
const INLINE_UUID_MARKER = new RegExp(
  String.raw`\s*\[\s*${UUIDISH.source}(?:\s*,\s*${UUIDISH.source})*\s*\]`, 'g'
)
```

⚠️ **과잉 매칭 주의.** 대괄호 안의 일반 텍스트(예: `[참고]`, `[LG U+]`)를 지우면 안 된다. 하이픈 구분 hex 패턴을 반드시 요구할 것. **단위 테스트로 위 4개 케이스 + 정상 텍스트 케이스를 함께 확인할 것.**

**삭제·재생성은 하지 않는다.** 정제가 렌더 시점(`cleanNarrative`)에 일어나므로 정규식만 고치면 **기존 발행본도 즉시 정상 표시**된다.

> 참고(범위 밖): 7자리 UUID는 LLM이 잘못 적은 것이다. 표시상으로는 가려지지만 **그 문장의 근거는 여전히 추적 불가**다. 이는 표시 문제가 아니라 근거 검증 문제이며, `docs/골드샘플-주간리포트-2026-W28.md` §3(패스 ③ 자동 검증)이 다룰 사안이다. **이번에 손대지 않는다.**
