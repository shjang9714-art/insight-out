> 선행: #4·#12·#13 머지됨. **서비스별 키워드 seed(`supabase/2026-06-03-키워드-seed.sql`)가 수희 Supabase 에 적용된 후** 실제 태깅이 동작(미적용이어도 코드는 안전, 매칭 0건일 뿐).
> 설계 근거: 크롤링 파이프라인 설계 §5 "적재 후 content_services/content_keywords 매핑". 충돌 시 본 지시서 우선.
> ⚠️ 작업 전 `AGENTS.md` + 현재 `src/lib/crawler/orchestrator.ts`·`quality.ts`·`dedup.ts` 를 읽고 현행 흐름에 맞출 것.

## 0. 목표 (한 줄)
크롤러가 콘텐츠 적재 직후, 등록 키워드를 제목/본문에 매칭해 **`content_keywords`(콘텐츠↔키워드)** 와 **`content_services`(콘텐츠↔서비스)** 를 자동 태깅한다 → 사용자의 "담당 서비스별 큐레이션"(#18 필터)이 실제 데이터로 작동.

## 1. 현행 흐름 (반드시 먼저 읽기)
- `runCrawl` 가 키워드를 1회 로드(현재 `select('name')`, #13 관련도용) → `crawlOne(admin, source, since, keywords)` 전달.
- `crawlOne` 루프: dedup 3단계 → 품질 제외(#13) → near-dup(#12) → 관련도 status 판정(#13) → `row` 구성 → `admin.from('contents').insert(row)` (id 미반환).
- 태깅하려면 **insert 가 새 content.id 를 반환**해야 하고, **키워드 객체에 `id`·`service_id`** 가 있어야 함.

## 2. 할 일

### 2.1 키워드 로드 확장 (runCrawl)
- 키워드 조회를 `select('id, name, service_id')` 로 변경 → `keywords: { id: string; name: string; service_id: string | null }[]`.
- `crawlOne` 시그니처의 `keywords` 타입을 위 객체 배열로 변경(`src/lib/types.ts` 의 `Keyword` 일부 사용 가능).
- **#13 관련도 호출 호환**: `relatednessScore(qText, keywords.map(k => k.name))` 로 이름 배열만 넘김(기존 로직 유지).

### 2.2 insert 가 id 반환하도록 (crawlOne)
```ts
const { data: insertedRows, error: insertError } = await admin
  .from('contents')
  .insert(row)
  .select('id')          // ← 새 id 반환
if (insertError) {
  // 기존 23505/에러 처리 그대로
} else {
  const newId = insertedRows?.[0]?.id
  if (contentStatus === 'pending') counts.held++; else counts.inserted++
  if (newId) await tagContent(admin, newId, qText, keywords)   // ← 신규 태깅
}
```
- ⚠️ `.select()` 를 붙이면 반환 타입이 배열이 됨 — `insertedRows?.[0]?.id` 로 접근(또는 `.select('id').single()` 사용 시 단건). 23505(중복 URL)는 여전히 `counts.duplicate++` 후 스킵(태깅 안 함).

### 2.3 태깅 함수 (orchestrator 내 또는 dedup/별도 모듈)
```ts
async function tagContent(admin, contentId, text, keywords) {
  const lower = text.toLowerCase()
  const matched = keywords.filter(k => lower.includes(k.name.toLowerCase()))
  if (matched.length === 0) return   // 매칭 키워드 없음 → 태깅 없음(단독)

  // content_keywords (PK: content_id, keyword_id)
  await admin.from('content_keywords').upsert(
    matched.map(k => ({ content_id: contentId, keyword_id: k.id })),
    { onConflict: 'content_id,keyword_id', ignoreDuplicates: true }
  )
  // content_services (PK: content_id, service_id) — 매칭 키워드의 distinct service_id
  const serviceIds = [...new Set(matched.map(k => k.service_id).filter((v): v is string => !!v))]
  if (serviceIds.length) {
    await admin.from('content_services').upsert(
      serviceIds.map(sid => ({ content_id: contentId, service_id: sid })),
      { onConflict: 'content_id,service_id', ignoreDuplicates: true }
    )
  }
}
```
- 매칭은 #13 관련도와 **동일한 includes 방식**(일관성). 오류는 try/catch 로 잡아 로그만(태깅 실패가 적재를 막지 않게).

### 2.5 관련도 보류 게이트 OFF (결정 B — 중요)
키워드 seed 가 들어가면 #13 관련도 게이트가 자동으로 켜져, 키워드 미매칭 기사가 전부 `pending`(숨김)이 된다. **현재 키워드 커버리지가 좁고 어드민 승인 큐도 없어, 정당한 기사까지 과도하게 숨길 위험** → **게이트는 OFF로 유지하고 태깅만 켠다.**
- `quality.ts` 에 플래그 추가: `export const RELATEDNESS_GATING_ENABLED = false`
- `orchestrator.ts` 의 status 판정을 플래그로 감싼다:
  ```ts
  const score = relatednessScore(qText, keywords.map(k => k.name))
  const status: 'pending' | 'published' =
    (RELATEDNESS_GATING_ENABLED && score !== null && score < RELATEDNESS_THRESHOLD)
      ? 'pending' : 'published'
  ```
  → 지금은 **전부 `published`**(아무것도 안 숨김). 태깅(§2.3)은 게이트와 무관하게 그대로 수행.
- 주석으로 "키워드 커버리지 충분 + 어드민 승인 큐 구축 후 `true` 로 전환" 명시.

### 2.4 건드리지 말 것
- dedup·near-dup·멱등·응답계약 로직 변경 금지(태깅 + 게이트 플래그만 추가).
- `schema.sql`·`types.ts` 변경 불필요(`content_keywords`/`content_services` 이미 존재).

## 3. 동작 요약 (게이트 OFF 기준)
- 모든 적재 기사는 `published` 로 보임(숨김 없음).
- 등록 키워드가 매칭되는 기사는 `content_keywords`·`content_services` 로 **태깅** → 담당 서비스별 필터(#18)에 노출.
- 매칭 안 되는 기사는 태깅 없이 그대로 게시(서비스 필터엔 안 잡힘). 보류 게이트는 후속에 ON 전환.
