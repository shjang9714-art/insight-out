# 지시서 194 — 제외 규칙 효과 리포트: hit_count 집계 + 최근 차단 가시화

> 작성: Opus(Cowork) · 2026-07-05 · 레인: 양질 콘텐츠 수집 체계(트랙 B)
> 근거: 190에서 `hit_count` 컬럼만 두고 **어디서도 증가시키지 않음**(항상 0). 규칙이 실제로 무엇을 얼마나 걸렀는지 안 보여 "반복 방지"가 관측 불가. 190을 관측 가능하게 만들어 다음 단계(195 자동 제외 후보 제안)의 신호 토대를 만든다.
> 협업 루프: 로컬(커밋X). David 위임 → 구현 → Opus 검증 → "커밋". **SQL 핸드오프 1건(`194-exclusion-hit-tracking.sql`). LLM 없음.**
> 선행: 190(exclusion_rules·matchExclusion·ExclusionRulesManager).

---

## 0. 한 줄

크롤 런 종료 시 **매칭된 제외 규칙별 hit_count 를 배치로 누적**(아이템별 update 아님)하고 `last_hit_at` 을 갱신한다. 어드민 제외 규칙 화면을 **효과 리포트**로 격상 — 많이 거른 규칙 우선 정렬, 최근 차단 시점, "아직 안 걸린 규칙"(정리 후보) 표시, 상단 요약("규칙 N개 · 지금까지 X건 차단").

## 1. 현행 진단 (검증된 코드 사실)

- `matchExclusion`(quality.ts:188)은 이미 `{ action, ruleId }` 를 반환 → **매칭 규칙 id 를 잡고 있음**. 그런데 `hit_count` 를 증가시키는 코드가 **전무**(grep: 표시 `ExclusionRulesManager.tsx:230`·타입 정의뿐). 즉 리포트가 보여줄 데이터가 0.
- 크롤 진입부(orchestrator, 크롤 런 최상위 함수)에서 `exclusionRules` 를 1콜 로드(`id, rule_type, value, action, is_active`) 후 `Promise.allSettled` 로 소스별 `crawlOne`/`crawlYoutube` 에 전달. `processCrawlItem`(320~)에서 `matchExclusion` 호출.
- `exclusion_rules.hit_count` 는 190 SQL 에 이미 존재(default 0). `last_hit_at` 은 없음 → 194 SQL 에서 추가.

## 2. DB / SQL (수희 핸드오프)

`docs/sql-handoff/194-exclusion-hit-tracking.sql` — 이미 작성·**먼저 커밋·푸시**.
- STEP1: `exclusion_rules.last_hit_at timestamptz` 추가(`add column if not exists`, 멱등).
- STEP2: `increment_exclusion_hits(hits jsonb)` RPC — `{ "<rule_id>": <delta>, ... }` 를 받아 `hit_count += delta`, `last_hit_at = now()` 원자적 갱신(read-modify-write 경쟁 없음).
- 미적용 시 194 코드는 graceful skip(RPC 없음/컬럼 없음 → hit_count 0·last_hit_at null 유지, 리포트는 "아직 집계 전").

## 3. 구현

### 3-1. 집계 — 크롤 런 단위 배치 (`orchestrator.ts` + `quality.ts`)

- 크롤 런 최상위 함수에서 `exclusionRules` 로드 옆에 **런 단위 누적 맵** 생성:
  ```ts
  const exclusionHits = new Map<string, number>()  // ruleId → 매칭 수(reject+hold 합산)
  ```
- `exclusionRules` 를 넘기는 경로와 **동일하게** `exclusionHits` 를 `crawlOne`/`crawlYoutube` → `processCrawlItem` 까지 스레드(후행 옵션 파라미터 `exclusionHits: Map<string, number> = new Map()` — 기존 호출부 무변경 컴파일).
- `processCrawlItem` 에서 `matchExclusion` 결과가 있으면 **판정 직후 1회** 카운트(reject/hold 공통 — 둘 다 "걸림"):
  ```ts
  const exclusionMatch = matchExclusion({ title: item.title, url }, exclusionRules)
  if (exclusionMatch) {
    exclusionHits.set(exclusionMatch.ruleId, (exclusionHits.get(exclusionMatch.ruleId) ?? 0) + 1)
  }
  ```
  (Node 단일스레드 · get→set 사이 await 없음 → `Promise.allSettled` 동시 실행에도 안전.)
- `Promise.allSettled` **완료 후**(결과 집계 즈음) 1콜로 flush:
  ```ts
  if (exclusionHits.size > 0) {
    try {
      const { error } = await admin.rpc('increment_exclusion_hits', {
        hits: Object.fromEntries(exclusionHits),
      })
      if (error) console.warn('[크롤러] exclusion hit 집계 skip (194 SQL 미적용 가능):', error.message)
    } catch (e) {
      console.warn('[크롤러] exclusion hit 집계 실패:', e)
    }
  }
  ```
- **매칭/판정 로직은 무변경** — hit 집계는 순수 관측(부가). `counts.rejected`/`held` 등 기존 카운트 불변.

### 3-2. 타입·API (`src/lib/admin/exclusion-rules.ts` + `/api/admin/exclusion-rules`)

- `ExclusionRuleRow` 에 `last_hit_at: string | null` 추가.
- GET select 에 `hit_count, last_hit_at` 포함(기존에 hit_count 이미 반환 중). **42703(컬럼 없음) graceful**: last_hit_at 미포함 재시도 또는 `select('*')` 유지 후 매핑에서 `?? null`(148/155 패턴). 규칙 목록 정렬 `order('hit_count', desc)` 서버 적용(활성 우선은 클라 보조 정렬 가능).

### 3-3. 효과 리포트 UI (`ExclusionRulesManager.tsx`)

- **상단 요약 줄**(AdminSectionHeader 아래, 기존 v2 스타일): `규칙 N개 · 지금까지 X건 차단`(X = hit_count 합). 활성인데 `hit_count === 0` 인 규칙 M개면 `· 아직 안 걸린 규칙 M개`(중립 톤, 그린 없음 — 정리 후보 힌트). 전부 0이면 "아직 집계 전(수집 1회 후 반영)" 안내.
- **정렬**: hit_count 내림차순(많이 거른 규칙이 위). 비활성은 기존처럼 `opacity-50`.
- **hit_count 셀**: `> 0` 이면 `text-foreground font-medium`(강조), `0` 이면 `text-muted-foreground`. 숫자만.
- **"최근 차단" 컬럼 신설**: `last_hit_at` → `formatKst` 상대 표기("N일 전"/"오늘"), null 이면 `—`. `≥ 30일` 이면 risk 아닌 중립 caption 으로 "오래됨" 뉘앙스(정리 후보), 과한 색 금지.
- 헤더 행에 "최근 차단" `<th>` 추가(hit_count 옆). 기존 종류/값/동작/활성/비고/생성 컬럼 유지.

### 3-4. (범위 밖 — 195 로) 자동 제외 후보 제안

- 이 리포트의 hit_count·186 불량률을 신호로, 반려/불량 높은 도메인을 **자동 "제외 후보"** 로 띄우는 건 **195**. 여기서는 계측·가시화까지만.

## 4. 회귀 가드 / 비기능 요건

- SQL 미적용(RPC/컬럼 없음) → flush skip·`last_hit_at` null·리포트 "아직 집계 전". 크롤·어드민 정상(회귀 0).
- `exclusionHits` 후행 옵션 파라미터(default `new Map()`) → 미갱신 호출부도 컴파일. flush 는 `size > 0` 일 때만 1콜.
- 매칭/판정·`counts` 불변(집계는 부가 관측). 아이템별 DB write 추가 없음(런당 RPC 1콜).
- 어드민 한정·service_role. 신규 hex 0. SQL 외 의존성 0. `formatKst` 기존 유틸 재사용.

## 6. 후속 (범위 밖 → 195~197)

- **195**: 반려율·불량률(186) + hit_count(194) 기반 **자동 제외 후보 제안**(원클릭 규칙화). 학습 루프 캡스톤.
- **196**: 구글뉴스 리다이렉트 → 원문 `canonical_url` 정규화(C-2, 교차중복 토대).
- **197**: 같은 사건 다매체 near-dup 클러스터링(196 canonical 위).
- (그 외) 런별 차단 히스토리 로그 테이블·규칙별 효과 추세 차트.
