# 통합 개선안 검토 (플래너) — 2026-07-24

> 대상: "인증·콘텐츠 수집·운영관리·사용자 피드백 통합 개선안"
> 관점: 코드 현실 대조 + 실현성·순서·리스크. 코드 근거는 앞선 인증/크롤러 조사(origin/main) 기준.

---

## 0. 총평
진단은 대체로 정확하고, 특히 **§6 파이프라인(짧은 RSS reject → 소스 편향)** 은 앞서 내가 독립 조사한 결과와 완전히 일치한다. 다만 이건 "기능 추가"가 아니라 **다개월 프로그램**이다. 우리 협업 루프(슬라이스 단위 배포)에 맞게 Phase로 쪼개야 하고, 한 번에 다 하려 하면 안 된다.

그리고 전체 실현성을 좌우하는 **관통 제약 하나**가 있다 — 이걸 먼저 풀지 않으면 큐·재시도·긴급알림·백필이 전부 무력화된다.

---

## 1. 🔴 관통 제약 — 실행 카덴스 (가장 먼저 결정할 것)
개선안의 상당 부분이 **자주 도는 워커**를 전제한다: 큐 드레인, 재시도(5분·30분·3시간), 긴급 알림 "즉시" 발송, 백필 커서 반복, fingerprint 집계.

그러나 **Vercel Hobby 는 크론 하루 1회**이고 "프로 재업그레이드는 옵션에서 제외" 확정이다. 이 상태로는:
- "즉시" 긴급 알림 → 하루 1회로 강등
- 재시도 5분/30분 → 불가
- 큐 상시 드레인 → 하루 한 번만 → 게시 게이트로 바꾸면 비공개 기사 적체

**해법: 시간 민감 처리를 Vercel 크론이 아니라 Supabase 로 옮긴다.**
- Supabase **pg_cron + Edge Functions** 는 Vercel Hobby 와 무관하게 **분 단위** 스케줄이 가능하다. 수희가 Supabase 를 소유하므로 여기서 큐 워커·재시도·긴급 알림·백필 커서를 돌린다.
- 역할 분담: **Vercel** = 요청 처리·화면·간헐 배치, **Supabase** = 상시 백그라운드 워커.
- 이 결정이 **Pro 없이** 큐/알림/재시도/백필 카덴스를 여는 핵심이다. 개선안의 §7·§8·§9 대부분이 여기에 얹힌다.

→ Phase 1에서 이 실행 모델을 먼저 세운다. 안 그러면 이후 모든 큐/알림 설계가 종이 위에만 남는다.

## 2. 섹션별 검토

### §4 인증 — 대부분 코드 아님(설정) + 패스키만 신규
- **세션 유지(§4.1·4.2)**: 코드에 세션 설정이 전혀 없고 전부 Supabase 대시보드 기본값. `persistSession`/`autoRefreshToken` 은 `@supabase/ssr` 이 이미 켜져 있음(확인). → **수희가 대시보드(Sessions: inactivity/time-box)** 조정이 즉효. "access 짧게 + refresh 길게" 원칙(§4.1) 정확.
- **아이디 저장(§4.3)**: 지시서 419 진행 중.
- **autocomplete**: 이미 `email`/`current-password` 적용됨. §4.3의 `autocomplete="username"` 권장은 비번관리자 호환에 실제 도움 — 419에 소소하게 반영 가능.
- **패스키/생체(§4.4·4.5)**: 완전 신규(라이브러리·테이블·RLS·엔드포인트). §4.4의 "도메인 확정 후" 정확 — WebAuthn rpId 가 도메인 고정이라 도메인 바뀌면 자격증명 무효. "패스키 로그인 vs 앱 잠금 해제" 구분(§4.5)도 정확. **복구수단 필수(§4.4)** — 이거 안 지키면 계정 영구 락아웃 위험, 반드시 지킬 것.
- **관리자 차등(§4.6)**: 좋음. `is_admin()` 이미 있음.
- **반복 로그인 지표(§4.2)**: 이벤트 추적 인프라(§10) 위에서만 가능 → 선후 관계 있음.

### §5 인앱 캠페인 — 방향 타당, 신규 테이블+어드민
- "즉시 모달 지양, 로딩 후 노출"(§5.2)·"세션당 1개·우선순위 1개"(§5.4) 정확 — 광고 피로 방지 핵심.
- **재사용**: `ui/dialog`(모달)·`ReportCard`·뉴스레터/AI리포트 콘텐츠·`DetailSheet`(모바일 bottom sheet).
- **신규**: campaign 테이블 + **per-user 노출/닫기 기록**(빈도 제한의 핵심) + 어드민 관리 UI(§5.6).

### §6·§7 파이프라인 — 즉시 최우선(핵심 버그)
- **§6.6 "250자 reject 제거 → stub 저장 → 게시 게이트"** = 내가 진단한 소스 편향의 근본 원인과 정확히 일치. **여기부터 착수 권장.**
- "저장 게이트가 아니라 게시 게이트"(§6.5) — 프레이밍 정확. 신규 기사는 무조건 보강 큐 등록, 보강·품질 통과분만 공개.
- `crawl_interval_minutes` NULL → 기본주기 적용, `disabled=true` 명시 제외(§6.6) — 로직+데이터. 수희 데이터 보정 병행.
- `discovered_at` 필수 / `published_at` nullable(§6.6) — 스키마 추가(수희). 발행일 없다고 버리지 않기 정확.
- ⚠️ **게시 게이트로 바꾸면 "수집됐으나 비공개"가 쌓인다.** 보강 워커 처리량이 관건 — Hobby 하루1회면 적체. → §0의 Supabase 상시 워커가 전제. (파이프라인 로직 전환은 Vercel 에서 가능하나, 큐 드레인 카덴스는 Supabase.)

### §8·§9 운영 인텔리전스 — 설계 훌륭, 카덴스가 제약
- fingerprint 묶기(§8.5)·자동 해결(§8.6)·기술로그→운영언어(§8.1) 설계 좋음.
- **이미 있음**: `EnrichJobsDock`(작업 실행 현황), 417 사용량·한도, `ops_requests`(운영 이슈 뼈대로 활용 가능). → 처음부터 새로 만들지 말 것.
- 3단 알림(§9.1): 일일/주간 = 스케줄 메일(Brevo 발송 인프라 이미 있음), **긴급 "즉시" = Supabase 워커**(Vercel Hobby 불가). 일일 브리핑 §14 구성은 구체적이고 좋음 — morning 스케줄 패턴 재사용 가능하나 대상이 운영지표라 별도.

### §10 사용자 분석 — 가장 큰 신규 데이터 인프라
- 현재 `last_seen_at`·`view_count`·`bookmark_count` 만 있고 **활동 이벤트 로그가 없다.** DAU/WAU/퍼널/리텐션엔 **활동 이벤트 테이블(신규)** 이 선행. 이게 이 축의 최대 리프트.
- "로그인 ≠ 활성"(§10.2) 정확. 가입 현황은 일부 존재(가입자 현황+조직 416). "개인정보 나열 대신 집계+어드민 링크"(§10.5) 좋은 원칙.

### §11·§12·§13 피드백 센터 — 순수 신규
- 테이블(피드백·상태·답변·클러스터) + 사용자 UI(전역/화면별/콘텐츠별) + 어드민.
- 자동 컨텍스트 첨부(§11.3)·사용자에게 심각도 선택 안 시킴(§11.3) 정확.
- **유사신고 묶기(§12.3)는 §8.5 운영이슈 fingerprint 와 같은 메커니즘** → 공용화. 피드백→운영이슈 연결(§12.4)이 좋은 통합 고리.
- 콘텐츠별 신고(AI요약·번역·중복·분류 오류)는 보강/분류 파이프라인과 연결 가능.

## 4. 권장 순서 (프로그램 로드맵)

**Phase 0 — 지금·저비용**
- 419 아이디 저장(진행) · autocomplete `username` 소소 반영 · **수희: Supabase 세션 수명 연장**(대시보드). → 체감 즉시.

**Phase 1 — 핵심 버그 + 실행 토대(최고 ROI)**
- §6.6 파이프라인 전환: reject 제거 → stub 저장 → 게시 게이트 (Sonnet) + `crawl_interval_minutes`/`discovered_at` 스키마·데이터 (수희).
- **§0 실행 모델 결정**: Supabase pg_cron + Edge Function 워커 도입 (수희) — 이후 모든 큐/알림/백필의 전제.

**Phase 2 — 파이프라인 신뢰성**
- 백필 파이프라인(커서·신규와 분리 §7.1) · 재시도 정책(§7.5) · 큐 분리(§7.4) — Supabase 워커 위.
- 운영 인텔리전스 최소판: 운영 이슈(fingerprint §8.5) + 일일 브리핑 메일(§14).

**Phase 3 — 사용자 접점**
- 피드백 센터(§11~13, 사용자 UI + 어드민 + 클러스터) · 인앱 캠페인(§5).

**Phase 4 — 분석·고급 인증**
- 사용자 분석(이벤트 인프라 §10 → 퍼널·리텐션) · 패스키/생체(§4.4·4.5, 도메인 확정 후).

## 5. 리스크
- **실행 카덴스(§1)** — 미해결 시 큐·알림·백필 전부 하루1회로 강등. 최우선 결정.
- **테이블·RLS 급증** — 캠페인·피드백·이벤트·큐·백필 등 신규 테이블 다수 → 수희 부하 + RLS 설계 신중(앞서 AI리포트 RLS 누락 전례 있음: 발행분 공개 정책 빠져 있었음).
- **보안: 장기 세션 × 공용 기기** — 관리자 짧은 만료·민감작업 재인증(§4.6) 반드시 지킬 것.
- **스코프** — 다개월. Phase 경계를 지키고 슬라이스로 배포. 한 번에 착수 금지.

## 6. 결론
방향은 옳다. 실행에서 딱 하나만 먼저 못박으면 나머지가 풀린다 — **시간 민감 처리를 Supabase(pg_cron+Edge Functions)로**. 그 위에서 **Phase 1의 파이프라인 게시-게이트 전환**이 지금 가장 아픈 문제(소스 편향·본문 누락)를 바로 해소한다. 이 둘을 먼저 하고 나머지를 Phase로 이어가길 권한다.
