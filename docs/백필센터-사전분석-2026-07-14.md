## 1. 현재 수집 흐름

```
Vercel Cron (12개)  ─ /api/cron/crawl  (매일 20:00 UTC = 05:00 KST)
        │
        ▼
runCrawl(options)              src/lib/crawler/orchestrator.ts (1,243행~, 파일 3,089행)
        │
        ├─ sources(is_active) · keywords · keyword_groups 로드
        ├─ 어댑터로 아이템 발견        adapters/index.ts · news-site.ts · youtube.ts
        │     (RSS/Atom, 키워드 검색 수집, 회사 seed 검색 수집, YouTube)
        │
        └─ 아이템마다 processCrawlItem():
              dedup(URL → title_hash → body_hash → near-dup 후보)
              → quality.ts 품질/EXCLUDE 게이트
              → similarity.ts near-dup 클러스터링(cluster_id)
              → keyword_groups 매칭 → importance_score · matched_groups/keywords
              → (예산 내) classifyRelevance() LLM 게이트
              → 번역(translateEnglishContent)
              → contents INSERT
              → tagContent(요약·분류) · content_signals 적재
        │
        ▼
crawl_logs 에 소스별 결과 기록 (fetched/inserted/duplicate/held/error)
job_runs 에 잡 실행 이력 기록 (runJob 래퍼, 289)
```

**핵심 관찰: 수집과 AI 가공이 한 트랜잭션 안에 붙어 있다.** `processCrawlItem` 안에서 dedup → 품질 → **LLM 분류** → **번역** → insert → **요약/태깅**이 순차로 일어난다. 작업지시서 §2-3이 지적한 바로 그 구조다. 다만 완전히 붙어 있는 건 아니고, 이미 **부분적으로 분리된 백필 크론들**이 있다:

| 크론 | 하는 일 |
|---|---|
| `/api/cron/body-backfill` | 본문(풀텍스트) 지연 추출 — `body_fetched_at` 로 미시도분만 |
| `/api/cron/summary-backfill` | 요약 지연 생성 |
| `/api/cron/signals-backfill` | 시그널 적재 |
| `/api/cron/ai-refresh` | AI 재생성 |

즉 **"수집 → 나중에 AI 보강"이라는 패턴이 이미 이 코드베이스에 존재한다.** 새로 발명할 필요가 없고, 이 패턴을 정식 큐로 승격시키면 된다.

## 2. 현재 데이터베이스 구조

요청서가 가정한 테이블과 실제의 대응 관계:

| 요청서 | 실제 | 상태 |
|---|---|---|
| `sources` | **`sources`** | ✔ 존재. `collection_method` enum(`rss/api/html/manual/youtube`) **이미 있음** |
| `contents` | **`contents`** | ✔ 존재. 아래 참조 |
| `collection_jobs` | **`crawl_logs`** + **`job_runs`**(289) | △ 유사물 존재. 소스별 1회 실행 로그이지 "작업 단위"는 아님 |
| `processing_jobs` | **없음** | ✘ AI 처리 큐가 테이블로 존재하지 않음(크론이 컬럼 null 을 스캔하는 방식) |
| `backfill_jobs` / `backfill_job_items` | **없음** | ✘ 신규 필요 |
| `keywords` · `entities` · `reports` | 전부 존재(`keywords`, `entities`, `ai_reports`) | ✔ |

**`contents` 의 기존 필드 vs 요청서 요구:**

| 요청 필드 | 현재 | 비고 |
|---|---|---|
| `canonical_url` | ✘ (`original_url` 만, **unique index** 있음) | 정규화 URL 컬럼 신규 필요 |
| `external_id` | ✘ | 신규 |
| `content_hash` | △ `title_hash` + `body_hash` **분리 보유** | 이미 3단 dedup 중. 통합 해시는 선택 |
| `collected_at` | ✔ | 있음 |
| `collection_method` | ✘ (sources 에만 있음) | contents 레벨 신규 |
| `is_backfill` / `backfill_job_id` | ✘ | 신규 |
| `raw_content_path` | △ `file_path`(Storage) 있음 | 용도 다름, 신규 권장 |
| `parse_status` / `enrichment_status` | ✘ (대신 `body_fetched_at`·`summary_ko` **null 여부로 암묵 표현**) | **명시 컬럼으로 승격 권장** |

**중복 방지 현황(이미 4단):** ① `original_url` unique index → ② `title_hash` → ③ `body_hash` → ④ `similarity.ts` Jaccard near-dup(클러스터링). 요청서 §8의 1~4차 기준과 **개념적으로 이미 일치**한다. 빠진 것은 **URL 정규화(utm/fbclid/모바일·PC)** 와 `source_id + external_id` 뿐이다.

## 4. 수정이 필요한 기능

1. **`processCrawlItem` 의 AI 결합 분리** — insert 이후의 `tagContent`(요약·분류)를 **큐 등록으로 대체**. 실시간 수집은 지금처럼 즉시 처리하되, **백필 경로는 큐만 등록**하도록 분기. (기존 실시간 동작 불변이 §2-1 요구)
2. **`sources`** — `collection_method`(단일) → `live_collection_method` / `backfill_collection_method` **2속성으로 분리**. 기존 컬럼은 남기고 `live_*`의 기본값으로 마이그레이션(하위호환).
3. **URL 정규화 유틸 신설** — `resolve-url.ts` 확장(utm/fbclid/gclid/trailing slash/m. 서브도메인).
4. **`contents`** — `canonical_url`, `external_id`, `collection_method`, `is_backfill`, `backfill_job_id`, `enrichment_status` 추가(전부 nullable/기본값).
5. **어드민 IA** — `운영센터 > 콘텐츠 수집 관리` 하위로 `소스 관리 / 실시간 수집 현황 / 과거 데이터 적재` 재편(현재는 `crawl-settings`·`sources`·`crawl-logs`가 평면 배치).

## 5. 신규 추가가 필요한 기능

- **`backfill_jobs` / `backfill_job_items` 테이블** (요청서 §7 그대로. `cursor` 컬럼이 재개의 핵심)
- **수집기 4종**: `RSSCollector` / `SitemapCollector` / `ArchiveCollector` / `ManualUrlCollector` — **공통 반환 형식**(요청서 §5-1) 준수
- **워커** — `/api/cron/backfill-worker`(1~5분 주기) + 어드민 수동 실행. 배치 20~100건, 배치마다 cursor·통계 저장
- **AI 처리 큐** — `enrichment_status` 기반 스캔 큐(별도 테이블 없이 컬럼 큐로 시작 가능. 기존 백필 크론과 동일 패턴)
- **미리보기(§9-3)** — URL 발견 + DB 중복 대조까지만. 원문 수집 없음
- **Backfill Center 어드민 화면**(목록/생성/상세/재처리)
- **robots.txt 확인 · 지수 백오프 · 요청 간격 제어**

| # | 위험 | 완화 |
|---|---|---|
| 1 | **`contents_original_url_key` unique index** — 백필이 대량 insert 하면 23505 충돌이 폭증한다. 현재 코드는 23505를 "중복 스킵"으로 처리하지만, 백필에선 이걸 **정상 경로**로 세야 한다 | 사전 SELECT 로 중복 판정 후 insert. 23505는 최후 방어선 |

## 7. 추천 구현 순서

작업지시서의 범위가 크므로 **4단계로 쪼갠다.** 각 단계가 독립적으로 가치를 낸다.

**1단계 — 기반(스키마 + 정규화)**
`backfill_jobs`·`backfill_job_items` 테이블, `contents` 신규 컬럼, URL 정규화 유틸, `sources.live/backfill_collection_method`. **실행 로직 없음.** 여기서 기존 기능 회귀만 없으면 나머지는 안전하다.

**2단계 — 수집기 + 워커 (실행 없는 미리보기부터)**
`SitemapCollector` → `RSSCollector` → `ManualUrlCollector` 순. **미리보기(§9-3)를 먼저 만든다** — URL 발견 + 중복 대조만 하므로 사이트에 부담이 없고, 이것만으로도 "이 소스에서 과거 몇 건을 건질 수 있나"를 알 수 있다. 그다음 워커(배치·cursor·재개).

**3단계 — AI 처리 큐 분리**
`enrichment_status` 컬럼 도입 + 기존 `summary-backfill`·`body-backfill` 크론을 이 큐로 통합. **실시간 수집 경로는 건드리지 않는다**(즉시 처리 유지).

**4단계 — `ArchiveCollector` + 사이트별 어댑터**
선택자 기반 목록 페이지 크롤링은 사이트마다 깨지므로 **가장 마지막.** 1~3단계로 사이트맵·RSS·CSV를 커버하면 실제 필요 소스의 상당수가 해결된다.

## 8. 요청서에 대한 이견 (Opus)

세 가지만 짚는다.

**① `processing_jobs` 테이블을 새로 만들 필요가 있는지 재검토가 필요하다.** 이 코드베이스는 이미 "컬럼 null 스캔 → 배치 처리" 방식(`body_fetched_at is null`, `summary_ko is null`)으로 4개 백필 크론을 굴리고 있고, 잘 돌고 있다. 큐 테이블을 새로 만들면 **두 개의 큐 개념이 공존**하게 된다. `contents.enrichment_status` 컬럼 하나로 시작하고, 재시도·우선순위가 실제로 필요해질 때 테이블로 승격하는 편이 낫다.

**② `content_hash` 통합 컬럼은 필요 없다.** 이미 `title_hash` + `body_hash`로 나뉘어 있고 dedup 로직이 이 둘을 각각 쓴다. 통합 해시를 추가하면 중복 개념이 셋이 된다.

**③ 가장 큰 리스크는 스크래핑이 아니라 AI 비용이다.** 과거 기사 5,000건을 넣는 건 기술적으로 어렵지 않다. 문제는 그 뒤다 — 요약·분류·임베딩을 전부 돌리면 무료 LLM 티어로는 며칠이 걸리고, 유료면 비용이 든다. 그래서 **§9-2의 "AI 처리: 중요 콘텐츠만" 기본값이 이 설계에서 가장 중요한 결정**이고, 여기에 더해 **"AI 없이 적재만 하고, 나중에 필요할 때 켠다"** 는 경로가 반드시 열려 있어야 한다. `enrichment_status='pending'`으로 쌓아두고 검색·근거로는 이미 쓸 수 있게 하는 것이 핵심이다(전략보고서 349의 역인입도 같은 구조).

## 10. 개정 설계 — "AI 없는 단순 수집" (David 결정 반영)

### 10-1. 무엇이 사라지나

백필 경로에서 **LLM 호출을 0회로** 만든다. 제외 대상:

- 요약(`summary_ko`) · 번역(`body_translated_ko`) · 관련도 LLM 게이트(`classifyRelevance`)
- 논조(`sentiment`) · LG U+ 관점(`lgu_impact`) · 임베딩 · 커버 이미지 생성

### 10-2. 무엇이 **남아야** 하나 — 룰 기반 가공은 유지한다

**중요:** "AI 제외"가 "가공 전면 제외"는 아니다. 이 코드베이스의 다음 처리는 **LLM이 아니라 결정적 규칙**이고, **비용이 0이며, 이것이 없으면 백필 데이터가 어디에도 안 잡힌다.**

| 처리 | 비용 | 없으면 |
|---|---|---|
| `keyword_groups` 매칭 → `matched_groups` · `matched_keywords` | 0 (정규식) | **기업동향·해시태그·주간리포트에 안 잡힌다** |
| `importance_score` 계산 | 0 (가중치 합) | 추천·정렬에서 바닥 |
| `title_hash` / `body_hash` | 0 (해시) | 중복 제거 불가 |
| `search_vector` (tsvector 트리거) | 0 (DB 트리거) | 검색에 안 걸린다 |
| `quality.ts` 게이트 | 0 (규칙) | 쓰레기 유입 |
| 본문 파싱(`normalize.ts`) | 0 (HTTP + 파싱) | 근거로 못 씀 |

→ **백필 = 원문 수집 + 파싱 + 중복 제거 + 룰 태깅 + 저장.** 여기까지가 "단순 수집"의 정확한 범위다.

### 10-3. LLM이 필요해지는 시점 — 지연(lazy) 보강

`contents.enrichment_status = 'pending'` 으로 쌓아두고, **실제로 쓰일 때** 채운다.

1. **사용자가 그 콘텐츠를 열 때** — 기존 `body-backfill`·`summary-backfill` 크론이 이미 하던 일과 동일. 백필분도 같은 큐에 자연히 들어온다.
2. **어드민이 범위를 골라 일괄 실행** — 예: "AIDC 그룹 매칭 + importance ≥ 임계치인 백필분만 요약 생성"
3. **전략보고서 근거로 인용될 때**(349) — 그때 요약을 채운다.

요약이 없는 콘텐츠는 카드에서 **제목 + 출처 + 발행일**만 보인다. 검색·근거·주간리포트 사실추출에는 **본문이 있으므로 이미 충분히 쓸모 있다.**

### 10-4. 단순화되는 것들

| 항목 | AI 포함 설계 | 단순 수집 설계 |
|---|---|---|
| 배치 크기 | 20~100건 (LLM 지연 때문) | **100~300건** (I/O만) |
| 워커 1회 처리 시간 | 예측 불가(LLM 큐·한도) | **예측 가능**(요청 간격 × 건수) |
| 실패 모드 | HTTP + LLM 한도 + 파싱 | **HTTP + 파싱** 뿐 |
| 비용 | 건당 LLM 토큰 | **0** |
| 요청서 §12(AI 처리 정책) | 필요 | **이번 범위에서 삭제** |
| `ai_queued_count` 컬럼 | 필요 | 불필요(단, 컬럼은 남겨도 무해) |

**near-dup 클러스터링도 백필 경로에서는 뺀다**(§6-8 위험). 건당 후보 조회가 DB를 때린다. 기존 `cluster-backfill.ts`로 **사후 배치** 처리.

### 10-5. 개정된 파이프라인

```
[미리보기]  URL 발견(sitemap/RSS/CSV) → 기간 필터 → DB 중복 대조 → 예상 건수 리포트
                                                       (원문 수집 없음)
        ↓ 관리자 확인 후 실행
[워커]  /api/cron/backfill-worker  (5분 주기 · 전용 크론 슬롯)
        cursor 이후 N건 →
          ① URL 정규화(utm/fbclid/m. 제거)
          ② 중복 검사(canonical_url → title_hash)   ← LLM 0
          ③ 원문 fetch (요청 간격 1~3s, 동시 2, 429 지수 백오프)
          ④ 본문 파싱(normalize.ts)
          ⑤ 품질 게이트(quality.ts)
          ⑥ 룰 태깅(keyword_groups → matched_groups·importance_score)
          ⑦ contents INSERT (is_backfill=true, enrichment_status='pending')
          ⑧ cursor + 통계 저장 → 반환
        ↓ (별도, 나중에, 선택)
[지연 보강]  기존 summary/body 백필 크론이 pending 을 소비
```

### 10-6. 이 결정의 대가 (정직하게)

- 백필된 과거 기사는 **요약이 없다.** 콘텐츠 카드가 제목만 보이는 상태로 쌓인다. 목록 화면의 밀도가 떨어진다.
- 영문 기사는 **번역이 없다.** 원제 그대로 보인다.
- `sentiment`·`lgu_impact`가 없으므로 **경쟁사 뉴스 탭의 위기/기회 배지에 안 잡힌다.** 과거분은 배지 없이 나온다.

→ 이건 **수용 가능한 대가**다. 백필의 1차 목적은 "보여주기"가 아니라 **"근거로 쓸 수 있는 원문을 확보하는 것"**이고, 그 목적에는 본문 + 룰 태깅이면 충분하다. 보여줄 필요가 생긴 범위만 나중에 골라서 LLM을 돌리면 된다.
