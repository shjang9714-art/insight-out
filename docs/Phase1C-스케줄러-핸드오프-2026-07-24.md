## 공통 사전조건
- **`CRON_SECRET`**: 인사이트 아웃 Vercel 환경변수와 **동일 값**을 스케줄러 측 시크릿으로 등록.
- 대상 엔드포인트: `GET https://insight-out-app.vercel.app/api/cron/body-backfill`
  - 인증: 헤더 `Authorization: Bearer <CRON_SECRET>`
  - 동작: 1회 호출당 `body_fetched_at IS NULL` 큐를 배치(30건/270초 바운드) 드레인 → 풀본문 추출 → (426 후)관련도 통과분 게시.
  - 멱등: `body_fetched_at` 마킹으로 재처리 안전. `runJob` 락으로 동시 실행 보호.

## 옵션 A — GitHub Actions (SQL 불필요, 권장)
리포지토리 워크플로 파일 1개 + GitHub 시크릿. Supabase SQL 접근 불필요.

**1) 시크릿 등록** (리포 Settings → Secrets and variables → Actions):
- `CRON_SECRET` = (Vercel 의 CRON_SECRET 과 동일 값)

**2) 워크플로 파일** `.github/workflows/enrich-drain.yml`:
```yaml
name: enrich-drain
on:
  schedule:
    - cron: '*/10 * * * *'   # 10분마다(UTC). GitHub 무료 티어는 수 분 지연·불규칙 가능
  workflow_dispatch: {}       # 수동 실행(테스트용)
concurrency:
  group: enrich-drain
  cancel-in-progress: false
jobs:
  drain:
    runs-on: ubuntu-latest
    steps:
      - name: Call body-backfill enrich drain
        run: |
          curl -sS -X GET "https://insight-out-app.vercel.app/api/cron/body-backfill" \
            -H "Authorization: Bearer ${{ secrets.CRON_SECRET }}" \
            --fail-with-body
```
- ⚠️ **스케줄 워크플로는 기본 브랜치(main)에 있어야 실행**됨. → 이 파일 커밋은 **426 배포 후** 진행(활성화 게이팅).
- 먼저 `workflow_dispatch` 로 **수동 1회 실행해 200 확인** 후 스케줄 신뢰.
- 주의: GitHub 무료 스케줄은 지연될 수 있음(대략 10~15분). 백필 드레인엔 충분.

**3) 확인**: Actions 탭에서 실행 로그(200) · Vercel 함수 로그에 body-backfill 호출 · `pending & body_fetched_at IS NULL` 큐 감소.

## 옵션 B — Supabase pg_cron + pg_net (SQL 여건 될 때)
Supabase SQL 접근이 되면 이 방식이 인프라상 깔끔.

```sql
create extension if not exists pg_cron;
create extension if not exists pg_net;

-- CRON_SECRET 을 Vault 에 저장해두었다고 가정 (name = 'CRON_SECRET')
select cron.schedule(
  'enrich-drain',
  '*/10 * * * *',
  $$
  select net.http_post(
    url    := 'https://insight-out-app.vercel.app/api/cron/body-backfill',
    headers:= jsonb_build_object(
      'Authorization', 'Bearer ' || (select decrypted_secret from vault.decrypted_secrets where name = 'CRON_SECRET'),
      'Content-Type', 'application/json'
    ),
    body   := '{}'::jsonb
  );
  $$
);
```
- ⚠️ `/api/cron/body-backfill` 은 GET 이지만 다수 라우트가 POST 도 허용 — 안 되면 route 에 GET 처리 확인/보강 필요(현재 GET). pg_net 는 http_post 만 제공하므로, GET 전용이면 **route 를 POST 도 받게 소폭 확장**하거나 옵션 A 사용.
- 확인: `select * from cron.job;` · `select * from cron.job_run_details order by start_time desc limit 10;`

> ⚠️ 옵션 B 유의: body-backfill route 가 현재 **GET 전용**이라 pg_net(POST)와 안 맞을 수 있음. 옵션 A(curl GET)는 이 문제 없음 → **A 권장.**

## 튜닝·리스크
- **간격**: 초기 적체 크면 5분, 안정되면 10~15분.
- **1회 바운드**: 현재 limit 30 / deadline 270s. 자주 부르면 **1회를 짧게**(limit 20, deadline 90~120s) 조정 권장 → 함수시간·중복 최소화(426 또는 별도 소폭 조정).
- **함수 사용량**: 자주 호출 × 최대 300s → Vercel Hobby 함수 실행시간 총량 모니터. 1회를 짧게 하면 여유.
- **활성화는 426 이후**(관련도 게이트) — 재차 강조.
