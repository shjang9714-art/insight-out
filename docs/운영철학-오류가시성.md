# 운영 철학 — 기능 실패의 가시성·관리 (David, 2026-07-26)

> 개별 버그가 아니라 파이프라인 전반을 관통하는 설계 원칙. 신규 기능·수정 시 반드시 적용.

## 원칙 (David 확정)
**기능이 "원래 의도대로" 동작하지 않으면:**
1. **에러 로그를 남긴다** — 조용히 실패(silent fail) 금지. 실패 사유를 구조화해 기록.
2. **어드민에서 관리된다** — 관리자가 실패를 한눈에 보고, 원인 파악하고, **재실행**할 수 있어야 한다.

즉 "실패했는데 아무도 모르고, 재시도도 안 되고, 검토대기에만 갇히는" 상태를 만들지 않는다.

## 배경 — 이 원칙이 나온 사례 (2026-07-26 개선검토)
- **본문 추출 실패**(조선비즈): 1회 실패 후 `body_fetched_at` 영구 마킹 → 재시도 없음 → 검토대기 영구 정체. 실패 사유·재시도 UI 부재. → 지시서 441(재시도 정책)로 부분 해소.
- **유튜브 요약 미생성**: `summarizeYoutubeKo` 실패 시 `summary_attempted_at` 영구 마킹 → 영구 미생성. 실패가 어디에도 안 보임. → 백로그(요약 재시도).
- **LLM 한도 초과**: 폴백/차단 상태가 UI에 안 뜸 → "되는지 안 되는지" 모름. → 백로그(사용량 상태 표시).
공통 결함: **silent fail + no retry + no admin visibility.**

## 시스템적 구현체 = 작업·오류 센터 (`/admin/errors`, nav 준비중 S9)
현재 nav에 `작업·오류 센터`가 "준비중"으로 존재. 이게 이 원칙의 집약 지점.
- **수집할 실패 종류**: 수집(crawl_logs) · 본문추출(body extract) · AI생성(요약·인사이트·리포트) · 자막(youtube transcript) · 번역/TTS · 발행.
- **기존 자산 재사용**: `job_runs`(크론/배치 실패·meta) · `ops_issues`(429 fingerprint 탐지) · `AdminFailedJobsCard`(최근 실패 크론). 이미 크론 레벨 실패는 잡힌다.
- **빠진 것 = 아이템 레벨 실패**: 개별 콘텐츠의 본문추출/요약/자막 실패가 구조화 기록되지 않음(현재 console.error·조용한 마킹뿐). 이걸 **실패 사유 컬럼/이벤트로 남기고**, 오류 센터에서 목록·필터·재실행(enrichByIds 등 재사용).

## 신규 기능 체크리스트 (앞으로 모든 지시서에 반영)
- [ ] 실패 경로가 **사유를 기록**하는가? (console.error만으론 부족 — 조회 가능한 컬럼/이벤트/job_runs.meta)
- [ ] 실패가 **재시도**되는가, 아니면 영구 정체되는가? (재시도 정책 or 수동 재실행 경로)
- [ ] 관리자가 **어드민에서 실패를 보고 재실행**할 수 있는가?

## 백로그 (이 원칙 관련)
- **작업·오류 센터(`/admin/errors`) 1차** — 아이템 레벨 실패(본문추출·요약·자막) 기록·목록·재실행. 오류 가시성의 본체. (규모 중, 일부 실패사유 컬럼 SQL 동반 가능)
- **요약 재시도 정책 + 유튜브 자막 활용** — 441(본문 재시도)과 동형. summary_attempted_at 영구 마킹 대신 백오프 재시도, 유튜브는 자막 있으면 요약에 활용(품질↑).
- **LLM 사용량 초과 상태 표시**(개선검토 [2], 443 후보) — 폴백/차단 명시.
