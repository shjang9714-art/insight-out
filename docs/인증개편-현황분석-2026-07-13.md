## 0. 한 줄

**스펙이 전제한 것이 하나도 없다.** 비밀번호도, 초대 코드도, 커스텀 OTP 테이블도 **전부 0회**다.
현재는 **Supabase Auth에 전적으로 위임한 패스워드리스(이메일 6자리 OTP) 로그인**이다.
→ 스펙은 **"수정"이 아니라 "인증 방식 교체(재구축)"** 다. 범위가 완전히 다르다.

**그리고 조사 중 심각한 취약점 2건을 찾았다(§8).** 개편보다 **이게 먼저다.**

## 1. 현재 인증 제공자

**Supabase Auth 단독.** 자체 인증 없음.

## 2. 현재 플로우 (가입 = 로그인. 구분이 없다)

```
[로그인 화면]  이메일 입력
      ↓  signInWithOtp(shouldCreateUser: true)
      ↓  ── Supabase Auth Hook(도메인 게이팅) 이 여기서 거부 가능 (§6)
      ↓  auth.users 행 생성 (신규면)
      ↓  DB 트리거 handle_new_user()  →  public.users 행 생성
      ↓                                  approval_status = 'approved' (자동승인!)
      ↓                                  allowlist.is_admin 이면 role='admin' 까지
[메일로 6자리 코드]  입력
      ↓  verifyOtp(type:'email')  →  세션 발급
      ↓
[미들웨어 게이트]
   onboarding_completed === false  →  /onboarding 강제
   approval_status !== 'approved' && role !== 'admin'  →  /pending
   /admin/*  &&  role !== 'admin'  →  /dashboard
      ↓
[온보딩]  이름·팀·기본렌즈·담당서비스  →  users.upsert({ onboarding_completed: true })  (클라이언트 직접)
      ↓
[/dashboard]
```

**즉 "회원가입"이라는 별도 플로우가 존재하지 않는다.** 처음 로그인하면 그게 가입이다.

## 3. 인증코드는 **초대 코드가 아니라 이메일 OTP**다

| 스펙 | 현실 |
|---|---|
| 초대 코드 입력 → 유효성·만료·조직·권한 확인 | **초대 코드 기능·테이블 0건.** `invite`/`invitation`/`초대` grep → 콘텐츠 텍스트 4건뿐, 인증과 무관 |
| 이메일 인증번호 발송 | ✅ 있음 — 단 **Supabase Auth가 발송·검증·만료를 전부 처리** |

**가입 통제는 초대 코드가 아니라 "도메인 + allowlist"다:**
- `public.signup_email_allowlist` (`docs/sql-handoff/239-*.sql:11-20`, +`is_admin` 컬럼은 240)
- 등재 계정: `yjhead@gmail.com`, `sh.jang9714@gmail.com` (둘 다 `is_admin=true`)
- ⚠️ **이 테이블은 `supabase/schema.sql`에 없다.** 핸드오프 SQL로만 존재 → 새 환경 구축 시 누락된다.

## 4. 비밀번호는 **저장도 관리도 되지 않는다**

`password` / `resetPasswordForEmail` / `updateUser({password})` / `password_hash` / `set-password`
→ **`.ts`·`.tsx`·`.sql` 전수 grep = 0회.**

Supabase의 `auth.users.encrypted_password`는 존재하지만 **한 번도 쓰이지 않는다**(OTP·OAuth만 사용).

---

## 5. "비밀번호 미설정 사용자" — **전원이 그렇다**

스펙 §4는 *"이메일 인증은 됐지만 비밀번호가 없는 계정"* 을 식별하라고 한다.
→ **현재 사용자 9명 전원이 여기 해당한다.** 비밀번호를 가진 계정이 0명이다.

식별 자체는 가능하다: `auth.users.encrypted_password is null` 로 판별.
하지만 **"기존 사용자 마이그레이션"이 아니라 "전원 최초 설정"**이다. 스펙 §4의 예외 플로우가 사실상 **주 플로우**가 된다.

---

## 6. 도메인 게이팅 — **코드가 아니라 대시보드 설정에 걸려 있다**

- Hook 함수는 SQL로 존재: `docs/sql-handoff/239-*.sql:25-49` `hook_restrict_signup_by_email_domain(event jsonb)` — `@lguplus.co.kr` 또는 allowlist면 허용, 아니면 403
- **활성화는 Supabase 대시보드 수동 설정** (Auth → Hooks → Before user created). 같은 파일 `:84-89`가 *"SQL만으로는 훅이 안 켜짐"* 이라고 명시
- **앱·DB 트리거 어디에도 도메인 검사가 없다.** `LoginCard.tsx:119` 주석: *"클라이언트 도메인 하드검증 금지 — allowlist 예외계정 보호"*

🔴 **fail-open 구조다.** Hook이 대시보드에서 꺼지면:
```
아무 이메일 → signInWithOtp(shouldCreateUser:true) → auth.users 생성
           → handle_new_user() 가 approval_status='approved' 로 즉시 생성 (240 SQL:35-42)
           → /pending 안 거치고 바로 /dashboard
```
**차단선이 코드 밖에 단 하나뿐이다.**

## 8. 🔴 보안 문제 — **개편보다 이게 먼저다**

### 8-1. ⛔ **일반 사용자가 스스로 admin이 될 수 있다** (직접 확인함)

```sql
-- schema.sql:122-125  — 본인 행 UPDATE, 컬럼 제한 없음
create policy "users: 본인 수정"
  on public.users for update
  using (auth.uid() = id) with check (auth.uid() = id);

-- 2026-06-18-가입승인-approval-status.sql:40-52  — 트리거는 있는데 role 이 빠졌다
create or replace function public.lock_approval_columns() ...
  if current_user <> 'service_role' then
    new.approval_status := old.approval_status;
    new.approved_at     := old.approved_at;
    new.approved_by     := old.approved_by;
  end if;                          -- ← new.role := old.role 이 없다
```

**`role`을 보호하는 트리거·정책·GRANT를 전수 grep → 0건.**

→ 로그인한 일반 사용자가 **브라우저 콘솔에서** anon 키로:
```js
await supabase.from('users').update({ role: 'admin' }).eq('id', <본인 id>)
```
**그리고 `role`은 신뢰의 뿌리다.** 미들웨어(`:128`) · `requireAdmin()`(`actions.ts:31`) · RLS `is_admin()` **셋 다 같은 `users.role`을 본다.** 하나만 뚫으면 전부 뚫린다.

**수정은 한 줄이다** — 같은 트리거에 `new.role := old.role;` 추가.
**⚠️ 컬럼 레벨 GRANT로 이미 막혀 있을 가능성은 코드로 확인 불가.** DB에서 확인해야 한다(§10 쿼리).

> 아이러니: **approval 컬럼을 막는 트리거 패턴이 이미 있는데 `role`만 빠뜨렸다.** 인수인계 §4-1의 *"graceful인데 silent"* — 아무 에러도 안 나고, 그냥 통과한다.

## 10. David에게 묻는 것

### 🔴 먼저 — 취약점부터 막을까?

**8-1(자기 admin 승격)은 개편과 무관하게 지금 위험하다.** 수정은 트리거 한 줄이다.

**확인 쿼리 (수희 · 읽기 전용):**
```sql
-- 컬럼 레벨 GRANT 로 이미 막혀 있는가?
select grantee, privilege_type, column_name
  from information_schema.column_privileges
 where table_schema='public' and table_name='users'
   and privilege_type='UPDATE'
   and grantee in ('anon','authenticated')
 order by grantee, column_name;
-- → column_name 에 'role' 이 있으면 🔴 뚫려 있다.
-- → 'role' 이 없으면 ✅ GRANT 로 이미 막혀 있다.
```

### 그리고 — 방향 결정

**A. 스펙대로 비밀번호 인증으로 전환**
- Supabase Auth를 비밀번호 전용으로 쓰고, **OTP는 자체 구현**(목적 구분·해시·실패횟수·rate limit)
- 비용: OTP 테이블 2개 + API 라우트 + 로그인 전면 재작성 + 미들웨어 게이트 + 사용자 9명 전원 비번 설정 유도
- 얻는 것: 스펙의 정책 통제, 초대 코드 기반 조직 확장

**B. 현행 패스워드리스 유지 + 보안 구멍만 막기**
- 8-1~8-5만 수정. 사용자는 지금처럼 OTP로 로그인
- 비용: 트리거 1줄 + 온보딩 서버액션화 + 도메인 검사 DB 이중화 + 캐시 TTL 단축
- 얻는 것: **훨씬 싸고, 사내 도구엔 패스워드리스가 오히려 안전하다**(비번 재사용·유출 리스크 0)

**C. 하이브리드** — 패스워드리스 유지하되, 스펙이 원한 것 중 **초대 코드**만 도입(외부 조직 확장용)

> **플래너 의견: B → (필요하면) C.**
> 스펙의 비밀번호 플로우는 **외부 사용자·다중 조직을 전제**한 설계다. 지금은 **@lguplus.co.kr 사내 도구**고 사용자가 9명이다. 비밀번호를 도입하면 **관리해야 할 공격면(재설정 플로우·세션 무효화·비번 유출)이 늘어난다.**
> **"조직 단위 B2B로 외부 고객사에 판다"** 가 확정된 계획이면 A/C가 맞다. 그게 아직 아니면 B가 맞다.
>
> ⛔ 어느 쪽을 고르든 **8-1은 지금 막아야 한다.**
